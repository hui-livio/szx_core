# SZX 加密工具库与应用设计

> 文档状态：目标设计。
>
> 编制日期：2026-08-04。
>
> 适用范围：在现有 `szx::crypto` 基础上，提供统一加密工具库、Qt GUI 应用和命令行工具。

## 1. 决策摘要

> 实现状态说明（2026-09-03）：当前仓库暂不构建或发布 `crypto_file`。文件容器、分块 I/O
> 和原子输出仍保留在本设计中作为后续规划，当前上层业务直接使用 `crypto_service`；待有明确文件加密需求后再恢复独立模块。

本项目采用“一套加密核心、一个基础加密服务、多个上层业务”的结构：

```text
Qt GUI / CLI -> CryptoApplicationService -> crypto_file ─┐
软授权及其他上层业务 ---------------------> license ────┼-> CryptoService
                                                       └-> crypto + crypto_keystore
                                                           -> Windows CNG/NCrypt/Crypt32
```

核心决策如下：

1. 扩展现有 `modules/crypto`，但把它严格限定为基础密码能力层：只处理字节、密钥和算法，不处理文件路径、业务格式、GUI、CLI 或软授权。
2. 同时支持对称加密和非对称加密；两种文件模式都使用 AES-256-GCM 加密数据。
3. 非对称文件加密采用混合加密：随机 AES 数据密钥加密文件，RSA-OAEP-SHA256 公钥包装数据密钥；不直接使用 RSA 加密大文件。
4. 保留现有 Python `cryptography.fernet` 兼容模式，用于当前模型权重和小型 token。
5. 新增 `modules/crypto_service`，以稳定的 `CryptoService` 作为所有上层业务唯一的加密能力入口；上层不得直接链接算法原语或平台 provider。
6. 新增独立 `modules/crypto_file` 承载 SZX 文件容器、分块 I/O 和原子输出；它调用 `CryptoService`，不把文件业务反向放进基础库。
7. GUI 和 CLI 不直接调用基础加密服务，而是调用同一个 `CryptoApplicationService` 完成文件任务编排。
8. 对称模式支持随机密钥和口令；非对称模式使用接收方公钥加密、私钥解密。
9. 完全不依赖 OpenSSL，避免 MySQL、Qt 或其他模块携带不同 OpenSSL 版本产生 ABI 和部署冲突。
10. 解密必须先通过认证；认证失败不得输出明文或保留“看似成功”的目标文件。
11. 使用临时文件、flush/close 和原子替换，禁止直接覆盖原文件。
12. 密钥、口令、私钥、明文和完整 token 不进入日志、进度消息和异常文本。

## 2. 背景与当前基础

仓库`当前`已有：

- `modules/crypto` 动态库目标 `szx_crypto`，别名为 `szx::crypto`。
- Base64、Hash/HMAC 和 Fernet API。
- Windows CNG/BCrypt 实现的 Fernet 加解密和随机数生成。
- Python Fernet 兼容黄金 token、篡改拒绝和二进制 round-trip 单元测试。
- PCB 模型权重通过 `PcbModelWeightLoader` 使用 Fernet 解密。

当前不足：

- Fernet API 以整块内存和 Base64 token 为主，不适合超大文件流式处理：`目标`。
- 没有统一的文件格式、密钥派生、取消、进度和原子输出契约：`目标`。
- 没有独立 GUI 和 CLI：`目标`。
- Fernet 当前仅在 Windows 实现：`当前`。本工具 P0 明确采用 Windows CNG，不引入 OpenSSL；跨平台不在当前范围。

## 3. 用户与使用场景

| 用户 | 场景 | 入口 |
|---|---|---|
| 软件开发人员 | 通过稳定服务 API 完成加解密、签名验签、摘要、KDF、随机数和密钥操作 | `szx::crypto_service` |
| 业务模块开发人员 | 基于统一加密服务实现文件容器、软授权及其他业务 | `szx::crypto_file` / `szx::license` |
| 算法/维护人员 | 加密模型、配置包、测试数据，验证并解密文件 | GUI |
| 构建与部署脚本 | 批量加密、CI 校验、自动解密 | CLI |
| PCBDetect | 继续读取现有 Fernet 模型权重 | 兼容 API |

第一版不承担证书签发、PKI、磁盘全盘加密、网络 TLS、密钥托管服务器或多人权限审批。

## 4. 功能范围

### 4.1 P0

基础库 `szx::crypto`：

- 安全随机数、SHA-256、HMAC-SHA256 和 PBKDF2-HMAC-SHA256。
- AES-256-GCM 字节级加解密。
- RSA-OAEP-SHA256 字节级加解密和 RSA-PSS-SHA256 签名验签。
- RSA 密钥生成、公私钥导入/导出及稳定 key ID。
- Fernet 文本/二进制 token 加解密兼容 façade，保持现有接口。

上层模块：

- `szx::crypto_service` 是所有上层业务的统一基础服务，提供对称密钥与 RSA 密钥对生成、对称/非对称加解密、签名验签、摘要/KDF、密钥引用、错误和后端能力查询契约。
- `szx::crypto_file` 提供 SZX 容器文件加密、解密、验证、分块 I/O、进度、取消和原子输出。
- `szx::license` 提供离线软授权请求、签发、验签、信息查询、完整校验、安装、机器绑定、期限和功能授权；签发实现仅进入内部发行工具。
- GUI：文件选择、模式选择、密钥/口令输入、进度、取消、结果提示。
- CLI：对称密钥生成、RSA 密钥对管理、`encrypt`、`decrypt`、`verify`、`info`。
- 单元测试、Python Fernet 互操作测试、文件篡改和异常恢复测试。

### 4.2 P1

- Windows DPAPI/凭据管理器集成，避免长期保存裸密钥。
- RSA 私钥受保护备份/恢复和 Windows 证书存储集成。
- 多接收方公钥包装同一个数据密钥。
- 批量文件任务、拖放、任务历史和错误导出。
- `rekey`：不暴露明文到持久文件的密钥轮换。
- 安装、签名和部署包。
- 可选在线激活、浮动授权、吊销列表和授权管理服务。

### 4.3 非目标

- 自研 AES、GCM、SHA 或随机数算法。
- 在 `szx::crypto` 中加入文件路径、JSON、许可证、QML、命令行或产品业务规则。
- OpenSSL、LibreSSL 及其运行时 DLL。
- 直接使用 RSA 分块加密大文件。
- 未认证的 AES-CBC/CTR“仅加密”模式。
- 在命令行参数、配置文件或 GUI 日志中明文保存口令。
- 加密后自动删除源文件。
- 无确认覆盖已存在的输出文件。
- 把许可证签发私钥或签发 API 打包到客户侧 GUI/CLI。
- 承诺软授权能够抵御拥有管理员权限、调试器和二进制修改能力的强攻击者。

所有可执行工具统一放在 `tools/` 下；`modules/` 只保存可复用库和服务。目录位置不改变发布边界：`tools/license-issuer` 仍是内部工具，禁止进入客户安装包。

依赖方向固定向下：

```text
GUI/CLI -> crypto_app -> crypto_file -> crypto_service
license -----------------------------> crypto_service
其他上层业务 ------------------------> crypto_service
crypto_service -> crypto + crypto_keystore -> common
```

`CryptoService` 是上层业务访问加密能力的唯一门面；`crypto_file`、`license` 及未来业务模块不得直接链接 `szx::crypto`、`szx::crypto_keystore` 或任何平台 provider。`license` 只能通过服务使用验签能力，客户侧目标不得链接 `license-issuer`。`szx::crypto` 不依赖 `crypto_service`、`crypto_file`、`crypto_app`、`license`、QML、Widgets、数据库或 PCB 检测模块，也不能链接 OpenSSL。Windows 基础实现只链接系统 `Bcrypt` 和必要的 `Crypt32`；持久化私钥的 `Ncrypt` 依赖隔离在 `crypto_keystore`。

## 6. 加密模式

### 6.1 Fernet 兼容模式

用途：

- 兼容现有数据库模型权重。
- 小型文本、JSON 或二进制 token。
- 与 Python `cryptography.fernet` 双向互操作。

约束：

- URL-safe Base64 32 字节 Fernet key。
- token 使用 AES-128-CBC + HMAC-SHA256 的 Fernet 规范。
- 解密先验证 HMAC，再返回明文。
- 不作为大文件默认格式；不改变当前 token 格式。

### 6.2 SZX 文件容器模式

用途：模型、配置包、归档和其他大文件。默认算法为 AES-256-GCM。GCM 同时提供机密性与完整性，设计依据为 [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)。

默认参数：

| 参数 | 默认值 |
|---|---:|
| 数据密钥 | 256 bit |
| GCM nonce | 96 bit/分块唯一 |
| GCM tag | 128 bit |
| chunk size | 4 MiB |
| 文件扩展名 | `.szxe` |
| 格式版本 | 1 |

每一块使用唯一 nonce，并把固定 header、chunk index、明文长度和 final 标记作为 AAD。header 中记录明文总长度和总块数，且受到认证，用于检测截断、重排、重复和拼接攻击。

### 6.3 对称密钥输入模式

#### 随机密钥

- 生成 32 字节随机主密钥，显示为 URL-safe Base64。
- 密钥不写入加密文件。
- GUI 默认只显示一次并支持显式复制/保存；关闭窗口前提示用户确认已保存。

#### 口令

- 每个文件生成独立随机 salt。
- P0 使用 PBKDF2-HMAC-SHA256，派生 256-bit key；salt、迭代次数和 KDF ID 写入 header。
- 默认迭代次数在目标部署机器上校准，使单次派生达到约 200～500 ms，并把实际值固定到发布配置。
- 口令派生设计参考 [NIST SP 800-132](https://csrc.nist.gov/pubs/sp/800/132/final)。P1 可在格式版本兼容前提下增加 Argon2id KDF ID。

### 6.4 非对称混合加密模式

非对称模式不直接用 RSA 加密文件内容，流程固定为：

```text
加密：CSPRNG 生成 256-bit DEK
  -> AES-256-GCM 分块加密文件
  -> 接收方 RSA 公钥使用 OAEP-SHA256 包装 DEK
  -> wrapped DEK 与公钥指纹写入受认证 header

解密：按公钥指纹定位 CNG 私钥
  -> RSA-OAEP-SHA256 解包 DEK
  -> AES-256-GCM 验证并解密所有分块
  -> 原子提交输出
```

P0 约束：

- RSA 密钥长度默认 3072 bit，最低接受 2048 bit。
- padding 固定为 OAEP，hash 固定为 SHA-256；禁止 PKCS#1 v1.5 加密 padding。
- 私钥默认由 Windows CNG Key Storage Provider 持久化并标记为不可导出。
- 公钥导出为版本化 `.szxpub` 文件，payload 固定为 DER SubjectPublicKeyInfo，并包含算法、位数和 SHA-256 指纹，不包含私钥；Windows 使用 Crypt32/CNG 编解码，预留 Linux 直接解析能力。
- 加密只需要公钥文件；解密使用本机 CNG key name 或 Windows 证书/密钥存储中的私钥。
- 公钥指纹用于选择密钥和提示用户，不替代 GCM/RSA 的密码认证。
- P0 单文件只支持一个接收方；多接收方 wrapped key 列表放入 P1。

Windows CNG 原生提供对称、非对称、签名、密钥派生和持久化密钥接口，设计参考 [Microsoft CNG 概览](https://learn.microsoft.com/en-us/windows/win32/seccng/cng-portal)和 [CNG 典型编程流程](https://learn.microsoft.com/en-us/windows/win32/seccng/typical-cng-programming)。

## 7. SZX 文件格式 v1

所有多字节整数固定使用 little-endian；读取端必须检查长度和上限后再分配内存。

### 7.1 Header

| 字段 | 类型/长度 | 说明 |
|---|---|---|
| magic | 4 bytes | `SZXE` |
| version | u16 | `1` |
| header_size | u16 | header 总长度 |
| algorithm_id | u16 | AES-256-GCM |
| protection_mode | u16 | symmetric-key / password / rsa-envelope |
| kdf_id | u16 | none / PBKDF2-SHA256 |
| key_wrap_id | u16 | none / RSA-OAEP-SHA256 |
| flags | u32 | 保留位必须为 0 |
| chunk_size | u32 | 明文块大小 |
| plaintext_size | u64 | 原文件字节数 |
| chunk_count | u64 | 分块数量 |
| salt_size | u16 | raw-key 为 0 |
| nonce_prefix_size | u16 | v1 固定长度 |
| kdf_iterations | u32 | raw-key 为 0 |
| salt | variable | 随机 salt |
| nonce_prefix | variable | 每文件随机 nonce 前缀 |
| recipient_key_id_size | u16 | 对称模式为 0 |
| recipient_key_id | variable | RSA 公钥 SHA-256 指纹 |
| wrapped_key_size | u32 | 对称模式为 0 |
| wrapped_key | variable | RSA-OAEP 包装的 256-bit DEK |
| metadata_size | u32 | 可选元数据长度 |
| metadata | variable | UTF-8 JSON，受认证但不加密 |

元数据默认只包含原扩展名、创建工具版本和时间；原绝对路径、用户名和机器名默认不写入，避免泄露环境信息。

### 7.2 Chunk

| 字段 | 类型/长度 | 说明 |
|---|---|---|
| chunk_index | u64 | 从 0 单调递增 |
| plaintext_length | u32 | 本块明文长度 |
| ciphertext | variable | 等长密文 |
| auth_tag | 16 bytes | GCM tag |

nonce 由随机文件前缀和 chunk index 组合，任何情况下禁止同一 key 下复用 nonce。最后一块通过 AAD final 标记和 header 中的总长度/块数共同认证。

### 7.3 解析约束

- 拒绝未知主版本、未知算法、未知保护模式、未知 KDF 和未知 key wrap。
- RSA envelope 模式必须同时包含合法 recipient key ID 和 wrapped key；对称模式必须不含二者。
- 拒绝 header/chunk 长度溢出、块数不一致和超出配置上限。
- 拒绝索引不连续、重复、乱序、截断或多余尾部字节。
- 任一 tag 失败即终止，删除临时输出，不返回部分明文文件。
- `info` 只能读取非敏感 header，不验证密钥正确性；`verify` 完整认证全部块但不生成输出文件。

## 8. 基础加密库 API

`szx::crypto` 公共 API 使用标准 C++20 字节类型和 `SZX::COMMON::Result<T>`，不接受文件路径，不执行文件 I/O，不解析 `.szxe/.szxlic`，也不向调用方暴露 CNG、Mbed TLS 或其他 provider handle。

```cpp
namespace SZX::CRYPTO
{

struct SecretKey
{
    std::vector<std::uint8_t> bytes;
};

struct AesGcmEncryptRequest
{
    std::span<const std::uint8_t> plaintext;
    std::span<const std::uint8_t> key;
    std::span<const std::uint8_t> nonce;
    std::span<const std::uint8_t> associatedData;
};

struct AesGcmCiphertext
{
    std::vector<std::uint8_t> ciphertext;
    std::array<std::uint8_t, 16> tag;
};

struct RsaPublicKey
{
    std::vector<std::uint8_t> subjectPublicKeyInfoDer;
    std::array<std::uint8_t, 32> keyId;
};

struct RsaPrivateKey
{
    std::vector<std::uint8_t> pkcs8Der;
};

Result<SecretKey> generateKey();
Result<std::vector<std::uint8_t>> randomBytes(std::size_t size);
Result<std::array<std::uint8_t, 32>> sha256(std::span<const std::uint8_t> input);
Result<std::array<std::uint8_t, 32>> hmacSha256(std::span<const std::uint8_t> key,
                                                std::span<const std::uint8_t> input);
Result<SecretKey> derivePbkdf2Sha256(const PasswordKdfRequest &);
Result<AesGcmCiphertext> encryptAes256Gcm(const AesGcmEncryptRequest &);
Result<std::vector<std::uint8_t>> decryptAes256Gcm(const AesGcmDecryptRequest &);
Result<std::vector<std::uint8_t>> encryptRsaOaepSha256(const RsaOaepEncryptRequest &);
Result<std::vector<std::uint8_t>> decryptRsaOaepSha256(const RsaOaepDecryptRequest &);
Result<std::vector<std::uint8_t>> signRsaPssSha256(const RsaPssSignRequest &);
Result<bool> verifyRsaPssSha256(const RsaPssVerifyRequest &);
Result<RsaKeyPairInfo> generateRsaKeyPair(const RsaKeyGenerationRequest &);

} // namespace SZX::CRYPTO
```

### 8.1 API 规则

- 对称 key、password、RSA public key 和导入型 RSA private key 使用不同类型/请求字段，避免调用方混用。
- API 只接收 byte span/owned byte vector 和算法参数；路径、扩展名、JSON 和产品标识不得进入基础库。
- 基础函数单次处理一个内存块；分块循环、进度、取消和原子文件由 `szx::crypto_file` 负责。
- `decryptAes256Gcm` 认证失败时返回失败和空明文。
- RSA-OAEP 输入超过密钥/算法允许上限时立即拒绝，基础库不替调用方拆分 RSA 明文。
- 密钥容器析构时尽力清零内存；禁止复制，允许移动。
- 错误码稳定，错误文本不包含 secret 或明文内容。
- 不可导出的持久化私钥不经过 `RsaPrivateKey`；由 `szx::crypto_keystore` 以稳定 key reference 执行 decrypt/sign，并复用相同算法契约。

### 8.2 兼容 façade

现有 `encryptFernet/decryptFernet` 暂时保留在 `szx::crypto`，作为由 AES-CBC、HMAC、Base64 和随机数组合而成的兼容 façade。除 Fernet 兼容外，不再向基础库增加新的业务容器格式。

### 8.3 文件层 API

`szx::crypto_file` 才提供 `encryptFile/decryptFile/verifyFile/inspectFile`、`.szxe` 解析、分块、进度、取消和原子写入。它可以使用 `std::filesystem::path`，但这些类型不得反向进入 `CryptoService` 或 `szx::crypto`。

### 8.4 基础加密服务 API

`szx::crypto_service` 对所有上层业务提供稳定、与平台无关的 `ICryptoService`；默认实现 `CryptoService` 组合 `szx::crypto` 和 `szx::crypto_keystore`。其职责包括：

- 对称加解密、非对称加解密、签名验签、Hash/HMAC、KDF、安全随机数和密钥生成。
- 公钥解析、key ID 计算，以及通过不透明 `KeyReference` 使用持久化私钥。
- 统一参数校验、敏感数据约束、错误码映射和后端能力查询。
- 根据构建平台装配 Windows CNG 或 Linux provider，但不向上层暴露 provider 类型。

服务不处理文件路径、`.szxe/.szxlic`、许可证策略、进度、取消、GUI 或 CLI。接口必须可注入，便于上层单元测试使用受控 fake；生产代码不得提供“跳过认证”“忽略验签”或不安全算法开关。

```cpp
class ICryptoService
{
public:
    virtual ~ICryptoService() = default;
    virtual CryptoCapabilities capabilities() const = 0;
    virtual Result<AesGcmCiphertext> encrypt(const AesGcmEncryptRequest &) = 0;
    virtual Result<SecretBytes> decrypt(const AesGcmDecryptRequest &) = 0;
    virtual Result<ByteVector> wrapKey(const RsaOaepEncryptRequest &) = 0;
    virtual Result<SecretBytes> unwrapKey(const RsaOaepDecryptRequest &) = 0;
    virtual Result<ByteVector> sign(const RsaPssSignRequest &) = 0;
    virtual Result<bool> verify(const RsaPssVerifyRequest &) = 0;
};
```

该接口示意能力边界，最终头文件按仓库命名规范拆分；业务模块持有 `ICryptoService&` 或受控 shared ownership，不自行构造平台 provider。

能力边界固定如下：

| 能力组 | P0 操作 | 主要调用方 |
|---|---|---|
| 密钥管理 | 生成 AES-256 对称密钥；生成 RSA-3072 密钥对；导入/导出公钥；创建或引用受保护私钥；查询 key ID、用途和算法信息 | 文件加密、软授权、维护工具 |
| 对称加密 | AES-256-GCM 加密、解密与认证校验；PBKDF2-HMAC-SHA256 派生密钥 | 文件容器及其他业务 |
| 非对称加密 | RSA-OAEP-SHA256 加密/解密；包装/解包 AES 数据密钥 | 文件容器及密钥交换业务 |
| 数字签名 | RSA-PSS-SHA256 签名与验签 | 内部授权签发端、客户授权验证端 |
| 信息查询 | 查询算法能力、密钥公开信息、key ID 和后端健康状态；不得返回私钥材料 | 所有上层业务、诊断工具 |
| 数据校验 | AEAD tag 校验、签名校验、Hash/HMAC 和输入参数/编码校验 | 文件、授权及其他业务 |

“信息查询”和“校验”必须语义分离：查询只解析和展示非敏感元数据；校验必须执行认证或验签并返回明确结论，不能因文件可解析就判定为有效。

## 9. 应用服务

`CryptoApplicationService` 负责 GUI/CLI 共用的非密码逻辑：

- 输入、输出和覆盖策略校验。
- 根据扩展名/显式参数选择格式。
- 临时输出路径和原子提交。
- 进度节流、取消和状态转换。
- 输入输出不能是同一文件。
- 批处理时单文件隔离，不跨文件复用 nonce/salt。

状态机：

```text
Idle -> Validating -> Running -> Verifying -> Committing -> Completed
                    ├──────────────> Cancelled
                    └──────────────> Failed
```

失败、取消和认证错误均不得进入 `Committing`。输出已存在且未允许覆盖时在 `Validating` 阶段失败。

## 10. CLI 设计

目标名建议：`szx_crypto_cli`；安装命令名建议：`szx-crypto`。

### 10.1 命令

```text
szx-crypto keygen symmetric [--output key.txt]

szx-crypto keygen rsa --name deployment-key [--bits 3072] \
    [--public-out deployment-key.szxpub]

szx-crypto key list
szx-crypto key public-info --input deployment-key.szxpub [--json]

szx-crypto encrypt --input model.engine --output model.engine.szxe \
    (--key-file key.txt | --password-stdin | --recipient deployment-key.szxpub) \
    [--format szxe|fernet]

szx-crypto decrypt --input model.engine.szxe --output model.engine \
    (--key-file key.txt | --password-stdin | --private-key deployment-key)

szx-crypto verify --input model.engine.szxe \
    (--key-file key.txt | --password-stdin | --private-key deployment-key)

szx-crypto info --input model.engine.szxe [--json]
```

### 10.2 CLI 安全规则

- 不提供 `--password <text>`，避免口令进入命令历史和进程列表。
- `--password-stdin` 从标准输入读取一行；交互终端优先无回显读取。
- `--key-file` 检查文件大小、格式和读取错误；不打印 key。
- RSA 私钥只按 CNG key name/证书指纹引用，不允许通过命令行传入裸私钥。
- `keygen rsa` 默认创建不可导出的持久化私钥；覆盖同名 key 必须显式确认。
- `--force` 才允许覆盖，且仍使用临时文件原子替换。
- stdout 用于成功输出或 `--json` 机器结果，stderr 用于诊断。
- 进度只在交互终端显示；`--quiet` 禁止进度。

### 10.3 退出码

| 退出码 | 含义 |
|---:|---|
| 0 | 成功 |
| 2 | 参数错误 |
| 3 | 输入/输出 I/O 错误 |
| 4 | key/password 错误或认证失败 |
| 5 | 不支持的格式/版本 |
| 6 | 取消 |
| 7 | 内部 provider 错误 |

脚本不得依赖本地化错误文本，只依赖退出码和可选 JSON `error_code`。

### 12.1 Linux 无 OpenSSL 迁移方案

Linux 迁移必须保持 `ICryptoService` 公共 API、错误码和 `.szxe` v1 文件格式不变，只替换服务层以下的 provider 与 keystore 实现。不得在公共头中出现 CNG、Mbed TLS 或其他后端类型，上层业务无需重新编译业务逻辑或增加条件分支。

推荐优先级：

| 方案 | 定位 | 结论 |
|---|---|---|
| Mbed TLS / PSA Crypto | Linux 默认 provider | 推荐；覆盖 AES-GCM、RSA、OAEP、SHA、RNG 和密钥解析，不依赖 OpenSSL |
| Botan | 备选用户态 provider | 能力完整、C++ API 友好，但体积和依赖管理成本更高 |
| Linux AF_ALG/libkcapi | 不采用 | 最新 Linux 内核文档已将 AF_ALG 标为不安全且弃用，不作为新实现基础 |

Mbed TLS 路线：

- 固定一个经过验证的 LTS/稳定 tag，通过仓库依赖管理统一拉取或 vendor，禁止系统库与内置库混用。
- 静态链接到 Linux 的 `szx_crypto`，使用 `PRIVATE` 依赖和 hidden symbol visibility，不向其他模块传播 include、编译宏或符号。
- 只启用 PSA Crypto/AES-GCM、RSA-OAEP、SHA-256、PBKDF2、熵源、密钥解析所需组件；关闭 TLS、DTLS、网络协议和不使用的算法。
- Linux 随机数使用 Mbed TLS/PSA 对接的系统 entropy source；任何熵源失败均 fail closed。
- Linux 私钥默认保存在权限为 `0600` 的受控目录，并以口令保护的私钥容器或后续 PKCS#11/TPM provider 管理；不得照搬 Windows CNG key name 作为持久化格式。
- `.szxpub` 使用平台无关的 DER SubjectPublicKeyInfo payload，不能直接写 Windows 专属 `BCRYPT_RSAPUBLIC_BLOB`。
- Windows 与 Linux 必须执行双向互操作测试：Windows 加密/Linux 解密、Linux 加密/Windows 解密，以及公钥 envelope 双向测试。

Mbed TLS 官方资料表明其提供 AES-GCM 和 RSA 能力，RSA 加密也存在明文长度上限，因此 Linux 仍使用 RSA 只包装 32 字节 DEK 的混合加密模式，不改变文件设计。[Mbed TLS 项目](https://github.com/Mbed-TLS/mbedtls)、[加解密模块文档](https://mbed-tls.readthedocs.io/projects/api/en/development/api/group/group__encdec__module/)。

Linux 内核的 AF_ALG 虽能暴露 AEAD、hash 和 RNG，但最新官方文档明确建议迁移到用户态密码实现并禁用该接口，因此不列入支持路线。[Linux Kernel AF_ALG 文档](https://docs.kernel.org/crypto/userspace-if.html)。

## 13. 软授权方案

### 13.1 目标与信任边界

软授权用于控制 CryptoTool、CLI 及可复用库的可用功能、有效期和授权机器。采用离线优先的签名许可证：

```text
客户机器生成授权请求 .szxreq
  -> 内部签发端审核
  -> 签发端使用独立 RSA-PSS-SHA256 私钥签名
  -> 生成许可证 .szxlic
  -> 客户端使用内置签发公钥验签
  -> 校验产品、机器、期限、功能和版本范围
  -> 发布 FeatureGate 快照
```

信任边界：

- 签发私钥只存在于内部签发环境，默认由 Windows CNG 持久化为不可导出密钥。
- 客户侧仅包含一个或多个签发公钥和 key ID，绝不包含签发私钥。
- 文件加密 RSA key 与许可证签名 key 必须分离，禁止复用同一密钥对。
- 客户端验签公钥可以公开；授权安全性依赖私钥保密和客户端完整性，而不是隐藏公钥。
- 软授权不能完全阻止管理员级二进制 patch、内存修改或系统时间伪造；目标是可靠授权管理和提高绕过成本。

### 13.2 授权类型

| 类型 | 语义 |
|---|---|
| Trial | 固定短期、不可续写本地起始时间；必须由签名许可证定义 |
| Term | 起止时间内有效 |
| Perpetual | 无到期日，但仍受产品、版本和机器约束 |
| Maintenance | 永久运行已授权版本，仅限制可升级到的版本/发布日期 |

P0 支持 Trial、Term、Perpetual；Maintenance 和浮动授权为 P1。

### 13.3 功能授权

许可证以稳定 feature code 控制能力，不依赖 UI 文本：

| Feature code | 功能 |
|---|---|
| `crypto.symmetric` | 对称文件加解密 |
| `crypto.asymmetric` | 非对称 envelope 加解密 |
| `crypto.fernet` | Fernet 兼容模式 |
| `crypto.key_management` | RSA/对称密钥管理 |
| `crypto.batch` | 批量任务（P1） |
| `crypto.cli` | CLI 自动化能力 |

FeatureGate 在启动/安装许可证后生成不可变快照。GUI 隐藏或禁用未授权入口只是展示层，Controller、CLI 和库服务必须再次检查授权。

### 13.4 机器指纹

机器绑定采用“多因子哈希 + 容错匹配”，不直接保存可识别硬件序列号：

- Windows SMBIOS system UUID。
- 系统卷标识。
- Windows MachineGuid。
- 可选 TPM 公钥/设备标识（P1）。

每个原始因子先规范化，再使用产品域分离字符串和 SHA-256 计算 factor hash。授权请求只携带 factor type 和 hash，不携带原始序列号。

默认匹配策略建议：三个基础因子中至少两个匹配。主板更换、系统盘更换、克隆镜像和虚拟机迁移必须形成明确的重新授权流程，不能通过自动放宽匹配静默继续授权。

### 13.5 授权请求格式 `.szxreq`

请求不是许可证，不提供任何授权。建议内容：

```json
{
  "schema_version": 1,
  "request_id": "UUIDv7",
  "product_id": "szx.crypto-tool",
  "app_version": "0.1.0",
  "machine_factors": [
    {"type": "smbios_uuid", "hash": "..."},
    {"type": "system_volume", "hash": "..."},
    {"type": "machine_guid", "hash": "..."}
  ],
  "requested_features": ["crypto.symmetric", "crypto.asymmetric"],
  "created_at": "UTC timestamp",
  "nonce": "random base64"
}
```

请求文件不含私钥、口令或用户文件信息。请求 ID 和 nonce 用于签发审计与防止操作人员混淆，不把请求本身视为可信输入。

### 13.6 许可证格式 `.szxlic`

许可证采用版本化二进制 envelope，签名覆盖 header 和 payload 原始字节：

| 字段 | 说明 |
|---|---|
| magic | `SZXL` |
| version | `1` |
| signature_algorithm | RSA-PSS-SHA256 |
| issuer_key_id | 签发公钥 SHA-256 指纹 |
| payload_size | payload 长度 |
| payload | 规范 UTF-8 JSON |
| signature_size | 签名长度 |
| signature | 对 header + payload 的签名 |

payload 至少包含：

- `license_id`、`product_id`、客户/项目标识。
- 授权类型、签发时间、开始时间、到期时间。
- features 列表。
- 最低/最高应用版本或最大维护日期。
- machine factor hashes 和最少匹配数量。
- issuer、备注和序列号。

解析顺序固定为长度/上限校验、定位 issuer key、验签、解析 JSON、校验产品/机器/时间/版本/功能。未经签名验证的 payload 不得用于功能决策。

### 13.7 签名算法与密钥轮换

- P0 使用 RSA-PSS-SHA256，签发 key 默认 3072 bit。
- 签名 key 与 RSA-OAEP 加密 key 使用不同 key usage 和 key ID。
- 客户端支持内置多个 issuer public key，用于平滑轮换。
- 每个公钥带 `not_before/not_after` 的信任配置；旧许可证可在策略允许期内继续验证。
- 私钥泄露时通过软件更新移除受信 key；完全离线客户端无法实时获得吊销信息，这是已知限制。
- P1 增加签名吊销列表或在线状态检查，但失败策略必须显式定义，不能默认“网络失败即永久不可用”。

### 13.8 时间校验与回拨防护

- 所有许可证时间使用 UTC。
- 客户端保存 `last_seen_utc` 和最近许可证状态，Windows 使用 DPAPI 保护并绑定当前用户或机器。
- 当前时间明显早于受保护的 `last_seen_utc` 时进入 `ClockRollbackSuspected`，不静默通过。
- 默认允许小范围时钟漂移；具体容差作为发布配置冻结。
- 离线软件无法绝对防止系统快照回滚。高价值授权建议 P1 使用在线时间票据、TPM 单调计数或短期续租许可证。

### 13.9 许可证存储和选择

- Windows 默认存储到受 ACL 保护的 ProgramData 产品目录；用户导入文件先复制到受控目录，再原子替换。
- 安装前完整验签和校验；失败许可证不覆盖当前有效许可证。
- 多许可证存在时按 product、版本和 feature 选择，不简单采用“到期最晚”策略；冲突必须可诊断。
- 许可证文件本身无需加密，因为签名提供完整性且授权内容不是 secret；客户敏感字段应最小化或用匿名 customer ID。

### 13.10 客户侧 API

内部发行端 API 独立放在 `license-issuer`，不导出到客户侧库：

```cpp
Result<IssuerKeyInfo> generateIssuerKeyPair(const IssuerKeyGenerationRequest &);
Result<IssuedLicense> issueLicense(const LicenseIssueRequest &);
Result<LicenseInfo> inspectLicenseRequest(const LicenseRequestBytes &);
Result<LicenseVerificationReport> validateIssuedLicense(const IssuedLicenseBytes &);
```

签发流程必须先校验请求格式、产品、机器指纹摘要、功能代码、期限和 operator 权限，再通过 `ICryptoService::sign` 使用不可导出的发行私钥签名。签发后立即以对应公钥自验，只有验签和字段复核全部通过才允许输出 `.szxlic`。查询接口只返回非敏感请求/许可证信息；`validateIssuedLicense` 返回签名、格式、时间和策略的分项校验报告。

### 13.11 CLI 与 GUI

客户侧 CLI：

```text
szx-crypto license request --output machine.szxreq [--json]
szx-crypto license install --input customer.szxlic
szx-crypto license status [--json]
szx-crypto license inspect --input customer.szxlic [--json]
szx-crypto license verify --input customer.szxlic [--json]
```

内部签发 CLI 独立为 `szx-license-issuer`：

```text
szx-license-issuer issue --request machine.szxreq \
    --type term --expires 2027-08-04 \
    --feature crypto.symmetric --feature crypto.asymmetric \
    --output customer.szxlic
szx-license-issuer inspect --input customer.szxlic [--json]
szx-license-issuer verify --input customer.szxlic [--json]
```

内部工具不加入客户安装包，不与 `szx-crypto` 共用“隐藏命令”。签发操作记录 operator、request ID、license ID、features、期限、issuer key ID 和时间，但不记录私钥材料。

GUI 增加“授权”页面，展示授权状态、许可证 ID、到期日、已授权功能、机器请求码和导入按钮。授权失效时允许进入授权页面和查看非敏感信息，但加解密操作由服务层拒绝。

### 13.12 Linux 迁移

- `.szxreq`、`.szxlic`、feature code、issuer key ID 和签名 payload 保持平台一致。
- Linux 使用同一 DER SubjectPublicKeyInfo issuer 公钥和 RSA-PSS-SHA256 验签。
- 机器因子替换为 `/etc/machine-id` hash、SMBIOS UUID、系统卷/文件系统 UUID 和可选 TPM2 标识；仍采用多因子容错匹配。
- `last_seen_utc` 状态使用权限 `0600` 的受控文件，并通过机器密钥、系统 keyring 或 TPM2 保护；不能照搬 DPAPI。
- Linux Mbed TLS provider 只负责验签，不包含签发私钥。

### 13.13 软授权测试

- 正确签名、错误签名、未知 issuer、payload 单字节篡改和尾部追加。
- product、版本、起止时间、feature 和 machine threshold 边界。
- 三个机器因子分别变化一个、变化两个和全部变化。
- Trial、Term、Perpetual 状态矩阵。
- 时间等于开始/到期边界、允许漂移和明显回拨。
- 旧许可证有效时安装无效新许可证，不得覆盖。
- GUI 隐藏/禁用后直接调用 Controller/CLI/Service 仍被拒绝。
- 签发工具和客户安装包依赖扫描，确认客户侧不含 issuer 私钥和签发命令。
- Windows/Linux 使用同一许可证双向验签。

## 15. 安全设计

1. Windows 只使用 CNG/NCrypt/Crypt32；Linux 目标使用固定版本的 Mbed TLS/PSA Crypto，不实现密码原语，也不依赖 OpenSSL。
2. 文件默认使用 AEAD；不提供未认证加密。
3. 随机数必须来自系统 CSPRNG，失败即终止。
4. 同一 key 下 nonce 必须唯一；每文件随机前缀，每块计数器。
5. header 和 chunk 元数据进入 AAD，防止算法、大小、顺序和截断被篡改。
6. 解密写临时文件，所有 tag 验证完成后才原子提交。
7. key/password 不进入 QString 属性、日志、剪贴板历史或持久配置；复制密钥需显式动作并提示风险。
8. 输入文件可以是符号链接，但输出目标必须经过规范化和覆盖校验；不得写出指定目录边界之外的隐式路径。
9. 解析不可信文件时限制 header、metadata、chunk size 和 chunk count，防止整数溢出及内存/磁盘耗尽。
10. 不承诺内存清零能抵御进程转储或管理员级取证；P1 可增加进程转储策略和 OS 密钥保护。
11. 许可证签发私钥与文件加密私钥物理/逻辑分离，客户侧永远只部署验签公钥。
12. FeatureGate 必须在服务层执行，不能仅依赖 QML 可见性或 CLI 参数检查。

## 19. 验收标准

- `crypto_file`、`license` 及其他上层业务只依赖 `szx::crypto_service`，不直接链接基础算法库、keystore 或平台 provider。
- Windows 与 Linux 实现通过同一套 `ICryptoService` 契约测试，上层业务 API 和行为一致。
- 库、GUI 和 CLI 对同一输入、格式和凭据结果一致。
- Fernet 与 Python 现有格式互操作不回归。
- SZX 文件对密文、header、tag、顺序和截断篡改全部拒绝。
- 对称 key/password 和 RSA envelope 三种保护模式均可 round-trip；错误私钥不能解密。
- 错 key/password 不产生可提交明文文件。
- 1 GiB 文件加解密峰值内存保持在 chunk 级，不随文件大小线性增长。
- GUI 加解密期间保持响应，可取消且无残留正式输出。
- CLI 退出码、JSON 输出和非交互行为可用于脚本。
- 密钥和口令不进入日志、命令行参数和持久配置。
- 未授权覆盖和源文件删除均不会发生。
- 无许可证、许可证过期、机器不匹配或 feature 缺失时，GUI、CLI 和服务层行为一致并拒绝受控操作。
- 客户安装包不包含签发私钥、签发代码入口或内部 issuer 工具。
- 正确许可证在允许的单硬件变化下继续有效，超过匹配阈值后明确要求重新授权。
- Windows 与 Linux provider 对同一 `.szxlic` 验签结论一致。

## 20. 待确认决策

1. 第一版是否只支持 Windows，还是必须同步支持 Linux。
2. GUI 使用独立 `CryptoTool` 应用，还是集成进现有 PCBDetect 维护页面；本方案默认独立应用。
3. P0 是否必须支持口令模式；若工具只供模型发布链路使用，可先只支持随机 key。
4. 目标最大文件大小和目标机器配置，用于冻结 chunk size、KDF 时间和性能门槛。
5. 密钥由人工管理、部署系统注入，还是需要 DPAPI/凭据管理器。
6. `.szxe` 是否需要保存原文件名；本方案默认只保存扩展名，减少元数据泄露。
7. Linux 私钥存储首选口令保护的 PKCS#8 文件、PKCS#11 还是 TPM2；公钥格式已固定为 DER SubjectPublicKeyInfo。
8. 软授权保护的是 CryptoTool 自身，还是作为通用库同时授权 PCBDetect；本方案按通用 `product_id + feature code` 设计。
9. 默认许可证类型、试用天数、时钟漂移容差和机器因子最少匹配数。
10. 是否需要 P1 在线激活/吊销服务，以及网络不可用时采用 fail-open、宽限期还是 fail-closed。
