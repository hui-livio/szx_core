# szx::network 网络库设计与开发计划

## 1. 目标与边界

为 `szx_core` 增加统一网络组件 `szx::network`，向应用仓库提供一致的 TCP/UDP/HTTP 客户端与服务端行为，后端实现使用 [third_party/libhv](../../third_party/libhv/)（v1.3.4，见[第三方库评审](../RBAC/07-C++三方库评审.md)）。

### 1.1 做的事

- 统一连接生命周期、收发回调、超时、重连和优雅停止语义；
- 统一错误模型：全部返回 `SZX::COMMON::Result<T>`，不抛异常穿越回调边界；
- 统一线程模型：事件循环线程数、回调线程约束和阻塞任务的外移方式；
- 把 libhv 完全封在实现内部，公共头文件不出现任何 `hv/` 类型。

### 1.2 不做的事

- 不做业务协议（登录、鉴权、RBAC 契约）。HTTP 服务端只提供路由和中间件挂点，认证仍属应用层，见[三方库评审 3.1 节](../RBAC/07-C++三方库评审.md)；
- 不做服务注册发现、负载均衡、消息队列客户端；
- 不做 TLS 证书管理与轮换，只透传证书路径与开关；
- 第一版不做 MQTT 与 KCP（libhv 对应选项保持 OFF）。

### 1.3 硬约束（来自现有评审结论）

[07-C++三方库评审.md:17](../RBAC/07-C++三方库评审.md) 已确定：不把 libhv 加入其他 `szx` 组件的 PUBLIC 依赖。本组件是该结论的唯一例外载体，方式是 libhv 仅作为 `PRIVATE` 依赖并通过 PIMPL 隐藏，因此消费方链接 `szx::network` 时不会看到 libhv 头文件与符号。

## 4. 错误模型

沿用 `SZX::COMMON::Result<T>`（[components/common/Result.hpp](../../components/common/Result.hpp)），错误码用组件内枚举，从 `1` 开始，与 `ZipError` 风格一致：

```cpp
enum class NetworkError : int
{
    InvalidArgument = 1,
    NotInitialized,     // 未 start / 已 stop
    AlreadyRunning,
    ResolveFailed,      // DNS 解析失败
    ConnectFailed,
    ConnectTimeout,
    BindFailed,         // 端口占用或权限不足
    Closed,             // 对端关闭或本地关闭后再操作
    SendFailed,
    SendQueueFull,      // 背压：发送队列超过上限
    ReadTimeout,
    MessageTooLarge,    // 超过帧长/请求体上限
    ProtocolError,      // 分帧或 HTTP 解析失败
    RouteConflict,      // 重复注册同一 method+path
    TlsUnavailable,     // 未启用 TLS 构建
    TlsHandshakeFailed,
    Cancelled,
    Internal
};
```

约定：

- 所有可能失败的公共方法标注 `[[nodiscard]]` 并返回 `Result`；
- `Result::error` 存 `static_cast<int>(NetworkError)`，`message` 带上端点或路径等定位信息，不带凭据、Cookie、Authorization 头和请求体；
- 回调内部禁止异常逃逸：实现层在每个 libhv 回调边界 `catch (...)` 并转成 `onError`，这条与[三方库评审 3.1 节](../RBAC/07-C++三方库评审.md)对线程模型的要求一致。

## 5. 公共 API 设计

### 5.1 基础类型（NetworkTypes.h）

```cpp
struct Endpoint final
{
    std::string host;          // IPv4/IPv6/域名
    std::uint16_t port = 0;
};

struct TlsOptions final
{
    bool enabled = false;
    std::string certFile;      // 服务端证书
    std::string keyFile;
    std::string caFile;        // 客户端校验用
    bool verifyPeer = true;
};

struct ReconnectPolicy final
{
    bool enabled                 = false;
    std::uint32_t minDelayMs     = 1000;
    std::uint32_t maxDelayMs     = 30000;
    std::uint32_t delayPolicyExp = 2;   // 指数退避基数
    std::uint32_t maxRetries     = 0;   // 0 = 不限
};

enum class FrameMode : std::uint8_t
{
    None,          // 原始字节流，由上层自行分帧
    Delimiter,     // 分隔符，如 "\r\n"
    FixedLength,
    LengthField    // 头部长度字段
};

struct FramePolicy final
{
    FrameMode mode              = FrameMode::None;
    std::string delimiter;
    std::uint32_t fixedLength   = 0;
    std::uint32_t lengthOffset  = 0;
    std::uint32_t lengthBytes   = 4;
    bool lengthIncludesHeader   = false;
    std::uint32_t maxFrameSize  = 8u * 1024u * 1024u;   // 硬上限，防止恶意长度字段
};
```

`FramePolicy` 直接映射 libhv 的 `unpack_setting_t`，把三种常见分帧从应用层收进组件，这是本次封装最能减少重复代码的部分。`maxFrameSize` 必须有默认上限，否则 `LengthField` 模式下一个伪造的长度字段就能触发超大分配。

### 5.2 EventLoopGroup

设计思路：libhv 的 `EventLoopThreadPool` 决定回调在哪个线程执行。默认情况下每个客户端/服务端自带循环即可；当一个进程里同时有 TCP 服务、UDP 采集和 HTTP 服务时，共享一组循环能避免线程数膨胀。因此把事件循环做成可选的显式对象：不传就各自私有，传了就共享。

常用 API：

```cpp
class SZX_NETWORK_API EventLoopGroup final
{
public:
    static auto Create(std::size_t threadCount = 1) -> SZX::COMMON::Result<std::shared_ptr<EventLoopGroup>>;

    [[nodiscard]] auto threadCount() const noexcept -> std::size_t;
    [[nodiscard]] auto running() const noexcept -> bool;
    auto stop(bool waitForFinish = true) -> SZX::COMMON::Result<void>;   // 幂等
};
```

`stop()` 语义：向所有循环线程投递退出请求；`waitForFinish = true` 时阻塞直到线程 `join`，返回后不再有回调触发。`shared_ptr` 是否唯一引用不影响 `stop()`——调用后循环已停，即便别处仍持有 `shared_ptr`，其上的客户端/服务端也会因“循环已停”而拒绝新操作。析构自动 `stop(true)`。禁止在回调线程内调用 `stop(true)`，实现层检测到会返回 `NetworkError::Internal`（否则自等死锁）。

### 5.3 TCP

设计思路：连接对象以 `std::shared_ptr<TcpConnection>` 暴露，回调里拿到的连接可以安全持有到下一次事件；客户端与服务端共用同一个连接类型，使上层收发代码可复用。`send` 线程安全（内部投递到所属事件循环），其余状态变更方法只保证在事件循环线程或调用线程串行使用。分帧交给 `FramePolicy`，`onMessage` 拿到的就是完整一帧。

连接需要携带上层状态（会话 ID、登录用户、设备编号）时，如果组件不提供挂载点，每个使用方都得自己维护一张 `map<connectionId, Session>` 并为它加锁。因此给 `TcpConnection` 一个类型擦除的上下文槽，生命周期跟随连接，省掉这张表。

`TcpConnection` 常用 API：

```cpp
class SZX_NETWORK_API TcpConnection final
{
public:
    [[nodiscard]] auto id() const noexcept -> std::uint64_t;
    [[nodiscard]] auto remote() const -> Endpoint;
    [[nodiscard]] auto local() const -> Endpoint;
    [[nodiscard]] auto connected() const noexcept -> bool;

    auto send(std::span<const std::uint8_t> data) -> SZX::COMMON::Result<void>;
    auto send(std::string_view text) -> SZX::COMMON::Result<void>;
    auto close() -> SZX::COMMON::Result<void>;

    [[nodiscard]] auto pendingBytes() const noexcept -> std::size_t;   // 背压观测

    // 上层状态挂载：仅在该连接自己的回调线程内访问，随连接销毁而释放
    void setContext(std::shared_ptr<void> context);
    [[nodiscard]] auto context() const -> std::shared_ptr<void>;
};
```

**`send()` 的语义必须在头注释里写明**：`Result::ok == true` 表示「已成功写入发送队列」，**不表示对端已收到**，也不表示已进入内核缓冲区。它是非阻塞的，不会等待网络。返回失败只有三种情况：连接已关闭（`Closed`）、队列积压超过 `maxSendQueueBytes`（`SendQueueFull`）、单帧超过 `maxFrameSize`（`MessageTooLarge`）。需要确认对端收到就得靠应用层回执，组件不提供送达保证。`SendQueueFull` 时上层应择一处理：丢弃、断开该连接、或暂停生产（用 `pendingBytes()` 观测水位），组件不会替使用方阻塞等待。

`TcpClient` 常用 API：

```cpp
struct TcpClientOptions final
{
    Endpoint server;
    std::uint32_t connectTimeoutMs = 5000;
    FramePolicy frame;
    ReconnectPolicy reconnect;
    TlsOptions tls;
    std::size_t maxSendQueueBytes = 16u * 1024u * 1024u;
    std::shared_ptr<EventLoopGroup> loops;   // 可空
};

using ConnectionCallback = std::function<void(const std::shared_ptr<TcpConnection> &)>;
using MessageCallback    = std::function<void(const std::shared_ptr<TcpConnection> &, std::span<const std::uint8_t>)>;
using ErrorCallback      = std::function<void(NetworkError, const std::string &)>;

// 断开原因：上层区分「正常收尾」与「异常掉线」的依据，决定要不要重连或告警
enum class DisconnectReason : std::uint8_t
{
    LocalClose,      // 本地调用 close() / disconnect() / stop()
    PeerClose,       // 收到对端 FIN
    ReadError,       // 读失败（含 RST）
    WriteError,      // 写失败
    FrameError,      // 分帧失败或超过 maxFrameSize，组件主动关闭
    SendQueueFull,   // 积压超限，组件主动关闭
    Timeout,         // 读空闲超时
    TlsError
};

using DisconnectCallback = std::function<void(const std::shared_ptr<TcpConnection> &, DisconnectReason, const std::string &)>;
```

`onDisconnected` 用 `DisconnectCallback` 而非 `ConnectionCallback`：只有 `LocalClose` 和 `PeerClose` 属于正常收尾，其余都该记日志或告警。缺了这个参数，上层只能靠“最近有没有调过 `disconnect()`”猜原因，在并发下不可靠。回调进入时连接已不可发送，`send()` 会返回 `Closed`；连接对象本身仍可安全读取 `id()` / `remote()` / `context()` 用于清理。

`TcpClient` 常用 API：

```cpp
class SZX_NETWORK_API TcpClient final
{
public:
    static auto Create(TcpClientOptions options) -> SZX::COMMON::Result<std::unique_ptr<TcpClient>>;

    void onConnected(ConnectionCallback cb);
    void onMessage(MessageCallback cb);
    void onDisconnected(DisconnectCallback cb);
    void onError(ErrorCallback cb);
    void onReconnecting(std::function<void(std::uint32_t attempt, std::uint32_t delayMs)> cb);

    [[nodiscard]] auto connect() -> SZX::COMMON::Result<void>;                     // 异步发起
    [[nodiscard]] auto connectAndWait(std::uint32_t timeoutMs) -> SZX::COMMON::Result<void>;
    [[nodiscard]] auto send(std::span<const std::uint8_t> data) -> SZX::COMMON::Result<void>;
    [[nodiscard]] auto disconnect() -> SZX::COMMON::Result<void>;                  // 幂等，停止重连
    [[nodiscard]] auto connected() const noexcept -> bool;
    [[nodiscard]] auto connection() const -> std::shared_ptr<TcpConnection>;
};
```

回调必须在 `connect()` 之前注册完毕；`Create` 只做参数校验，不产生系统调用，这样端口/地址错误在 `connect()` 一处返回。

`onReconnecting` 是可观测性缺口的补齐：开了 `ReconnectPolicy` 之后，重连是组件内部行为，上层原本完全看不见，线上排查“为什么这条链路一直在抖”时没有任何依据。回调只报告即将进行第几次重试、等待多久，不提供干预能力（要停就调 `disconnect()`）。`maxRetries` 耗尽后触发一次 `onError(ConnectFailed, ...)` 并停止重连，不静默放弃。

`TcpServer` 常用 API：

```cpp
struct TcpServerOptions final
{
    Endpoint listen;                              // host 为空表示 0.0.0.0
    std::size_t ioThreadCount     = 2;
    std::size_t maxConnections    = 0;            // 0 = 不限
    FramePolicy frame;
    TlsOptions tls;
    std::shared_ptr<EventLoopGroup> loops;
};

class SZX_NETWORK_API TcpServer final
{
public:
    static auto Create(TcpServerOptions options) -> SZX::COMMON::Result<std::unique_ptr<TcpServer>>;

    void onConnected(ConnectionCallback cb);
    void onMessage(MessageCallback cb);
    void onDisconnected(DisconnectCallback cb);
    void onError(ErrorCallback cb);   // 服务级错误；单连接错误走 onDisconnected 的原因参数

    [[nodiscard]] auto start() -> SZX::COMMON::Result<void>;   // 绑定失败返回 BindFailed
    [[nodiscard]] auto stop() -> SZX::COMMON::Result<void>;    // 幂等，等待循环退出
    [[nodiscard]] auto running() const noexcept -> bool;
    [[nodiscard]] auto port() const noexcept -> std::uint16_t; // listen.port 为 0 时返回实际端口
    [[nodiscard]] auto connectionCount() const noexcept -> std::size_t;
    auto broadcast(std::span<const std::uint8_t> data) -> SZX::COMMON::Result<void>;
    auto foreachConnection(const std::function<void(const std::shared_ptr<TcpConnection> &)> &fn) const -> void;
};
```

`port()` 在 `listen.port == 0` 时返回内核分配的端口，这是测试用例能并发跑而不抢固定端口的前提。

两个回调的职责边界要在头注释里划清，否则使用方会把连接级抖动当成服务故障处理：

- `onError`：影响整个服务的错误（accept 失败、监听套接字异常、事件循环内部错误）。一条连接读写失败**不**触发它。
- `onDisconnected`：单连接终止，原因见 `DisconnectReason`。

`maxConnections` 达到上限时的行为也要定死：直接关闭新接受的连接，触发一次 `onError(SendQueueFull...)` 级别的服务级提示不合适，改为触发 `onDisconnected(conn, DisconnectReason::LocalClose, "maxConnections reached")`，并且**不**触发该连接的 `onConnected`——避免使用方在 `onConnected` 里已分配资源却立刻被关。

`broadcast` 与 `foreachConnection` 的线程约束：两者都会遍历连接表。`foreachConnection` 的 `fn` 可能在多个循环线程上被调用（每条连接在自己的循环上执行），因此 `fn` 内部不得假设串行，也不得阻塞。只需要统计信息时优先用 `connectionCount()`。

### 5.4 UDP

设计思路：UDP 没有连接，客户端与服务端的差别只是“是否绑定固定端口”和“对端是否固定”。因此只提供一个 `UdpSocket`，用 `bind()` / `setPeer()` 区分角色，避免造出行为几乎相同的两个类。数据报保持整包语义，不做分帧，不做重传。

常用 API：

```cpp
struct UdpSocketOptions final
{
    Endpoint bind;                          // port 为 0 表示不固定本地端口
```

### 5.5 HTTP 客户端

设计思路：绝大多数调用点只想要“发一个请求，拿到状态码和 body”，所以同步接口是主入口，异步接口用于事件循环内不能阻塞的场合。请求/响应用纯 std 类型，JSON 不在本组件处理（仓库已有 [JsonHelper.hpp](../../components/common/JsonHelper.hpp)）。

常用 API：

```cpp
struct HttpClientOptions final
{
    std::string baseUrl;                       // 可空；非空时 request 的 path 相对它拼接
    std::uint32_t connectTimeoutMs = 5000;
    std::uint32_t timeoutMs        = 15000;
    std::uint32_t maxRetries       = 0;        // 仅对幂等方法生效
    std::size_t maxResponseBytes   = 32u * 1024u * 1024u;
    std::map<std::string, std::string> defaultHeaders;
    TlsOptions tls;
};

struct HttpClientRequest final
{
    std::string method{"GET"};
    std::string url;                           // 绝对地址或相对 baseUrl
    std::string body;
    std::map<std::string, std::string> headers;
    std::map<std::string, std::string> query;
    std::uint32_t timeoutMs = 0;               // 0 = 用 options
};

struct HttpClientResponse final
{
    int statusCode = 0;
    std::string body;
    std::map<std::string, std::string> headers;
    std::uint32_t elapsedMs = 0;
};

class SZX_NETWORK_API HttpClient final
{
public:
    static auto Create(HttpClientOptions options) -> SZX::COMMON::Result<std::unique_ptr<HttpClient>>;

    [[nodiscard]] auto send(const HttpClientRequest &request) -> SZX::COMMON::Result<HttpClientResponse>;
    [[nodiscard]] auto get(std::string_view url) -> SZX::COMMON::Result<HttpClientResponse>;
    [[nodiscard]] auto postJson(std::string_view url, std::string body) -> SZX::COMMON::Result<HttpClientResponse>;
    [[nodiscard]] auto download(std::string_view url, const std::filesystem::path &target) -> SZX::COMMON::Result<void>;

    void sendAsync(HttpClientRequest request,
                   std::function<void(SZX::COMMON::Result<HttpClientResponse>)> cb);
};
```

`statusCode >= 400` 仍返回 `ok == true`：HTTP 语义上的错误码是有效响应，只有传输层失败才是 `Result` 失败。这条要在头文件注释里写清楚，否则调用方容易漏判。

**`send()` / `get()` / `postJson()` / `download()` 全部同步阻塞调用线程。**绝对不能在 `HttpServer` 的路由处理函数、`onMessage` 或任何事件循环回调里调用——那会占住循环线程，让同循环上的其他连接一起停摆。这类场景一律用 `sendAsync`，或把请求投递到 [ThreadPool.hpp](../../components/common/ThreadPool.hpp)。这条要写进头注释，并在使用说明里给反例。

**HTTP 头大小写**：头名按 RFC 7230 大小写不敏感，但 `std::map<std::string, std::string>` 是敏感的，`headers["Content-Type"]` 与 `headers["content-type"]` 会变成两个条目——写请求时可能发出重复头，读响应时可能取不到值。因此 `headers` 用大小写不敏感的比较器：

```cpp
struct CaseInsensitiveLess final
{
    using is_transparent = void;
    auto operator()(std::string_view lhs, std::string_view rhs) const noexcept -> bool;
};

using HttpHeaders = std::map<std::string, std::string, CaseInsensitiveLess>;
```

`HttpClientOptions::defaultHeaders`、`HttpClientRequest::headers`、`HttpClientResponse::headers` 以及 5.6 节服务端的 `headers` 统一改用 `HttpHeaders`。`query` 保持大小写敏感的 `std::map`（查询参数名按 RFC 是敏感的）。`maxRetries` 的适用范围也要写明：仅 GET/HEAD/PUT/DELETE/OPTIONS/TRACE 这些幂等方法重试，POST/PATCH 永不自动重试，避免重复下单类事故。

### 5.6 HTTP 服务端

设计思路：只提供通用能力——监听、路由、路径参数、中间件、请求体上限、静态目录挂载、未命中处理。**不内置任何业务约定**：错误响应体格式、鉴权、请求 ID 生成、SPA 回退策略都由使用方在中间件和 `onNotFound` 里实现。

常用 API：

```cpp
struct HttpServerRequest final
{
    std::string method;
    std::string path;
    std::string body;
    HttpHeaders headers;                             // 大小写不敏感，见 5.5
    std::map<std::string, std::string> query;
    std::map<std::string, std::string> pathParams;   // 路由 /users/{id} 的 id
    Endpoint peer;

    // 中间件 → handler 的传值通道：认证结果、request id、耗时起点等
    std::map<std::string, std::string> attributes;
    std::shared_ptr<void> userContext;               // 需要传结构体而非字符串时用
};

struct HttpServerResponse final
{
    int statusCode = 200;
    std::string body;
    HttpHeaders headers;
};

using HttpRouteHandler = std::function<HttpServerResponse(const HttpServerRequest &)>;

// 洋葱模型：中间件自己决定是否调用 next，并且能在 next 返回后加工响应
using HttpNext       = std::function<HttpServerResponse(HttpServerRequest &)>;
using HttpMiddleware = std::function<HttpServerResponse(HttpServerRequest &, const HttpNext &)>;
```

两处偏离初稿，都是为了让中间件真正够用：

`attributes` / `userContext`：初稿里中间件解析出的 request ID 和认证用户没有正规通道传给 handler，只能塞进 `headers` 冒充请求头——handler 分不清哪个是客户端发来的、哪个是自己注入的，这在鉴权场景里是真实的安全隐患（客户端可以伪造 `X-User-Id` 头）。`attributes` 由服务端独占写入，与 `headers` 物理隔离，杜绝这种混淆。

中间件从「短路型」改为「洋葱型」：`std::optional<HttpServerResponse>(HttpServerRequest &)` 只能在 handler **之前**做事，无法在之后加工响应，因此访问日志（要记状态码和耗时）、统一响应头注入、异常兜底、压缩这些最常见的中间件全都写不了。洋葱模型的代价只是多传一个 `next`，换来的是全覆盖：

```cpp
server->use([](HttpServerRequest &req, const HttpNext &next) {
    const auto start = std::chrono::steady_clock::now();
    auto response    = next(req);                       // 不调用 next 即短路
    response.headers["X-Elapsed-Ms"] = std::to_string(
        std::chrono::duration_cast<std::chrono::milliseconds>(
            std::chrono::steady_clock::now() - start).count());
    return response;                                     // 可加工响应
});
```

```cpp
struct HttpServerOptions final
{
    Endpoint listen;
    std::size_t ioThreadCount        = 4;
    std::size_t maxBodyBytes         = 1u * 1024u * 1024u;
    std::uint32_t keepaliveTimeoutMs = 60000;
    TlsOptions tls;
    std::shared_ptr<EventLoopGroup> loops;
};

class SZX_NETWORK_API HttpServer final
{
public:
    static auto Create(HttpServerOptions options) -> SZX::COMMON::Result<std::unique_ptr<HttpServer>>;

    [[nodiscard]] auto route(std::string method, std::string path, HttpRouteHandler handler) -> SZX::COMMON::Result<void>;
    [[nodiscard]] auto get(std::string path, HttpRouteHandler handler) -> SZX::COMMON::Result<void>;
    [[nodiscard]] auto post(std::string path, HttpRouteHandler handler) -> SZX::COMMON::Result<void>;
    [[nodiscard]] auto put(std::string path, HttpRouteHandler handler) -> SZX::COMMON::Result<void>;
    [[nodiscard]] auto del(std::string path, HttpRouteHandler handler) -> SZX::COMMON::Result<void>;

    // fallbackFile 非空时，前缀下未命中的路径返回该文件（SPA 一行接入）
    [[nodiscard]] auto mountStatic(std::string urlPrefix,
                                   std::filesystem::path directory,
                                   std::string fallbackFile = {}) -> SZX::COMMON::Result<void>;

    void use(HttpMiddleware middleware);                       // 最先注册的最外层
    void onNotFound(HttpRouteHandler handler);
    void onError(ErrorCallback cb);

    [[nodiscard]] auto start() -> SZX::COMMON::Result<void>;
    [[nodiscard]] auto stop() -> SZX::COMMON::Result<void>;
    [[nodiscard]] auto running() const noexcept -> bool;
    [[nodiscard]] auto port() const noexcept -> std::uint16_t;
};
```

补 `put` / `del`：初稿只有 `get` / `post` 两个便捷方法，REST 服务缺了 `PUT` / `DELETE` 就得退回 `route("PUT", ...)` 手写字符串方法名，拼错只能运行时发现。

`mountStatic` 的 `fallbackFile`：SPA 回退如果只能在 `onNotFound` 里实现，每个使用方都要重写一遍「判断是不是静态前缀 → 读 index.html → 猜 MIME → 处理读失败」，而且容易把 API 的 404 也错误地回退成 HTML 页面（前端拿到 200 + HTML 却在解析 JSON）。挂载点自带回退能把范围精确限制在该 URL 前缀内，API 路径的 404 仍然是 404。

**路由路径语法要在头注释里定死**，否则使用方按 libhv 的写法传参会静默失配：统一用 `{name}` 占位（如 `/api/v1/users/{id}`），实现层负责转换成 libhv 的语法；通配用 `/*`。`route()` 在路径语法非法或与已注册路由冲突时返回 `InvalidArgument`，这也是这些方法标 `[[nodiscard]]` 的原因。

**路由处理函数抛异常的行为**同样要写明：组件在最外层兜底捕获，返回 500 并触发 `onError`，绝不让异常穿透到 libhv 的事件循环里（那会终止整个循环线程，等于一次请求打挂整个服务）。

安全默认值，必须在文档和头注释里写明：

- `HttpServer` **默认没有任何认证与授权**。任何对外暴露的服务都要自行加鉴权中间件，组件不会替使用方兜底；
- `mountStatic` 内部做路径规范化并拒绝越界路径（`..`、符号链接逃逸、Windows 盘符前缀），实现时按 admin 侧已有的安全路径校验思路处理；
- `maxBodyBytes` 有默认上限，超限直接返回 413 且不读完请求体；
- `listen.host` 默认建议填 `127.0.0.1`，需要对外监听时由使用方显式写 `0.0.0.0`。

## 6. 线程模型与生命周期

1. **回调线程**：所有 `onMessage` / `onConnected` / `onDatagram` / 路由处理函数都在事件循环线程执行。同一连接的回调串行，不同连接可并发。
2. **禁止阻塞**：回调里不做数据库访问、文件大 IO、密码哈希或加锁等待。需要阻塞时投递到 [ThreadPool.hpp](../../components/common/ThreadPool.hpp) 或 [WorkQueueService.hpp](../../components/common/WorkQueueService.hpp)，处理完再用连接对象 `send`。这条与[三方库评审](../RBAC/07-C++三方库评审.md)对 libhv + ormpp 的结论一致。
3. **停止顺序**：`stop()` 先停止接受新连接与新请求，再关闭已有连接，最后等待事件循环退出后返回；返回后不再有任何回调触发。析构函数内部调用 `stop()`，保证漏调也不会悬空。
4. **回调持有的对象**：回调只捕获 `weak_ptr` 或保证生命周期长于服务端的对象。`TcpConnection` 用 `shared_ptr` 暴露正是为此。
5. **重入**：在回调内调用 `close()` / `send()` 安全；在回调内调用 `stop()` 不安全（会自等），实现层需检测并返回 `NetworkError::Internal` 而不是死锁。

## 7. 与现有代码的关系

`SZX::ADMIN::INFRA::HttpTransport`（[tools/szx_admin/include/SzxAdmin/Infra/HttpTransport.h](../../tools/szx_admin/include/SzxAdmin/Infra/HttpTransport.h)）是 admin 服务的内部实现，不是通用能力，**不上移为 `szx::network` 的公共 API**。它承载的统一错误响应、request ID、静态资源与 SPA 回退、`/api/v1/health` 都是 admin 的产品约定，保持在 RBAC 内部。

因此两者关系是：

- `szx::network` 独立设计通用 `HttpServer`，不参考 admin 的契约做取舍，也不为兼容 admin 保留任何接口形状；
- admin 是否在后续把 `HttpTransport` 的实现改成基于 `szx::network`（对外接口不变，只换内部后端）由 admin 自己决定，不属于本计划的交付项；
- 唯一必须协同的是 libhv 的获取方式（第 3.1 节）：两边共用 `szx_add_libhv()`，避免选项互相覆盖。

覆盖点：

| 用例 | 断言 |
| --- | --- |
| TCP 回环收发 | `listen.port = 0` 取实际端口，客户端连上、发帧、收到回包、正常断开 |
| 三种分帧 | 分隔符/定长/长度字段各自切帧正确；超过 `maxFrameSize` 返回 `MessageTooLarge` 且连接关闭 |
| 连接失败 | 连未监听端口返回 `ConnectFailed`；域名不存在返回 `ResolveFailed` |
| 端口占用 | 两个 server 绑同端口，第二个返回 `BindFailed` |
| 重连 | 服务端重启后客户端按退避重连成功，重试上限生效 |
| UDP 回环 | `sendTo` / `onDatagram` 收到完整数据报和正确来源端点 |
| HTTP 客户端 | 200/404/500 均 `ok == true` 且 statusCode 正确；超时返回 `ReadTimeout`；连不通返回 `ConnectFailed` |
| HTTP 服务端 | 路由命中、路径参数解析、中间件短路、`onNotFound` 生效、超 `maxBodyBytes` 返回 413 |
| 静态目录 | 正常文件可取；`..` 越界路径被拒绝 |
| 停止语义 | `stop()` 返回后无回调触发；重复 `stop()` 和析构不崩溃 |
| 断开原因 | 本地 `disconnect()` → `LocalClose`；对端关闭 → `PeerClose`；超 `maxFrameSize` → `ProtocolError`；积压超限 → `SendQueueFull` |
| 发送队列背压 | 不读取的对端 + 持续 `send`，`pendingBytes()` 上升并最终返回 `SendQueueFull`，进程不 OOM |
| `maxConnections` | 达上限后新连接被关且**未**触发 `onConnected` |
| 头大小写 | `headers["content-type"]` 与 `headers["Content-Type"]` 命中同一条目；响应头按任意大小写均可读出 |
| 中间件洋葱序 | 三个中间件的进入顺序为注册序、退出顺序为逆序；外层能改到内层产生的响应状态码 |
| 中间件传值 | 中间件写入 `attributes` 后 handler 可读；客户端伪造的同名请求头不污染 `attributes` |
| handler 抛异常 | 返回 500、触发 `onError`、事件循环存活，后续请求仍能正常处理 |
| 路由冲突 | 重复注册同 method+path 返回 `InvalidArgument`；非法占位语法同样被拒 |
| SPA 回退 | `mountStatic` 带 `fallbackFile` 时前缀内未命中返回该文件；前缀外的 API 路径仍返回 404 |
| 幂等重试范围 | GET 在 5xx 下按 `maxRetries` 重试；POST 不重试（用计数服务端断言只收到一次） |

约束：只绑 `127.0.0.1`，端口一律由内核分配，用例不依赖外网。

## 10. 风险与未决问题

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| libhv 两处配置互相覆盖 | `HttpClient` 缺失或行为不一致 | 第 3.1 节的 `szx_add_libhv()`；改动后必须回归 admin 构建 |
| 打开 `WITH_HTTP_CLIENT` | admin 产物体积增加、编译时间变长 | 阶段 0 单独提交并记录构建时长与体积差 |
| MSVC 运行库/配置混用 | SHARED 库跨 DLL 传 `std::string` 崩溃 | 沿用 `szx_apply_default_compile_policy`，Debug/Release 不混链；接口层不返回裸容器引用之外的跨 DLL 所有权 |
| libhv 分帧能力边界 | 少数私有协议无法用 `LengthField` 表达 | 保留 `FrameMode::None`，上层自行分帧 |
| Windows 停止时序 | `stop()` 后仍有回调或线程残留 | 停止语义列为独立用例，含重复 stop 与析构 |
| 两份 OpenSSL | 符号冲突 | TLS 与 `szx::crypto` 共用 `SZX_OPENSSL_ROOT`，不引入第二份 |

需要确认的取舍：

1. 首版是否要 `HttpClient`。RBAC 当前显式关掉了 libhv 的 HTTP 客户端，如果暂时没有出站 HTTP 需求，可以把它推到阶段 3 之后，阶段 0 就不动 `WITH_HTTP_CLIENT`。
2. TLS 是否进首版。评审结论倾向由 NGINX/网关终止 TLS，那么阶段 4 可以推后。
3. WebSocket 是否需要（例如 Admin 实时日志或设备状态推送）。
4. 是否需要 IPv6 与 Unix Domain Socket（libhv `ENABLE_UDS` 默认 OFF）。

### 10.1 明确推迟到 v1 之后的能力

评审中识别出但**刻意不进首版**的点，记在这里避免日后重复讨论，也避免实现时顺手加进来把 API 面撑大：

| 能力 | 推迟原因 | 何时该做 |
| --- | --- | --- |
| 流式请求/响应体（chunked、`onBodyChunk`） | 会把 `HttpServerResponse` 从值语义变成回调语义，波及整个 API 面 | 出现大文件上传或下载需求时 |
| `Range` / `ETag` / `Last-Modified` 条件请求 | `mountStatic` 首版只服务小体积前端资源，够用 | 静态资源体积变大或需要断点续传时 |
| TCP 半关闭（`shutdownWrite`） | 只有少数私有协议依赖它表达“我发完了” | 遇到需要它的协议时 |
| 发送高低水位回调（`onWritable`） | `pendingBytes()` + `SendQueueFull` 已能表达背压，回调形式的水位事件是精细化优化 | 出现持续大流量推送场景时 |
| 连接级限速 / 全局连接数配额 | 属于治理策略，不是传输能力 | 需要多租户隔离时 |
| TLS 双向认证、ALPN、SNI | 取决于 TLS 是否进首版（上面第 2 条） | TLS 落地时一并设计 |

同时明确两条**永不进入**本组件的边界，防止组件退化成业务框架：业务序列化格式（JSON/Protobuf 的编解码由使用方决定，组件只搬字节）、鉴权与会话策略（组件只提供中间件挂载点，不内置任何认证实现）。这与第 1.2 节的边界一致。
