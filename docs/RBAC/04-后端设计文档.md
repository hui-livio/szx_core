# 单项目 RBAC 后端设计

## 1. 模块

- `auth`：登录、刷新、登出、改密、锁定。
- `user`：用户生命周期、状态和单角色分配。
- `audit`：可信安全审计写入和查询。
- `telemetry`：客户端行为事件校验、有界队列、批量延迟写和查询。
- `maintenance`：安全审计和行为事件保留期清理。
- `policy`：按固定角色执行接口校验。

第一阶段单体服务即可。Controller 负责协议，Service 负责规则和事务，Repository 使用参数化 SQL 和版本化 migration。任何数据库、JWT 或第三方库异常都必须在服务边界转换为稳定错误码。

创建用户时先锁定 `admin_bootstrap` 单例行，再锁定调用者并检查身份冲突；事务结束时释放锁，使多个服务实例的跨字段判重与插入串行执行。UID 保留大小写，username 的跨字段比较复用登录 Unicode 规范化逻辑。修改用户后在原事务内重新读取记录，使响应中的 updated_at 与本次数据库写入一致。

连接回滚失败时关闭连接并保留空池槽位；后续请求重新连接并设置 UTC、事务隔离级别及锁等待超时。重连失败仍保留容量，不重放失败的业务事务。

运行日志使用 INFO 记录认证初始化、数据库 schema/迁移/bootstrap 结果，以及停止信号。连接不可用/恢复、审计写入失败/恢复仅在状态变化时记录；HTTP 失败响应的稳定错误码合并到原访问日志。用户操作详情继续由事务内审计承载，运行日志不重复输出密码、token、数据库凭据或完整请求/响应。

## 2. 固定角色策略

后端内置角色能力矩阵，不允许运行时编辑：

| 能力 | 操作员 | 工程师 | 管理员 | 超管 |
|---|---:|---:|---:|---:|
| 业务查看/操作 | ✓ | ✓ | ✓ | ✓ |
| 工程配置/诊断 |  | ✓ | ✓ | ✓ |
| 用户读取/创建/编辑/启停（仅操作员/工程师） |  |  | ✓ | ✓ |
| 用户解锁/密码重置（仅操作员/工程师） |  |  | ✓ | ✓ |
| 管理员/超管用户管理 |  |  |  | ✓ |
| 管理员/超管角色分配 |  |  |  | ✓ |
| 安全审计查询（`audit.read`） |  |  | ✓ | ✓ |
| 行为事件查询（`behavior.read`） |  |  | ✓ | ✓ |

用户只有一个角色，采用固定映射；后续增加动态权限时再替换 Policy 实现。能力码至少包括 `business.read`、`business.operate`、`engineering.configure`、`user.read`、`user.create`、`user.update`、`user.status`、`user.unlock`、`user.password.reset`、`user.role.assign`、`audit.read` 和 `behavior.read`。项目配置和系统重置不属于第一阶段，不定义对应能力码或接口。

Policy 在每个请求中同时校验：当前用户状态、当前 `authz_version`、能力码、目标用户角色和目标用户状态。不得只根据 JWT 中的 role 判断。

管理员对用户管理接口的目标角色只能是 `operator/engineer`；超管可操作四类角色，但不能禁用、降级或并发移除最后一个 active 超管。`user.unlock` 和 `user.password.reset` 遵循相同的目标角色限制。任何用户都不能给自己分配角色（包括提交原角色）或禁用自己，返回 `403 / 2204`；不能操作高于自身权限或超出管理范围的目标。

## 3. 认证与审计

Argon2id 密码哈希，参数和升级策略由部署配置冻结；access JWT 15 分钟，refresh token 一次一换并检测重放。refresh 默认空闲期限为 30 分钟，family 绝对期限为 7 天；成功轮换重置空闲窗口，但不延长绝对到期时间。JWT 固定使用 issuer、audience、subject、jti、iat、nbf、exp 和 authz version。登录、改密、用户操作、角色变更、禁用/解锁和 refresh 重放写入 `security_audit_logs`；客户端上传的自定义行为事件写入 `client_behavior_events`，通过有界内存队列批量延迟入库。关键安全审计必须可靠落库；审计写入失败时，相关安全操作回滚或明确失败，不得静默成功。

后端按用户固定角色计算能力码，通过 Client 接口返回；能力列表不由客户端提交，角色变更后按最新用户记录计算。客户端行为埋点是非可信 telemetry，服务端必须独立记录安全审计。

行为上报接口不使用分钟计数。HTTP 线程只校验、脱敏并尝试写入容量为 `queueCapacity` 的进程内队列，成功入队返回 202；队列满返回 `503 / 2225`，写入器未接入、故障或排空中返回 `503 / 2226`。单消费者按 `batchSize` 或 `flushIntervalMs` 组批，并用 `minCommitIntervalMs` 控制数据库提交频率。重试保留原事件 UUID；提交结果未知时淘汰连接并按 UUID 幂等确认，系统性 schema/权限错误令写入器进入 `Faulted`，readiness 同步失败。

Windows 服务收到 `SIGBREAK`、POSIX 服务收到 `SIGHUP` 时只设置恢复请求标志；主循环随后调用 `resumeAfterFault()`。恢复探测会开启事务、验证仓储/schema/写权限并执行可回滚试写，成功后才重新接入。`SIGINT` 和 `SIGTERM` 仍用于排空停机。

当前不再提供 legacy 日志开关、双写、回填或聚合兼容接口。`/admin/audit-logs` 只查询 `security_audit_logs`，`/admin/behavior-events` 只查询 `client_behavior_events`；Migration 5 删除历史 `user_logs`。

## 4. 安全规则

管理员不能创建、编辑、禁用或重置超管；管理员只能管理操作员/工程师。只有超管可以分配管理员/超管角色。禁止禁用、降级或并发移除最后一个 active 超管。所有写操作使用事务和 `version` 防止并发覆盖；角色/状态/密码变更同时递增 `authz_version`。

## 5. 认证与账户安全规则

- 登录统一使用 `identifier + password_hash`；password_hash 是原始密码 UTF-8 字节的 SHA-256 小写十六进制值，服务端使用随机盐 Argon2id 保存，格式为 `sha256-v1:<PHC>`。不接受明文 password 回退，失败响应不可泄露账号是否存在。
- 待改密超管登录返回 `force_password_change=true`，业务端必须先完成改密；非超管返回 `force_password_change=false`、`password_change_recommended=true`，业务端允许跳过。跳过不清除数据库待改密标记。
- 临时凭据只允许在 `temporary_credential_expires_at` 前登录；超管成功登录时消费，非超管为支持跳过而保留原有效期。改密成功后清除数据库 `force_password_change` 和该过期时间。
- `src/auth/ChangePassword.cc` 实现首次及自助改密；在用户行锁内校验 JWT 对应用户、active 状态、authz_version、If-Match 和旧密码摘要。同一事务写入新密码、版本、refresh 撤销及审计；成功后要求重新登录。
- 连续失败次数、锁定阈值、锁定时长和按 IP 限流必须配置化并记录审计。
- disabled/locked 用户不能登录；每次受保护请求都要按服务端用户状态校验。
- 改密、管理员重置密码、角色变更和禁用统一递增 `authz_version`，使相关 access token 立即失效；refresh family 同时按会话规则撤销。
- 当前 bootstrap 幂等创建 `admin` / `superadmin` 初始超管，强制首次改密；重复启动不重置密码。数据库只保存摘要经 Argon2id 处理后的值，运行日志不输出凭据。
- 密钥由部署环境安全管理并支持轮换；禁止客户端指定 JWT 算法。

Refresh token 消费必须在事务中对当前 token 行加锁并原子设置 `revoked_at/replaced_by`；并发 refresh 只能有一个成功，旧 token 重放时在同一事务中撤销整个 family。

`src/auth/SessionLifecycle.cc` 已实现 refresh/logout。与登录/改密保持相同锁顺序：先无锁查询 token 归属，再锁用户，随后锁定并重新读取 token。刷新同时校验 `expires_at` 绝对期限和 `created_at + auth.refreshIdleTimeoutSeconds` 空闲期限，任一到期均返回 `401 / 2201` 且不签发新 token；成功轮换的新行以当前时间写入 `created_at`，重置空闲窗口，并保留 family 原到期时间。Cookie 的 `Max-Age` 取两个期限的剩余时间较小值。登出撤销当前 family，重复调用幂等。两个接口使用 Cookie + CSRF，不依赖 access JWT；重放撤销必须提交后再返回 409，审计失败则回滚。会话签发与登录共享实现，路由和 OPTIONS 仍由 `Routes.cc` 注册。登出/重放不即时吊销已签发的 access JWT；实际角色、状态和密码变更已与授权版本递增、refresh 撤销在同一事务中提交。

## 6. Admin 静态托管

`HttpTransport` 复用网络库的 `HttpServer::CreateStaticHandler`，将 `server.staticRoot/admin` 挂载到 `/admin/`；`GET /admin` 返回 308 跳转到 `/admin/`。开启 `spaFallback` 后，无扩展名的前端路由（例如 `/admin/users`）回退到该目录的 `index.html`。API 请求、非 GET/HEAD 请求、缺失的 JS/CSS 和被拒绝的路径穿越不会回退到 Admin HTML。API 前缀根路径单独提供 Swagger UI：`/api/v1` 跳转 `/api/v1/`，`/api/v1/openapi.json` 提供契约，`/api/v1/docs/` 提供本地文档资源；只允许 GET/HEAD，未知 API 仍返回 JSON 404。资源来自 `staticRoot/api-docs`，入口和请求地址随配置的 apiPrefix 变化。

静态目录在服务启动时初始化，首次部署需重启；相对路径以进程工作目录为准。Vite 生产构建使用 `/admin/` base；CMake 在配置时检测到 dist 后添加 `szx_admin_web_assets`，每次构建服务复制已有产物，不负责执行 npm。具体目录和命令见 [部署指南](12-Admin部署与使用指南.md)。
