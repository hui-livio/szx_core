# 用户审计与行为事件拆分方案

- 文档状态：方案已确定，代码正在按分阶段迁移落地
- 决策日期：2026-09-21
- 适用范围：`tools/szx_admin`、`tools/szx_admin/web/admin`、`docs/RBAC`

## 1. 背景与问题

当前服务端安全审计和客户端上传的自定义行为事件共同写入 `user_logs`。两类数据复用同一个写入接口、查询接口和管理页面：

- 登录、改密、刷新令牌和用户管理操作由服务端生成，属于可信安全审计；
- `POST /client/behavior-events` 接收客户端提交的数据，属于非可信 telemetry；
- `GET /admin/user-logs` 同时返回两类记录，响应中没有可信来源字段；
- 两类数据共用索引、保留期和清理策略。

当前实现通过拒绝客户端提交 `auth.*`、`user.*` 事件名降低伪造风险，但事件名前缀不是持久化的数据来源证明。行为接口不设置每用户或全局每分钟写入上限，允许短时间突发上报；数据库写入端设置有界待入库队列、批次大小和提交间隔，由后台分批延迟写入。客户端事件的数据增长速度会显著高于用户管理和认证审计，继续共表会让高频 telemetry 影响安全审计的查询、存储、归档和保留策略。

## 2. 决策

采用同一服务、同一 MySQL 数据库、两个物理表和两个领域仓储：

| 数据 | 物理表 | 所有者 | 信任级别 | 默认保留期 |
|---|---|---|---|---:|
| 服务端安全审计 | `security_audit_logs` | `AUDIT` | 服务端可信 | 180 天 |
| 客户端行为事件 | `client_behavior_events` | `TELEMETRY` | 客户端非可信 | 30 天 |

不拆分进程或微服务。两个仓储继续使用同一个 `DatabaseConnection`，保证安全审计能够与用户变更、密码变更和会话撤销处于同一数据库事务。

客户端事件采用进程内异步批量写入：HTTP 完成鉴权、校验、脱敏和有界队列入队后返回 `202`；单个后台消费者按批次和固定提交节奏写入数据库。接口不再按分钟或按用户计数限流，数据库写入频率由批次大小和最小提交间隔控制。队列容量是内存保护和背压机制，不属于每分钟调用限制。

```text
POST /client/behavior-events
        │ 鉴权、校验、脱敏、生成 ID/接收时间
        ▼
有界内存队列 ──202 Accepted──► Client
        │ 单消费者组批、失败重试
        ▼
client_behavior_events
```

原 `user_logs` 在迁移期保留为兼容表，不再作为长期写模型。完成一个完整审计保留窗口和备份恢复验证后，才允许通过单独审核的破坏性 migration 删除。

## 3. 数据库设计

### 3.1 security_audit_logs

```sql
CREATE TABLE IF NOT EXISTS security_audit_logs (
  id CHAR(36) NOT NULL PRIMARY KEY,
  actor_user_id CHAR(36),
  target_user_id CHAR(36),
  event_name VARCHAR(96) NOT NULL,
  result VARCHAR(16) NOT NULL,
  request_id VARCHAR(128) NOT NULL,
  ip VARCHAR(45),
  user_agent VARCHAR(512),
  details_json JSON NOT NULL,
  created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  CONSTRAINT chk_security_audit_result
    CHECK (result IN ('success', 'failure', 'denied')),
  INDEX idx_security_audit_time (created_at DESC, id ASC),
  INDEX idx_security_audit_actor_time (actor_user_id, created_at DESC, id ASC),
  INDEX idx_security_audit_target_time (target_user_id, created_at DESC, id ASC),
  INDEX idx_security_audit_event_time (event_name, created_at DESC, id ASC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

`actor_user_id` 和 `target_user_id` 不建立用户外键。安全审计必须独立于用户记录生命周期保留；未来即使引入用户物理删除，也不能连带删除审计事实或清空原始用户 ID。API 仍可通过 `LEFT JOIN users` 返回当前登录标识，无法关联时返回空字符串。

`ip` 和 `user_agent` 属于内部审计字段。当前 API 不暴露数据库中的 IP，拆分后保持这一安全边界。

### 3.2 client_behavior_events

```sql
CREATE TABLE IF NOT EXISTS client_behavior_events (
  id CHAR(36) NOT NULL PRIMARY KEY,
  user_id CHAR(36) NOT NULL,
  event_name VARCHAR(96) NOT NULL,
  result VARCHAR(16) NOT NULL,
  request_id VARCHAR(128) NOT NULL,
  ip VARCHAR(45),
  user_agent VARCHAR(512),
  details_json JSON NOT NULL,
  created_at DATETIME(6) NOT NULL,
  persisted_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  CONSTRAINT chk_client_behavior_result
    CHECK (result IN ('success', 'failure')),
  CONSTRAINT fk_client_behavior_user
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE RESTRICT,
  INDEX idx_client_behavior_time (created_at DESC, id ASC),
  INDEX idx_client_behavior_user_time (user_id, created_at DESC, id ASC),
  INDEX idx_client_behavior_event_time (event_name, created_at DESC, id ASC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

客户端接口现有语义规定操作者和目标用户都是当前用户，因此新表只保留一个非空 `user_id`。客户端不能提交该字段。`details_json` 继续执行现有递归脱敏和 4096 字节限制。

`created_at` 在事件成功进入队列前由服务端记录，表示 HTTP 接收时间；批量 SQL 必须显式写入该值。`persisted_at` 由 `DEFAULT CURRENT_TIMESTAMP(6)` 在首次成功插入行时生成，表示数据库执行 `INSERT` 的时间，不表示事务 `COMMIT` 完成时间；幂等重试命中已有 UUID 时不得更新该字段。`persisted_at - created_at` 只用于近似监控排队至写入语句的延迟，事务提交耗时单独统计。两个字段都不改变管理页面的事件时间或保留期起点，延时写入不能把 `created_at` 改成数据库写入时间。

外键显式使用 `ON DELETE RESTRICT`。当前系统没有用户物理删除接口；将来若引入物理删除，必须先按受控流程清理该用户已超过业务保留要求的客户端事件，不能隐式级联删除或匿名化安全审计。

### 3.3 Migration 版本

在 `DatabaseInitialization.cc` 追加 `kMigration4` 和对应 SHA-256 checksum。已发布的 Migration 1–3 及其 SQL、空白和 checksum 保持不变。

Migration 4 只创建两张新表，不搬迁历史数据。应用启动 migration 不适合执行可能持续较久的数据回填；历史搬迁由可观测、可重试的运维步骤完成。

## 4. 后端模块与仓储边界

新增以下内部边界：

```text
AUDIT
  AuditRecord
  AuditFilter
  AuditRepository::append/query
  AuditService::list

TELEMETRY
  BehaviorEvent
  BehaviorEventFilter
  BehaviorEventRepository::appendBatch/query
  BehaviorEventBuffer
  BehaviorEventWriter
  BehaviorEventService::record/list
```

具体调整：

- `LoginRepository` 删除 `insertAudit()`，只负责用户认证状态和 refresh token；
- `UserRepository` 删除 `queryLogs()`，只负责用户生命周期数据；
- `DatabaseConnection` 增加 `auditRepository()` 和 `behaviorEventRepository()`；
- 登录、改密、刷新、登出和用户变更从当前事务连接取得 `AuditRepository`；
- `UserService::recordBehavior()` 移入 `BehaviorEventService`；
- `BehaviorEventService::record()` 只负责同步验证与非阻塞入队，不在 HTTP 线程执行事件 INSERT；
- `BehaviorEventWriter` 是单消费者，负责组批、控制提交频率、重试和停机排空；
- 仓储把数据库失败转换为 RBAC 后端稳定错误码，数据库驱动编号、异常文本和 SQL 诊断不得进入 HTTP 响应。

队列复用 `SZX::COMMON::BlockingQueue<BehaviorEventRecord>` 的显式容量、`pop_for()`、`try_pop()`、`close()` 和高水位统计。现有队列只有阻塞式 `push()`，实现阶段在 `common` 中补充通用的非阻塞 `try_push()`，返回类型化的 `Pushed`、`Full` 或 `Closed` 结果，并增加单元测试。状态判断和入队必须在同一队列锁内完成，HTTP 线程不得先检查 `full()` 或 `is_closed()` 再调用 `push()`，该组合存在竞争并可能阻塞或映射错误码。`WorkQueueService` 面向逐任务状态、future 和取消，停止时会取消排队任务，不符合本场景的批量提交和关闭后排空语义，因此不使用。

`BehaviorEventBuffer` 在底层队列之外维护 `Accepting`、`Faulted`、`Draining`、`Stopped` 生命周期。HTTP 入队与状态迁移使用同一生命周期锁：只有 `Accepting` 才调用 `try_push()`；其他状态返回 2226。`Faulted` 只关闭 admission，不调用不可逆的 `BlockingQueue::close()`，因此已接收数据仍保留且修复后可以继续消费；只有进入终态 `Draining` 时才调用 `close()`，排空后转为 `Stopped`。

不在 `common` 中增加日志领域抽象。可信审计和非可信 telemetry 的批处理、重试与错误语义仍由各自领域模块拥有。

## 5. 一致性与失败语义

### 5.1 安全审计

成功的用户创建、用户资料修改、状态变更、解锁、角色变更、密码重置、登录状态修改、refresh 撤销与对应审计必须使用同一连接和同一事务。业务写入和成功审计同时提交或同时回滚。

鉴权拒绝、登录失败等没有业务变更的安全结果使用独立短事务提交审计，审计提交成功后才返回原业务错误。业务事务因数据库或内部错误回滚时，不保留同一事务内的成功审计；只有产品明确要求记录的失败事件才在回滚后开启独立事务写入。

对于已经确定必须审计的安全结果，获取连接、开始事务、写入或提交中的任何失败都在审计领域边界统一转换为 `2212 / AUDIT_WRITE_FAILED`，底层数据库原因只写内部监控。业务操作本身在形成必须审计的结果之前发生数据库失败时，仍返回对应的稳定数据库错误，不把一般业务数据库失败误报为审计失败。

安全审计写入失败时返回 `2212 / AUDIT_WRITE_FAILED`，业务事务回滚。不得降级为仅写普通运行日志后继续返回成功。

### 5.2 客户端行为事件

行为事件在验证 access token、当前用户状态、`authz_version`、事件名和脱敏规则后，生成稳定 UUID 和服务端接收时间，再尝试非阻塞入队。接口不执行每用户或全局的分钟计数，不返回行为上报 `429`。

成功入队后返回 `202`。该响应只表示事件已进入当前进程的内存队列，不表示已经提交数据库。队列为有界、非持久化队列；进程崩溃、强制终止或停机排空超时可能丢失已返回 `202` 但尚未提交的 telemetry。客户端事件是尽力而为的数据，不能用于安全审计、计费或必须准确执行的业务状态。如未来要求进程故障后不丢失，必须另行引入持久化 WAL 或外部消息代理，不能通过扩大内存队列宣称可靠。

`BehaviorEventWriter` 使用单消费者保持接收顺序。空批次先阻塞等待第一条；取得第一条后记录单调时钟截止点，再用 `pop_for(剩余时间)` 收集后续事件，直到达到 `batchSize`、`flushIntervalMs` 截止点或进入关闭排空状态。关闭排空时可用 `try_pop()` 立即填满当前批次。每次数据库事务最多写一个批次，两个成功提交之间至少间隔 `minCommitIntervalMs`，从而限制事件表的事务频率和单次写入量。

批次写入必须按服务端生成的 ID 幂等。`BehaviorEventRepository::appendBatch()` 返回内部类型化结果，写入器不能依靠数据库错误文本决定重试：

| 结果 | 典型场景 | 处理 |
|---|---|---|
| `Committed` | 整批提交成功；或相同 UUID 和不可变内容已经存在 | 完成当前批次，继续消费 |
| `RetryableFailure` | 已确认事务未提交的临时连接、死锁或锁等待失败 | 保留原 UUID，按有上限的指数退避重试 |
| `CommitResultUnknown` | 发送 `COMMIT` 后连接中断或操作超时，无法确认结果 | 丢弃该连接，使用原 UUID 重试并按幂等结果收敛 |
| `RecordPermanentFailure` | 单条记录违反约束、编码非法，或相同 UUID 对应不同不可变内容 | 回滚当前尝试，通过二分批次隔离坏记录 |
| `SystemicPermanentFailure` | 表或列缺失、权限错误、schema 不兼容或运行配置无效 | admission 转为 `Faulted`、readiness 失败，保留内存中的待写数据并等待运维处理 |

重复 UUID 只有在目标表中除 `persisted_at` 外的字段与待写记录一致时才视为成功；内容冲突属于 `RecordPermanentFailure`，不能静默覆盖。`RetryableFailure` 和 `CommitResultUnknown` 在成功前不消费后续批次，数据库故障可能使队列逐渐填满。所有重试都复用原 ID，不能生成新 ID；相同 UUID 重试确认已提交后，该批次不再属于未决提交。

`RecordPermanentFailure` 不能无限重试并阻塞整个队列。批次大于一条时，写入器按原顺序二分并分别提交，直到定位到单条失败记录；每个成功子批次仍遵守最小提交间隔。失败单条属于尽力而为 telemetry，丢弃后才继续处理后续记录，只记录事件 ID、失败分类、计数和时间，不把事件内容、details 或数据库诊断写入普通日志。需要保留样本时只能进入访问受控且有容量上限的隔离存储，本方案默认不启用该存储。

`SystemicPermanentFailure` 不执行二分或无休止重试。写入器把 admission 原子转为 `Faulted`、使 readiness 失败并暂停消费，但不关闭底层队列；当前批次和队列中已有记录只在进程内保留。运维修复 schema、权限或配置后，通过仅限本机管理命令或进程控制信号显式触发 `resumeAfterFault()`；该操作先执行 schema、权限和试写探测，成功后在同一生命周期锁内转回 `Accepting` 并唤醒写入器，失败则保持 `Faulted`。liveness 在 faulted 期间保持成功，部署系统不能因 readiness 失败自动重启进程而丢失队列。实际停机从 `Faulted` 转入 `Draining` 并关闭底层队列；若故障在截止时间内仍未修复，待写记录按尽力而为语义报告并丢弃。

新增稳定错误码：

| 数值 | 名称 | HTTP | 语义 |
|---:|---|---:|---|
| 2225 | `BEHAVIOR_EVENT_QUEUE_FULL` | 503 | 内存队列已达到配置容量，本次事件未被接受，可稍后重试 |
| 2226 | `BEHAVIOR_EVENT_QUEUE_CLOSED` | 503 | admission 处于 `Faulted`、`Draining`、`Stopped` 或写入器未运行，本次事件未被接受 |

队列满或关闭属于容量和生命周期状态，不使用 `2211 / RATE_LIMITED`，也不复用数据库写入错误。异步批次写入发生在 `202` 之后，失败只进入内部日志、指标和健康状态，不能再通过原 HTTP 请求返回。现有 `2212` 只保留给服务端可信安全审计，查询数据库失败继续使用 `2221 / DATABASE_QUERY_FAILED`。新增错误码必须同步更新 `ErrorCode.h/.cc`、REST 映射、测试和 API 文档。

## 6. API 契约

### 6.1 客户端写入

`POST /api/v1/client/behavior-events` 的请求和成功响应保持兼容：

```json
{
  "event_name": "report.view",
  "result": "success",
  "details": {"source": "dashboard"}
}
```

成功仍返回 `202` 和服务端生成的 `event_id`，但响应时事件可能尚未写入数据库。接口取消 `auth.behaviorEventsPerMinute` 及每用户分钟计数；请求体、字段、鉴权和队列容量限制继续生效。

队列成功接收后不提供单事件状态查询。进程存活期间后台写入器使用同一 `event_id` 重试；跨进程故障不承诺交付。`request_id` 只用于链路追踪，不具有唯一约束，响应丢失后的客户端重试可能产生内容相同但 ID 不同的两条事件。行为统计和下游分析必须同时容忍少量丢失和重复记录。

队列已满时返回 `503 / 2225`；admission 不处于 `Accepting` 时返回 `503 / 2226`。响应携带 `Retry-After`。这两种情况均表示事件没有被接收，客户端可以稍后重新上报。行为上报不再返回分钟限流对应的 `429 / 2211`。

### 6.2 安全审计查询

新增 `GET /api/v1/admin/audit-logs`，只查询 `security_audit_logs`。

沿用当前分页和筛选参数：`page`、`page_size`、`from`、`to`、`event_name`、`event_search`、`result`、`actor_user_id`、`actor_search`。响应继续使用 `Page<AuditLog>`，不暴露数据库 IP 和 user agent。

### 6.3 客户端事件查询

新增 `GET /api/v1/admin/behavior-events`，支持以下参数：

| 参数 | 说明 |
|---|---|
| `page`、`page_size` | 与现有分页规则相同 |
| `from`、`to` | 服务端接收时间范围 |
| `event_name`、`event_search` | 精确匹配或字面量子串搜索 |
| `result` | `success` 或 `failure` |
| `user_id`、`user_search` | 用户 UUID，或展示名／用户名／UID 子串 |

`from` 和 `to` 必须同时提供或同时省略；只提供一个时返回 `422 / 2206`。两者均省略时默认查询最近 24 小时；显式时间跨度不得超过 31 天。该限制使包含式 `event_search` 在高数据量下仍能先由时间索引缩小候选集。

响应条目定义为：

```json
{
  "id": "20000000-0000-4000-8000-000000000001",
  "user_id": "10000000-0000-4000-8000-000000000002",
  "username": "alice",
  "event_name": "report.view",
  "result": "success",
  "request_id": "report-view-001",
  "details": {"source": "dashboard"},
  "created_at": 1789636500510
}
```

### 6.4 兼容查询

`GET /api/v1/admin/user-logs` 在 v1 生命周期内保留，聚合两张新表和尚未迁移的 `user_logs`。兼容查询以新表记录为准，双写和已回填的遗留行通过相同 UUID 排除：先合并两张新表，再合并 `user_logs` 中 ID 不存在于任一新表的行。total、筛选和分页都在该去重结果上计算，排序仍为 `created_at DESC, id ASC`。

响应增加以下只读字段：

```json
{"source": "security_audit"}
```

允许值为 `security_audit`、`client_behavior`、`legacy_unknown`。客户端行为记录在兼容 DTO 中将 `user_id` 映射到 `actor_user_id` 和 `target_user_id`。

OpenAPI 将该接口标记为 deprecated，并指向两个新查询接口。v1 不删除路径；只在下一个 API 主版本删除，避免现有 Admin 或外部客户端静默丢失行为事件。

## 7. 权限与前端

在 `Capability` 枚举末尾追加 `BehaviorRead`，稳定字符串为 `behavior.read`。`admin` 和 `super_admin` 默认拥有该能力；两个新查询接口分别要求 `audit.read` 和 `behavior.read`。枚举必须追加，不能插入已有成员之间改变现有数值。

兼容接口 `/admin/user-logs` 是 v1 的明确例外：继续要求原有 `audit.read` 并返回两类数据，因为当前接口已经公开这两类记录。不能在 v1 中新增 `behavior.read` 必选条件或按能力裁剪结果，否则会改变既有客户端的授权和分页语义。该例外随兼容接口在 v2 一起删除。

Admin 的 `/logs` 页面调整为两个页签：

| 页签 | 默认 | API | 展示规则 |
|---|---:|---|---|
| 安全审计 | 是 | `/admin/audit-logs` | 显示已配置中文事件名和原始代码 |
| 用户行为 | 否 | `/admin/behavior-events` | 以客户端原始事件名为主，不标记为安全事实 |

两个页签分别维护筛选条件、加载状态和分页，切换页签不复用上一页签的查询结果。前端新增 `BehaviorEventRecord` 类型；`AuditLog` 不再承担客户端事件模型。

## 8. 历史数据迁移与发布顺序

### 8.1 第一阶段：建表与兼容双写

1. 发布 Migration 4，确认两张空表和索引创建成功。
2. 发布兼容版本：服务端审计同步写 `security_audit_logs` 和 `user_logs`；后台行为事件写入器按批次写 `client_behavior_events` 和 `user_logs`。同一逻辑事件在两表中复用同一个 UUID。
3. 每类双写位于各自同一事务，任一目标写入失败则整笔业务事务或整个行为批次回滚，避免两份记录出现不一致。行为批次失败后保留相同 ID 重试。
4. 新接口读取新表；旧接口按“新表优先、遗留表反连接排除相同 UUID”的规则聚合，任何事件最多返回一次。

双写仅维持一个发布周期，用于旧版本回滚和滚动发布兼容，不作为长期架构。

### 8.2 第二阶段：历史回填

当前实现的服务端事件全部使用 `auth.*` 或 `user.*`，客户端接口拒绝这两个前缀。回填前必须运行校验查询并冻结该约束测试。

历史分类规则：

- `auth.*`、`user.*` 写入 `security_audit_logs`；
- 其他事件仅在 `actor_user_id` 非空、`actor_user_id = target_user_id` 且结果为 `success/failure` 时写入 `client_behavior_events`；
- 不满足任一规则的记录不自动迁移，保留在 `user_logs`，来源标记为 `legacy_unknown`，由人工复核。

回填使用原 UUID 作为目标主键并支持重复执行。执行 `INSERT IGNORE ... SELECT` 前必须先完成无效行检查；执行后检查 warnings、源记录数、目标新增数和未分类数，不能依靠 `IGNORE` 隐藏数据错误。

历史客户端事件回填时令 `created_at` 和 `persisted_at` 都等于原 `user_logs.created_at`，避免把回填日期误报为排队延迟。兼容双写期间，后台写入器向新旧两表显式写入同一个接收时间；不能让遗留表使用批次提交时间覆盖事件接收时间。

### 8.3 第三阶段：停止双写

满足以下条件后停止写入 `user_logs`：

- 所有服务实例都已升级；
- 新旧表分类数量与抽样内容一致；
- 新查询接口和 Admin 页面验证通过；
- 审计业务事务回滚测试通过；
- 已验证可以回滚到兼容双写版本。

停止双写后，`user_logs` 进入只读遗留状态。兼容 API 继续查询它，直到未分类记录处理完毕。

### 8.4 第四阶段：停止读取遗留表

完成全部可分类数据回填并确认 `legacy_unknown` 为零后，先发布一个仍保留 v1 兼容接口、但兼容接口只聚合两张新表的版本。所有实例升级后，确认运行查询不再引用 `user_logs`，并完成该版本的应用回滚演练。此阶段不执行删除 DDL。

### 8.5 第五阶段：删除遗留表

至少等待 180 天，完成数据库备份、恢复演练、兼容接口调用方确认，并确认所有实例都已运行“不读取 `user_logs`”版本后，再通过单独审核的 migration 删除 `user_logs`。删除不得与建表、回填、停止双写或停止遗留读取放在同一发布中。

## 9. 保留、清理与监控

新增配置建议：

```yaml
logs:
  auditRetentionDays: 180
  behaviorRetentionDays: 30
  cleanupBatchSize: 5000
telemetry:
  queueCapacity: 10000
  batchSize: 200
  flushIntervalMs: 200
  minCommitIntervalMs: 200
  retryInitialMs: 500
  retryMaxMs: 10000
  databaseOperationTimeoutMs: 5000
  shutdownFlushTimeoutMs: 30000
  retryAfterSeconds: 1
```

上述容量、批量、保留天数和时间配置都必须是非零正值，并满足 `batchSize <= queueCapacity`、`retryInitialMs <= retryMaxMs`、`minCommitIntervalMs <= flushIntervalMs`、`databaseOperationTimeoutMs <= shutdownFlushTimeoutMs`。任一约束不满足时启动失败，不能在运行期静默修正。单条 details 上限为 4096 字节，内存估算按 `queueCapacity + batchSize` 条记录计算，并计入固定字段和容器开销。默认配置下单实例最多约 5 个事件写事务/秒，每批最多 200 条，即理论落库上限约 1000 条/秒。多实例部署时该限制按实例生效，总数据库写入上限是各实例之和；需要全局严格限速时必须引入共享消息代理或统一写入服务。

`flushIntervalMs` 是数据库健康且不存在更早失败批次时，首条事件进入空批次到发起提交的最长组批等待；`minCommitIntervalMs` 是两个批次成功提交之间的最小间隔。两者必须分别实现，不能在队列积压时通过立即连续提交绕过数据库写入限制。失败重试从 `retryInitialMs` 指数增长至 `retryMaxMs`，重试等待不消耗新的批次，并使用可被停机信号和单调时钟截止点唤醒的条件变量，不能用不可中断的 `sleep`。

启动顺序为数据库和 migration、行为写入器、HTTP transport；写入器启动失败时服务不得进入 ready。停机顺序为停止 HTTP 接入并等待在途 handler 完成、关闭队列、在 `shutdownFlushTimeoutMs` 内排空，然后停止数据库。排空开始时用单调时钟生成绝对截止点；每次尝试的数据库截止点取排空截止点和 `now + databaseOperationTimeoutMs` 的较早者，剩余时间不足完成一次受控尝试时不再启动新事务。

实现阶段必须增加 deadline-aware 的数据库调用，不能仅在写入器外层等待 30 秒：连接池执行槽和连接获取改为 `wait_until(deadline)`；连接或重连超时取配置值和剩余时间的较小值；事务锁等待、网络读写、批量 `INSERT` 和 `COMMIT` 都由驱动超时或可取消机制限制在同一绝对截止点内。达到截止点的连接必须从池中丢弃；`COMMIT` 已发送但未确认时记为 `CommitResultUnknown`，其余只有在确认未提交时才能记为 `RetryableFailure`。启动配置校验必须确认有效的连接、锁等待、读写和语句超时均不大于 `databaseOperationTimeoutMs`，底层驱动不能满足该约束时写入器不得进入 ready。

排空结果必须区分 clean、超时且确定未提交、存在未决提交。只有队列为空、消费者本地批次为空且没有尚未通过幂等重试消解的未知提交时才能报告 clean。截止时间到达后记录队列剩余数、本地批次数、最老事件年龄、确定丢弃数和未决提交批次数，再允许进程退出；不能把超时退出记为排空成功，也不得在数据库先停止后才尝试排空。

清理由受控 maintenance 命令和独立数据库身份执行；应用运行账号继续不具备删除审计数据的权限。清理按 `created_at` 和固定批量执行，避免一次大事务长期持锁。客户端事件清理和审计清理都要产生一条新的服务端审计，例如 `user.behavior_events.purged`，记录截止时间和删除数量，不记录被删 details。

兼容期内清理任一新表时，maintenance 命令必须在同一事务中按 UUID 集合删除目标表记录和 `user_logs` 中对应的双写副本，然后提交清理审计。安全审计按 180 天截止时间同步清理 `security_audit_logs` 与其遗留副本，客户端事件按 30 天截止时间同步清理 `client_behavior_events` 与其遗留副本。不能先删除新表记录而保留遗留副本，否则兼容查询会让已过期记录重新出现。未完成分类的 `legacy_unknown` 不自动删除，必须人工确认后处理。

至少增加以下监控：

- 两张表的行数、数据大小和每日增长量；
- 安全审计写入失败率和恢复事件；
- 队列当前深度、容量、高水位、最老事件年龄和 2225/2226 拒绝次数；
- 批次大小、提交频率、提交耗时、重试次数、排队延迟和停机丢弃量；
- 五类批次结果、坏记录隔离数、systemic fault 与恢复尝试次数、当前 admission 状态、提交结果未知累计次数、当前未决提交数和非 clean 排空次数；
- 查询 P95/P99 延迟；
- 清理批次耗时、删除数量和失败次数；
- `legacy_unknown` 剩余数量。

初期不引入 MySQL 分区。先依据真实增长量和查询计划决定是否按月分区，避免在缺少容量证据时增加迁移和外键约束复杂度。

## 10. 测试与验收

### 10.1 数据库和仓储

- `embeddedMigrations()` 包含 Migration 4，前三个 checksum 不变，新 checksum 与 SQL 一致；
- 审计 `append()` 和事件 `appendBatch()` 只写各自目标表，参数绑定覆盖所有字段；
- 批次事务全部成功或全部回滚；提交结果不确定时按相同 UUID 重试且不产生重复行；
- 相同 UUID 和相同不可变内容按 `Committed` 收敛；任一不可变字段不同则返回 `RecordPermanentFailure` 且不覆盖原记录；
- `created_at` 保持 HTTP 接收时间，`persisted_at` 反映首次成功执行 `INSERT` 的时间且幂等重试不更新；提交耗时使用独立指标；
- 默认时间倒序分页使用 `(created_at, id)` 稳定排序；
- 精确事件、时间、结果和用户筛选的 total 与 items 使用相同条件；
- details 超过 ORM 单次安全绑定大小时仍按既有分块读取策略正确返回；
- 回填脚本重复运行不产生重复记录，并明确报告未分类行；
- 兼容查询面对相同 UUID 的双写记录只返回一条，total 与 items 使用同一去重集合；
- 30 天行为清理和 180 天审计清理都在同一事务删除新表记录及其遗留双写副本，清理后兼容查询不会重新显示该记录。

### 10.2 事务和错误码

- 用户业务写入成功但审计写入失败时，用户变更和会话撤销整体回滚，返回 2212；
- 登录失败和鉴权拒绝的独立审计提交后返回原业务错误，独立审计失败返回 2212；
- 行为接口不再执行分钟限流，突发请求在队列容量内不返回 429；
- 队列满返回 2225，队列关闭返回 2226，两者都不携带内部诊断文本；
- 返回 202 后的批次失败在后台重试并上报健康状态，不尝试向已结束的 HTTP 请求返回错误；
- 客户端超时重试允许产生不同 ID 的重复事件，测试不得假设 request ID 幂等；
- 已确定必须审计的结果在连接、事务或写入失败时统一返回 2212；一般业务数据库失败仍保留原数据库错误；
- 数据库异常和第三方诊断文本不进入 API 响应；
- 已有稳定错误码在 Controller、Service 和 Repository 之间保持不变。

### 10.3 API 和权限

- 两个新查询接口只返回所属数据类型；
- `audit.read` 和 `behavior.read` 分别生效，operator/engineer 均不能调用管理查询；
- v1 兼容接口继续只要求 `audit.read`，不按 `behavior.read` 裁剪 items 或 total；
- 行为上报仍拒绝 `auth.*`、`user.*`，且不能提交 user ID；
- 202 仅在事件成功入队后返回；队列拒绝的事件不返回 event ID；
- 行为查询缺少单侧时间边界或跨度超过 31 天时返回 2206；
- 兼容接口正确返回 `source`，分页 total 与筛选结果一致；
- OpenAPI、静态 `openapi.json`、Markdown 接口文档和实际路由一致。

### 10.4 Admin Web

- 默认进入安全审计页签；
- 页签切换、独立筛选、分页和详情展示正确；
- 行为事件不会显示为可信中文安全事件；
- 现有 `/logs` 路由和导航入口保持有效；
- E2E mock 和请求断言改为两个新接口。

### 10.5 队列、批处理与生命周期

- `BlockingQueue::try_push()` 在有空间时返回 `Pushed`，在满或关闭时分别返回 `Full`、`Closed`，不能阻塞 HTTP 线程；
- 单消费者按 `batchSize` 组批，低流量事件不晚于 `flushIntervalMs` 发起提交；
- 队列持续积压时仍遵守 `minCommitIntervalMs`，测试使用可控时钟或调度点，不能依赖宽松 sleep；
- `RetryableFailure` 和 `CommitResultUnknown` 保留原 UUID，使用可中断的有上限指数退避，并在重试后分别收敛为一次写入；
- `RecordPermanentFailure` 对多条批次执行有序二分，隔离单条坏记录后继续处理，日志只包含事件 ID 和分类；
- `SystemicPermanentFailure` 转入 `Faulted`、暂停消费并使 readiness 失败，但不关闭底层队列；修复探测成功后 `resumeAfterFault()` 恢复消费和接入；
- `Accepting -> Faulted -> Accepting` 与 `Accepting/Faulted -> Draining -> Stopped` 状态迁移无入队竞态，底层队列只在 `Draining` 时关闭；
- 任一数值为零，或违反批次/容量、重试上下限、提交/刷新间隔、数据库/停机超时关系时，配置校验拒绝启动；
- 正常停机先停止接入并等待 handler，再关闭和排空队列；排空成功不丢事件，截止时间到达时分别记录确定未提交数和未决提交数；
- 连接池等待、连接/重连、锁等待、`INSERT` 和 `COMMIT` 都服从注入的单调时钟截止点，超时连接不会回到池中；
- 停机信号能够立即打断重试等待，数据库不可用时写入器仍在 `shutdownFlushTimeoutMs` 内返回非 clean 结果；
- 回滚编排只有在所有实例 clean 排空后才建立最终水位；任一实例超时或存在未知提交时拒绝补写和旧版本启动；
- 写入器未运行或已经关闭时 readiness 不成功，竞态请求稳定返回 2226；
- 队列容量、高水位、重试和排队延迟指标与实际状态一致。

## 11. 回滚方案

兼容双写版本支持应用回滚：旧版本仍可从 `user_logs` 读取完整新增数据。回滚时保留两张新表，不执行反向 DDL；重新部署兼容版本后继续双写。

停止双写时必须记录数据库时间水位、发布版本和最后一次双写成功的 request ID。停止双写后如需回滚，必须按以下顺序执行：

1. 从负载均衡摘除全部实例并停止新入口流量，等待所有在途 HTTP handler 和同步审计事务结束。
2. 关闭每个实例的行为事件队列并触发排空；逐实例确认队列、本地批次和未决提交数都为零。
3. 只有全部实例报告 clean 后，才开启数据库一致性快照，记录数据库时间、发布版本、两张新表的行数及各自最大时间键作为最终水位证据；这些时间键只用于核验，不作为补写选择条件。
4. 在同一静止数据集上按 UUID 扫描两张新表的全部可见记录，将 `user_logs` 缺失项幂等补写，并校验分类型数量、最大时间键和抽样内容。补写不能依赖 `persisted_at <= 水位时间`，因为 `persisted_at` 是 `INSERT` 执行时间而不是提交完成时间。
5. 部署兼容双写版本，确认写入器和兼容查询 ready 后再恢复流量。

任一实例无法在截止时间内 clean 排空、仍存在未决的 `CommitResultUnknown` 批次或无法取得一致性快照时，必须中止回滚，不能建立最终水位、执行补写或启动旧版本。排除故障后从第一步重新执行。补写和校验完成前，旧版本不得对外服务；最终水位建立后也不能再启动仍运行停止双写版本的写入器，否则必须作废水位并重新排空。

遗留表删除后不再支持直接回滚到只认识 `user_logs` 的版本，只能通过数据库备份恢复或向前修复。

发布验收必须至少演练一次停止双写后的回滚流程，验证流量门禁、全实例排空、最终水位补写、数量校验和恢复顺序，并验证任一写入器排空超时或提交结果未知时回滚会拒绝继续，不能只验证兼容双写阶段的应用回滚。

删除 `user_logs` 前还必须验证兼容接口已完全切换为只读两张新表，并证明滚动发布期间旧实例不会再执行引用遗留表的 SQL。

## 12. 主要取舍

拆表增加两个仓储、两个查询接口和一次历史迁移，但获得以下长期边界：

- 安全审计来源由物理写入路径保证，不再依赖事件名前缀推断；
- 高频客户端事件不会扩大安全审计的主要查询和索引工作集；
- 两类数据可以采用不同保留、清理和容量策略；
- 错误码、权限和管理界面明确表达两类数据的不同可信语义；
- 仍保留单体服务和本地数据库事务，不引入分布式一致性成本。

当前代码已完成 Migration 4、新旧表同事务双写、历史检查与幂等回填、兼容查询 UUID 去重、独立查询 API 和权限、管理端页签、有界队列与延迟批写、数据库截止时间、未知提交幂等消解、系统性故障停写、恢复探测、保留期清理和清理审计。上线仍需在目标 MySQL 版本执行容量验证、备份恢复和停止双写后的回滚演练；这些是发布操作，不通过代码自动跳过。

维护命令使用同一制品和配置文件，执行完即退出：

```powershell
szx_admin_service --config config/config.yaml --maintenance inspect
szx_admin_service --config config/config.yaml --maintenance backfill
szx_admin_service --config config/config.yaml --maintenance purge --confirm-purge
```

`inspect` 报告可分类数量、`legacy_unknown`、缺失和内容冲突；`backfill` 获取 `szx_log_split_maintenance` advisory lock，按 `cleanupBatchSize` 分批事务写入原 UUID，冲突立即停止，重复运行幂等；`purge` 按各自保留期在同一事务删除新表记录和 `user_logs` 双写副本，并写一条新的安全审计。维护账号需要连接目标库，读取 `users/user_logs/security_audit_logs/client_behavior_events`，向两张新表插入，删除三张日志表记录，向 `security_audit_logs` 插入清理审计，以及执行 `GET_LOCK/RELEASE_LOCK`；无需用户管理和 refresh token 写权限。生产应用账号不授予日志 DELETE。

写入器进入 `Faulted` 后先修复 schema、权限或数据库故障，再向 Windows 进程发送 `SIGBREAK`，或向 POSIX 进程发送 `SIGHUP`。信号处理函数只设置原子标志，主循环执行事务、schema、权限和可回滚试写探测；探测成功才恢复 readiness 和事件接入。重复信号或非 `Faulted` 状态会记录拒绝，不会重建队列。

`user_logs` 不能在上述迁移项完成并经过一个完整审计保留窗口和备份恢复验证前删除。当前有界队列位于进程内，`202` 只承诺已接收至队列；进程故障下的可靠投递不在本阶段承诺范围内。

行为接口的分钟计数和 `auth.behaviorEventsPerMinute` 不属于新契约；认证和凭据签发的 `auth.attemptsPerMinute` 保持不变。`telemetry.queueCapacity` 是内存容量和背压阈值，不是分钟限流；短时间积压由 `batchSize`、`flushIntervalMs` 和 `minCommitIntervalMs` 控制数据库写入节奏。
