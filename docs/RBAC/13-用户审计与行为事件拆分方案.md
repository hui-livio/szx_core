# 用户审计与行为事件拆分说明

- 文档状态：已完成
- 完成日期：2026-09-22
- 适用范围：`tools/szx_admin`、`tools/szx_admin/web/admin`、`docs/RBAC`

## 1. 最终架构

Admin 服务使用同一个 MySQL 数据库中的两个独立日志表：

| 数据 | 物理表 | 所有者 | 信任级别 | 默认保留期 |
|---|---|---|---|---:|
| 服务端安全审计 | `security_audit_logs` | `AUDIT` | 服务端可信 | 180 天 |
| 客户端行为事件 | `client_behavior_events` | `TELEMETRY` | 客户端非可信 | 30 天 |

安全审计与用户、密码和会话变更共用事务，审计失败时相关安全操作回滚。客户端行为事件在鉴权、校验和脱敏后进入进程内有界队列，由后台批量写入；HTTP `202` 只表示事件已接收入队。

## 2. API

- `GET /api/v1/admin/audit-logs`：查询安全审计，要求 `audit.read`。
- `GET /api/v1/admin/behavior-events`：查询客户端行为事件，要求 `behavior.read`。
- `POST /api/v1/client/behavior-events`：提交非可信客户端行为事件。

安全审计与行为事件不再通过聚合兼容接口返回。管理端日志页面直接调用对应的独立接口。

## 3. 数据库迁移

Migration 4 创建 `security_audit_logs` 和 `client_behavior_events`。Migration 5 执行：

```sql
DROP TABLE IF EXISTS user_logs;
```

运行时不再读取或写入历史日志表，也不再提供双写、兼容读取、检查或回填逻辑。已删除历史表后，旧版本应用不能直接回滚；需要回退时使用部署前数据库备份，或以前向修复方式恢复服务。

## 4. 保留期清理

维护命令只保留 `purge`：

```powershell
szx_admin_service --config config/config.yaml --maintenance purge --confirm-purge
```

命令分别按 `logs.auditRetentionDays` 和 `logs.behaviorRetentionDays` 分批删除两张当前日志表中的过期记录，并在 `security_audit_logs` 中记录清理审计。`logs.cleanupBatchSize` 控制每批数量；生产应用账号不应授予日志删除权限，维护账号需具有两张日志表的删除权限、审计写入权限以及 advisory lock 权限。

## 5. 验收要求

- `schema_migrations` 当前版本为 5，数据库中不存在历史日志表。
- 安全操作只写 `security_audit_logs`，失败时业务事务回滚。
- 客户端事件只写 `client_behavior_events`，队列满或写入器故障返回稳定错误码。
- 两个管理查询接口按各自能力鉴权，筛选、排序、分页和 total 一致。
- OpenAPI、Markdown 接口文档、Admin 前端和自动化测试均不再引用已删除的兼容接口。
- 保留期清理只处理当前两张日志表，并产生可追踪的安全审计。
