# 单项目 RABC 开发计划

## 1. 计划基线

本计划以 `01-系统设计文档.md` 至 `05-RESTful-API接口文档.md` 为范围基线，首版目标是交付一个单项目用户与权限管理服务：四个固定角色、用户启停与角色分配、JWT 登录、行为/安全审计，以及 Vue Admin 管理界面。

当前 `szx_core` 是 C++/CMake 组件库，而 RABC 设计采用 Vue 3 + TypeScript + REST API。因此建议 RABC 以独立应用（后端服务 + Admin 前端）开发，通过 HTTP API 与现有业务客户端集成；本仓库只承载需要复用的 C++ 客户端适配或协议代码，不将 Web 服务强行并入 CMake 组件。

## 2. 交付范围与不做事项

### 本期交付

- 单项目部署，不提供项目切换。
- `operator`、`engineer`、`admin`、`super_admin` 四个固定角色及能力矩阵。
- 首次部署生成超管、首次登录强制改密。
- 登录、刷新、登出、改密、锁定/禁用、用户 CRUD、角色分配、重置密码。
- Admin 用户列表/表单、日志查询、路由守卫和 401/403 统一处理。
- Client 查询当前角色与能力码，业务接口服务端二次鉴权。
- `users`、`refresh_tokens`、`user_logs` 表及迁移、索引、乐观锁。
- 自动化单元、API 集成、前端组件/端到端、安全回归测试。

### 明确不做

多项目/组织树、动态权限编辑器、权限组、数据行级权限、角色组合、项目切换器和平台管理页。

## 3. 阶段计划（建议 8 周）

| 阶段 | 周期 | 主要任务 | 交付物与出口条件 |
|---|---:|---|---|
| 0. 立项与技术决策 | 2–3 天 | 固定 libhv、ormpp、jwt-cpp；确定 `szx_crypto` 的 OpenSSL 静态构建方式、SQLite 或 PostgreSQL、部署方式、JWT 密钥管理、前端与业务 Client 的集成方式；补齐 API OpenAPI 草案 | 技术决策记录、环境矩阵、API/错误码冻结；所有阻塞决策关闭 |
| 1. 工程骨架与数据库 | 1 周 | 创建后端分层（Controller/Service/Repository/Policy）、前端 Vite 工程、迁移工具；实现 `users`、`refresh_tokens`、`user_logs`、唯一约束、索引、`version` 乐观锁 | 可重复迁移和回滚；健康检查；空库可启动；数据库约束测试通过 |
| 2. 认证与初始化 | 1 周 | Argon2id；登录/刷新令牌轮换/登出/改密；access JWT 15 分钟；禁用/锁定校验；首次超管初始化与强制改密 | `/auth/*` API 可用；令牌不落原文；登录、失败、改密、登出均写审计；认证集成测试通过 |
| 3. 用户与 Policy 核心 | 1–1.5 周 | 固定角色能力矩阵；用户列表/详情/创建/编辑；启停；角色分配；重置密码；管理员不可操作超管；不得删除最后超管；事务与版本冲突 | `/admin/users*` API 与错误码稳定；权限矩阵测试覆盖四角色及边界规则 |
| 4. 审计与 Client API | 3–4 天 | `user_logs` 追加写入和分页查询；`GET /client/me/permissions`；可信业务事件自动记录；非可信埋点 `202` 接口及限流/大小限制 | `/admin/user-logs`、Client 权限接口可用；日志不可改删；request_id 可追踪 |
| 5. Admin 前端 | 1–1.5 周 | 登录/首次改密、用户列表与表单、启禁用/重置/角色、日志页、业务首页；Pinia、路由守卫、`can()`、分页搜索、空状态、防重复提交 | 四角色菜单/入口正确；错误码可读；token 失效能清理状态并回登录页 |
| 6. 集成、测试与安全加固 | 1 周 | 接入业务 Client；CORS/CSRF（如使用 Cookie）、限流、输入校验、密码策略、敏感字段脱敏；契约、集成、E2E、并发版本冲突测试 | 测试门禁通过；安全检查无高危项；API 契约与实现一致 |
| 7. 发布与验收 | 3–4 天 | Docker/Windows 服务或目标环境部署脚本、配置模板、备份恢复、日志轮转、监控告警、迁移演练、用户手册 | 预生产验收通过；可回滚；备份恢复演练成功；发布包与运维手册签署 |

阶段 2 与阶段 3 可在数据库骨架完成后并行；阶段 5 可在 API 契约冻结后提前开发 Mock，缩短总工期。

## 4. 后端任务拆分

1. **基础设施**：配置加载、密钥/密文管理、统一响应与错误模型、request_id、参数化 SQL、事务封装、健康检查。
2. **auth**：通过 `CryptoService` 完成密码哈希校验、失败次数与锁定；由 jwt-cpp 处理 JWT 协议、由 `szx_crypto` 完成 PS256 签名/验签；refresh token 哈希存储和轮换重放检测。
3. **user**：身份标识二选一校验、唯一性冲突、状态机、角色及超管保护规则、分页搜索。
4. **policy**：集中维护能力矩阵和中间件/服务级鉴权；禁止从客户端接受 capabilities 作为授权依据。
5. **behavior-log**：安全事件可靠落库；业务事件区分可信服务端事件和不可信前端埋点；查询过滤与分页。
6. **API 契约**：冻结 `/api/v1` 路径、状态码、错误码（含 `USER_IDENTITY_ONE_OF_REQUIRED`、`CONFLICT_VERSION` 等）和示例，生成客户端类型/Mock。

## 5. 前端任务拆分

- Axios 实例：自动附加 access token、刷新并发合并、401/403/429 统一提示。
- Pinia：保存当前用户、单角色、capabilities；登出或失效时彻底清理。
- 路由：`/login`、`/users`、`/logs`、`/home`；管理员默认 `/users`，其他角色默认 `/home`。
- 用户表单：`uid` 与 `username` 互斥且提交前校验；角色单选；编辑使用 `version`。
- 可用性：分页、搜索、空列表引导、加载态、重复提交保护、禁用用户提示。

## 6. 验收与质量门禁

### 关键验收场景

- 新部署仅能使用初始化超管；首次登录必须改密，改密前不能访问业务页面。
- admin 可管理普通用户但不能创建/修改超管；仅 super_admin 可分配管理员/超管。
- 任意角色访问越权 API 返回 `403 FORBIDDEN`；未登录/过期令牌返回 `401`。
- 禁止禁用或删除最后一个超管；并发编辑产生 `409 CONFLICT_VERSION`。
- 角色变更后，Client 权限接口按最新角色返回；旧 token 不绕过服务端 Policy。
- 登录、改密、角色变更、禁用和关键业务事件均可按 `request_id` 在日志中追踪。

### 测试门禁

- 后端：Policy/Service/Repository 单元测试，API 契约和数据库集成测试，认证与并发安全测试。
- 前端：表单/权限指令组件测试，路由守卫测试，至少覆盖登录到用户管理的 E2E 主流程。
- 安全：密码哈希参数检查、refresh 重放、暴力登录限流、越权矩阵、日志敏感信息扫描。
- 发布前：迁移从空库和上一版本升级均成功，备份恢复和回滚演练成功。

## 7. 风险、依赖与待决策

| 项目 | 影响 | 应对 |
|---|---|---|
| 后端技术栈未在文档指定 | 影响工程初始化和工期 | 阶段 0 冻结框架、ORM/SQL 方案及团队负责人 |
| SQLite/PostgreSQL 未定 | 影响并发、部署和迁移 | 开发可用 SQLite，预生产优先验证 PostgreSQL；最终以部署约束决策 |
| 现有 Client 尚无统一鉴权接入 | 影响业务接口保护 | 先交付 `/client/me/permissions` 与 SDK/适配层，再逐个接入业务 API |
| JWT 密钥和初始超管凭据管理不当 | 高安全风险 | 使用部署密钥注入/密钥库，禁止写入仓库和日志；强制首次改密 |
| 日志量增长 | 影响存储和查询 | 索引、分页、轮转/归档策略，关键安全日志保留期在阶段 0 确认 |
| 文档与实现漂移 | 造成联调失败 | OpenAPI 作为契约源，CI 中执行契约测试并同步示例 |

## 8. 建议里程碑与责任分工

- **M1（第 1 周末）**：技术决策、数据库迁移、服务可启动。
- **M2（第 3 周末）**：认证和用户管理 API 完成，后端权限矩阵稳定。
- **M3（第 5 周末）**：Admin 主流程和 Client 权限接口完成，可联调。
- **M4（第 7 周末）**：测试、安全、业务 Client 接入完成，进入预生产。
- **M5（第 8 周）**：部署演练、验收、发布。

建议至少配置：后端负责人 1 名、前端负责人 1 名、业务 Client/集成负责人 1 名、测试/安全兼职 1 名；每个里程碑以可运行环境和验收场景作为完成定义，而不是仅以代码提交量衡量。
