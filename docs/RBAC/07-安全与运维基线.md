# RBAC 安全与运维基线

## 1. 密码与账户

- 密码使用 Argon2id；版本、内存、迭代次数、并行度和输出长度由部署配置冻结，并保留升级/re-hash 判断。
- 第一阶段默认 Argon2id 参数为 memory=64 MiB、iterations=3、parallelism=1、salt=16 bytes、output=32 bytes；生产发布前可提高但不得降低，参数变更触发 re-hash。
- 密码长度为 12～128 个 Unicode 字符；禁止记录密码，不强制脆弱的字符类别规则。登录失败使用统一错误响应；同一账号 15 分钟内失败 5 次进入 locked 15 分钟，同一 IP 每分钟最多 60 次登录请求。
- 初始超管通过一次性 bootstrap 创建，不使用固定默认密码；首次登录必须改密。
- disabled/locked 账户拒绝登录和受保护请求；解锁、改密和重置密码都写入审计。
- 密码不得出现在 URL、日志、异常、审计 details、前端状态或 telemetry 中。

## 2. Token 与密钥

- access JWT 有效期 15 分钟，固定使用 PS256；`iss` 和 `aud` 分别来自部署配置 `RBAC_JWT_ISSUER`/`RBAC_JWT_AUDIENCE`，客户端不能指定或覆盖。
- JWT 至少包含 `iss`、`aud`、`sub`、`jti`、`iat`、`nbf`、`exp` 和 `authz_version`；JWT header 必须包含 `kid`，用于密钥轮换。
- refresh token 使用高强度随机值，数据库只保存 hash；每次使用后轮换。
- refresh token 重放撤销整个 token family，并生成安全审计事件。
- 改密、角色变更、禁用和解锁统一通过 `authz_version` 立即影响旧 token；refresh family 另外执行会话撤销。
- 签名密钥不提交到代码仓库或日志，部署使用受控密钥来源；轮换时保留明确的旧密钥验证窗口。

## 3. 审计与日志

审计记录至少包含：

```text
actor_user_id, target_user_id, event_name, result,
request_id, ip, user_agent, created_at, details_json
```

审计事件包括登录成功/失败、改密、重置密码、refresh 轮换/重放、创建/编辑/启停用户、角色变更、锁定/解锁、权限拒绝和关键业务操作。

安全审计必须可靠落库。若审计写入失败，相关安全写操作必须回滚或返回明确失败；不能只记录到普通应用日志后继续返回成功。

Client 提交的 behavior event 只用于非可信业务 telemetry，不能作为安全审计事实来源。日志查询需要分页、时间范围和事件过滤，并执行脱敏。

## 4. 部署与网络

- 所有 API 使用 HTTPS；反向代理、CORS、安全响应头和请求体大小限制写入部署配置。
- access token 通过 Authorization header 传递；浏览器 refresh token 使用 HttpOnly、Secure、SameSite Cookie，所有 Cookie 写操作配置 CSRF token；禁止无保护 localStorage。
- 数据库账号遵循最小权限；应用运行账号不能直接修改或删除审计表。
- 数据库连接、密钥、bootstrap 凭据和限流参数通过部署密钥管理，不写入仓库。
- 记录应用版本、migration 版本、JWT key id、数据库版本和依赖 SBOM，便于回滚。
- 审计日志默认保留 180 天；保留期、归档位置和删除授权由运维配置冻结，任何清理操作必须单独审计。

## 5. 监控、备份与回滚

至少监控：登录失败率、账户锁定数、403/429 比例、refresh 重放、审计写入失败、数据库连接失败和 migration 失败。

发布前完成：

1. 数据库备份与恢复演练；
2. migration 向前/回滚演练；
3. 密钥轮换和旧 token 验证窗口演练；
4. 旧版本制品回滚演练；
5. 审计日志保留周期和访问权限确认。

所有部署和回滚操作必须关联 request/release 标识并写入运维审计。
