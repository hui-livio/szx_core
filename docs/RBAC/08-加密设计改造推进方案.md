# 加密设计改造推进方案

## 1. 目标与约束

本方案用于当前 RBAC 实施分支，将当前加密模块改造成分层结构：

```text
szx_crypto（密码学原语）
    └── third_party/OpenSSL（OpenSSL 3.5.8 LTS 预编译 SDK）
CryptoService（业务加密门面）
    └── 依赖 szx_crypto，返回统一 Result/错误码
RBAC JwtService（令牌协议适配）
    └── 应用层依赖 CryptoService；jwt-cpp 负责 JWT/JWS 协议
```

约束：

- 公共头文件不得暴露 OpenSSL、jwt-cpp 或其他三方库类型。
- 业务边界、DLL 导出、回调和线程入口不得让异常逃逸。
- 保持现有 `szx::crypto` / `szx::crypto_service` API 的行为兼容；破坏性变更必须显式版本化。
- OpenSSL 仅由 `szx_crypto` 封装和链接；`CryptoService`、RBAC 服务和其他应用层只依赖 `szx::crypto`/`szx::crypto_service`。
- JWT 固定使用 PS256（RSA-PSS-SHA256），禁止由客户端指定算法。

OpenSSL 不作为本仓库的 CMake 子项目构建。当前固定使用 `third_party/OpenSSL` 中的 OpenSSL 3.5.8 LTS Windows x64 预编译 SDK，制品从维护者本机 `C:\Program Files\OpenSSL-Win64` 安装目录提取。仓库保留完整头文件、`MD`/`MT` Release 静态库和动态导入库，并只保留 `libcrypto-3-x64.dll`、`libssl-3-x64.dll` 两个核心运行时 DLL。版本、来源和制品 SHA-256 记录在 `third_party/OpenSSL/manifest.json`。

## 2. 当前基线与差距

当前 `components/crypto/CMakeLists.txt` 通过仓库自有 `szx_find_openssl.cmake` 链接 `SZX::OpenSSL::Crypto`，`szx_crypto` 保持 shared target；默认选择 `STATIC` + `MD`，可显式切换 `SHARED` 或 `MT`。查找过程不使用系统安装版本，并校验 Windows MSVC x64、最低版本 3.5.8 和所选制品是否完整。实现文件包含 AES-GCM、Base64、Fernet、Hash、PBKDF2、RSA、Random、SecureBytes 和 Argon2id。`components/crypto_service` 通过 `PUBLIC szx::crypto` 提供业务门面。

需要补齐的能力：

1. 将现有 OpenSSL 集成抽取为可校验架构/配置的 CMake helper，并补齐 provider 适配。
2. OpenSSL 实现与现有 API 行为的兼容测试。
3. Argon2id 密码哈希/验证能力（使用当前 OpenSSL provider 的 `ARGON2ID` EVP_KDF 实现，并隐藏在 `szx_crypto` 内）。
4. `CryptoService` 的密码哈希、`kid` 计算、错误码和能力声明。
5. RBAC 所需的 jwt-cpp 适配层（不放入 `szx_crypto` 公共 API）。

## 3. 分阶段实施

### 阶段 0：冻结接口与构建策略

- 建立 OpenSSL 私有实现与 RAII 封装；不保留运行时多 backend 抽象。
- 冻结 OpenSSL 主版本、静态构建参数、x64/Debug/Release、`/MT` 或 `/MD` 选择。
- 决定 `szx_crypto` 保持 shared 还是增加 static 变体；优先保持现有 shared target 名称不变。
- 为 OpenSSL、Argon2 实现和 jwt-cpp 登记版本、许可证、源码来源和 SBOM 信息。

出口条件：新增技术决策记录；没有公共头文件依赖 OpenSSL；CI 能定位固定的 OpenSSL 安装/构建产物。

### 阶段 1：OpenSSL 链接骨架

- 在 `components/crypto/CMakeLists.txt` 默认使用 OpenSSL 静态 SDK，不增加 CNG 回退选项；动态模式仅用于明确需要 DLL 部署的构建。
- 不把 OpenSSL 源码作为 CMake 子目录；使用外部预编译 SDK，并通过 `SZX_OPENSSL_ROOT` 指定根目录。
- `cmake/szx_find_openssl.cmake` 根据 `SZX_OPENSSL_ROOT` 创建 `SZX::OpenSSL::Crypto`/`SZX::OpenSSL::SSL` imported targets，校验版本、头文件、库文件、运行时 DLL、架构和 MSVC 运行库配置。
- `szx_crypto` 只链接 `SZX::OpenSSL::Crypto`；只有确实需要 TLS 的目标才链接 `SZX::OpenSSL::SSL`。静态库通过明确的 toolchain 配置选择，禁止全局修改链接器标志。
- 将 OpenSSL 链接保持在 `szx_crypto PRIVATE`；不要将 OpenSSL include 目录或库传播给消费者。
- Windows 静态链接所需系统库由 target 精确声明，并用 `dumpbin /dependents` 检查最终 DLL/EXE。
- 新增 `openssl/` 私有适配目录和 RAII wrapper，统一释放 `EVP_MD_CTX`、`EVP_PKEY`、`EVP_CIPHER_CTX` 等对象。

出口条件：`szx_crypto` 可使用 OpenSSL 静态 SDK 构建；安装树不泄漏 OpenSSL 私有头文件。

当前目录结构：

```text
third_party/OpenSSL/
  bin/libcrypto-3-x64.dll
  bin/libssl-3-x64.dll
  include/openssl/
  lib/VC/x64/MD/{libcrypto,libssl}{,_static}.lib
  lib/VC/x64/MT/{libcrypto,libssl}{,_static}.lib
  LICENSE.txt
  manifest.json
```

`manifest.json` 记录 OpenSSL 版本、来源、架构、`MD`/`MT`、Release 配置、许可证和核心制品 SHA-256。仓库不保留 `MDd`/`MTd` 调试库、`.pdb`、`.exp`、测试、示例、命令行工具或非核心 provider DLL；Debug 工程同样链接 Release OpenSSL 库。

### 阶段 2：迁移和补齐密码学原语

按风险从低到高迁移：

1. Base64/Base64URL、随机数、Hash/HMAC。
2. AES-256-GCM 与 SecureBytes。
3. RSA-OAEP-SHA256、RSA-PSS-SHA256。
4. PBKDF2 兼容实现。
5. Argon2id 哈希、验证和 rehash 判断。

每个能力通过现有公共 API 返回 `Result<T>`；第三方错误在边界映射到 `InvalidArgument`、`AuthenticationFailed`、`ProviderFailure`、`Unsupported` 等稳定错误码。密码、私钥、token 原文不得进入日志或错误消息。

出口条件：每个算法均有固定向量测试、错误输入测试、失败清理测试；OpenSSL 实现与既有 API 的结果和错误语义完成验证。

### 阶段 3：扩展 CryptoService 业务能力

- 已增加 Argon2id PHC 哈希/验证、PS256 `signPs256/verifyPs256` 和 RSA 公钥 `publicKeyId` 门面；RBAC 不直接访问 `szx_crypto` 原语。
- JWT 适配层仍由阶段 4 实现，使用上述 PS256 门面组装 signing input。
- JWT 门面必须支持 `iss/aud/sub/jti/iat/nbf/exp/authz_version` claims 和 `kid` header；不得让 RBAC 直接依赖 jwt-cpp 类型。
- 完善 `CryptoCapabilities`，区分算法可用性与 backend 类型，避免客户端依赖实现细节。
- 明确定义密钥输入格式、密钥 ID/版本、轮换和失效策略。
- 为所有公开方法补齐异常捕获和稳定错误码；`FakeCryptoService` 同步扩展用于业务测试。

出口条件：RBAC 只依赖 `szx::crypto_service`；公共头文件不出现 OpenSSL/jwt-cpp；服务错误码可映射到 API 错误响应。当前 `kid` 为规范 DER 公钥 SHA-256 小写十六进制；密钥版本、轮换窗口和失效策略由阶段 4 的密钥仓储负责，CryptoService 不持有私钥或轮换状态。

### 阶段 4：jwt-cpp Token 适配

- 在 RBAC 服务内部新增 `JwtService`，jwt-cpp 只作为实现依赖。
- 固定 PS256、issuer、audience、15 分钟 access token、`iat/nbf/exp/jti`。
- access token 还必须携带 `authz_version`，refresh token 不使用 JWT 格式且只保存 hash。
- 将 JWT signing input 交给 `CryptoService`/`szx_crypto`；禁止 jwt-cpp 的异常或类型穿透 Service API。
- 实现密钥版本选择、旧密钥验证窗口和轮换测试。
- refresh token 使用高强度随机值，数据库只保存 hash；refresh 重放必须撤销 token 链。

出口条件：通过 RFC 兼容 token、篡改 token、过期 token、错误算法、错误 issuer/audience、时钟偏差和密钥轮换测试。

### 阶段 5：切换、发布与回滚

- 先在 CI 和测试环境验证 OpenSSL 静态构建，再切换生产制品；不保留 CNG 运行时回退。
- 对比性能、二进制依赖、启动行为和内存清理；记录 OpenSSL 静态库版本及构建哈希。
- 通过版本化制品切换；出现算法结果或稳定性问题时回退到上一个 OpenSSL 提交，不改变上层 API。
- 发布包包含许可证、NOTICE、SBOM、OpenSSL 构建参数和安全升级流程。

出口条件：全量测试通过，依赖审计无高危项，回滚演练成功。

## 4. 建议的代码布局

```text
components/crypto/
  include/SzxCrypto/              # 稳定公共 API
  src/openssl/                    # OpenSSL 实现与 RAII wrapper
  src/backend/                    # provider 选择与公共实现适配
components/crypto_service/
  include/SzxCryptoService/       # 业务门面 API
  src/                            # 业务校验、错误映射、密钥策略
  RBAC/szx_admin/
  src/auth/JwtService.*           # jwt-cpp 适配，仅服务私有
```

## 5. 测试门禁

- 算法测试：AES-GCM、RSA-OAEP、RSA-PSS、Hash/HMAC、Base64、随机数、Argon2id。
- 兼容测试：OpenSSL 对公共 API 的结果、失败类型和边界行为。
- 安全测试：错误密钥、篡改密文、签名伪造、算法混淆、短/超长输入、敏感数据日志扫描。
- 资源测试：OpenSSL context/key/cipher 的 RAII 释放、异常路径无泄漏、线程安全和并发调用。
- Service 测试：所有第三方异常均转换为稳定 `Result<T>`；无异常穿透 DLL/业务边界。
- Token 测试：PS256、claims、过期、撤销、refresh 轮换、密钥轮换和重放检测。

## 6. 提交顺序与回滚点

建议按以下提交拆分，便于审查和回退：

1. `crypto: add backend abstraction and OpenSSL build option`
2. `crypto: add OpenSSL RAII wrappers and primitive implementations`
3. `crypto: add Argon2id password hashing`
4. `crypto-service: expose business crypto capabilities`
5. `rbac: add jwt-cpp token adapter`
6. `crypto: switch default backend after compatibility gate`

每一步都应保持可构建、可测试；阶段 1–4 失败时回退到上一个 OpenSSL 提交，阶段 4 失败时不影响非 JWT 业务能力。
