# RABC C++ 三方库评审

## 1. 结论

RABC 设计本身是 Vue + REST API，C++ 并不是前端或后端的硬性要求。若后端必须采用 C++，建议将其作为独立服务工程，不直接并入 `szx_core` 的组件目标。

已确认的首选组合：

- HTTP/REST：libhv
- JSON：复用 `szx::common` 已封装的 nlohmann/json
- 数据库访问：ormpp；首版使用 SQLite 后端，生产并发或多实例部署再评估 PostgreSQL 后端
- 密码哈希、随机数和令牌密钥材料：由 `szx::crypto` 提供；Argon2id 作为其新增能力，底层实现单独评审
- JWT：由 RABC 认证模块使用 jwt-cpp 处理协议层；密码学原语统一经 `szx::crypto`（OpenSSL 静态库）提供，业务调用通过 `szx::crypto_service`
- 日志：复用 `szx::logger`/spdlog，或服务端独立使用固定版本 spdlog
- 测试：复用仓库 GoogleTest/GMock 接入方式

不建议把 libhv、数据库驱动或 OpenSSL 直接加到 `szx_core` 其他组件的 PUBLIC 依赖中。OpenSSL 仅由 `szx_crypto` 私有封装；RABC 服务和 C++ 客户端适配应通过稳定 HTTP 契约隔离。

## 2. 依赖矩阵

| 能力 | 推荐库/方案 | 当前仓库状态 | 结论 |
|---|---|---|---|
| HTTP 服务、路由、中间件 | libhv | 未纳入 | RABC 独立服务必需；需自行实现 REST 路由、认证中间件、统一错误响应、限流和请求体限制 |
| JSON 编解码 | nlohmann/json，经 `szx::common::Serializer` | 已有 `components/common/ext/nlohmann` | 直接复用，避免服务与客户端出现两套 JSON 行为 |
| SQLite | ormpp 的 SQLite 支持 | `third_party/ormpp` 已纳入 | 单实例首选；需确认当前 CMake target、线程模式、WAL、busy timeout 和备份策略 |
| PostgreSQL | ormpp PostgreSQL backend + libpq | `third_party/ormpp` 已纳入；libpq 未纳入 | 多实例、较高并发或集中式部署时选用；作为可选构建依赖并做独立集成测试 |
| ORM/SQL | ormpp | `third_party/ormpp` 已纳入 | 统一 Repository 访问；必须确认事务、连接池、参数绑定和异常模型，不再叠加第二个 ORM |
| Argon2id 密码哈希 | `szx::crypto` 统一封装 | 当前未提供 | 必须新增 Argon2id 能力；底层实现不得泄漏到业务公共 API，哈希参数需可升级 |
| JWT 签名/校验 | jwt-cpp + RABC `JwtService` + `szx::crypto` | `szx::crypto_service` 已提供 RSA-PSS-SHA256 sign/verify 与 Base64；`szx::crypto` 当前实现为 Windows CNG | jwt-cpp 仅负责协议层；固定 PS256，适配 `szx::crypto` 的密钥格式，并补充 claims/算法白名单校验 |
| TLS | libhv/OpenSSL 或反向代理终止 TLS | 未纳入 | 生产建议由 Nginx/网关终止 TLS；服务到网关链路按部署威胁模型决定，避免把 OpenSSL 带入 szx 核心 |
| UUID | `boost::uuid`、平台实现或轻量 header-only UUID | 未纳入 | 可用 C++/平台随机源生成；不要为 UUID 单独引入大型框架，统一序列化格式 |
| 时间 | `std::chrono` + 数据库 timestamp | 无需新增 | 统一 UTC；由 Repository 负责数据库类型转换 |
| 密码/令牌随机数 | `szx::crypto` CSPRNG | 已有随机数能力 | refresh token 只存 hash，不存原文 |
| 日志 | `szx::logger` / spdlog | 已纳入 | 可复用；必须增加敏感字段脱敏和 request_id 关联约束 |
| 单元/集成测试 | GoogleTest/GMock | 已有构建辅助和第三方目录约定 | 复用现有 CMake 测试模式；服务测试可放独立工程[^4] |
| API 契约 | OpenAPI Generator/静态 OpenAPI 文件 | 未纳入 | 工具链依赖，不进入运行时；CI 做契约校验并生成 TS Client/Mock |

## 3. 关键取舍

### 3.1 libhv 的边界

libhv 负责 HTTP/HTTPS、连接和事件循环，但 RABC 所需的认证中间件、路由分组、JSON 错误模型、请求上下文、限流和审计关联需要在应用层实现。建议建立 `HttpServerAdapter`，将 libhv 类型隔离在 transport 层，Controller/Service 不直接依赖 libhv。

libhv 与 ormpp 的线程模型必须明确：HTTP 回调中不要执行可能阻塞的数据库操作或 Argon2id 哈希；使用任务线程池/工作队列，并在回调边界捕获异常后转换为稳定错误码。

### 3.2 SQLite vs. PostgreSQL（通过 ormpp）

SQLite 适合单实例部署，依赖少、备份简单，但写事务并发能力有限；SQLite 官方说明其可以有多个读事务，但同时只有一个写事务[^6]。启用 WAL、短事务和可靠备份后可满足首版低到中等并发。若要多副本、容灾或多实例横向扩展，直接采用 PostgreSQL，并在 Repository 层保持 SQL 兼容边界。

### 3.3 ormpp 使用注意事项

- 以 ormpp 的参数绑定 API 为唯一 SQL 入口，禁止拼接用户输入。
- 为 `users`、`refresh_tokens`、`user_logs` 建立显式迁移脚本；不要把 C++ 结构体变化自动视为数据库迁移。
- 为用户创建、角色变更、禁用/启用、重置密码和审计写入设计事务边界。
- 用连接池隔离 HTTP 请求；SQLite 下限制写并发，配置 WAL、busy timeout 和 checkpoint。
- 在 Repository/Service 边界捕获 ormpp/SQLite/libpq 异常，映射为稳定错误码。

### 3.4 `szx::crypto` 的 JWT 边界

`szx::crypto` 负责 OpenSSL 静态库的唯一封装边界，提供哈希、HMAC、RSA-PSS、随机数和 Base64 等密码学能力；Argon2id 也应归入该层。`CryptoService` 负责面向业务的密码哈希、参数校验、密钥生命周期和统一 `Result<T>` 错误契约。jwt-cpp 只放在 RABC 的 Token 适配层，不能让其类型穿透 `CryptoService` 公共 API。当前 `szx::crypto` CMake 仍链接 Windows CNG (`Bcrypt`)，迁移到 OpenSSL 前需要新增 OpenSSL provider 实现并保持现有 API/测试兼容。现有 KDF 是 PBKDF2-HMAC-SHA256，不能替代 RABC 要求的 Argon2id；应在 `szx::crypto` 中新增稳定的 Argon2id 能力。

### 3.5 JWT 与 OpenSSL 边界

如果 RABC 服务独立部署，使用 OpenSSL 是可接受的工程选择；可以采用静态 `libssl`/`libcrypto`，从而避免随 RABC 服务分发对应 OpenSSL DLL。静态链接并不等于没有系统依赖：Windows 仍需链接 `WS2_32`、`ADVAPI32`、`CRYPT32`，OpenSSL 官方还列出 `GDI32`、`USER32` 等依赖，具体以构建配置和 `dumpbin /dependents` 结果为准[^7]。

采用 OpenSSL 静态库后，需同步修订 `szx_core` 现有“核心加密不依赖 OpenSSL”的约束，建议：

1. `szx_crypto` 私有链接 OpenSSL 静态库，并在公共头文件中隐藏 OpenSSL 类型；
2. `CryptoService` 继续作为业务唯一入口，调用 `szx::crypto` 的实现；
3. jwt-cpp 仅在 RABC Token 适配层使用，固定 PS256 并做完整 claims 校验。

无论选哪种方案，都必须校验算法白名单、issuer、audience、过期时间、not-before、jti 和密钥版本，不能只“解析 JWT 后相信 payload”。

## 4. 建议的最小依赖集合

### RABC 独立 C++ 后端

- libhv（HTTP/HTTPS 与事件循环）
- ormpp + SQLite；或 ormpp + PostgreSQL/libpq（二选一，按部署规模决定）
- `szx::crypto`（OpenSSL 静态库）+ `szx::crypto_service`（业务门面）；Argon2id 作为 szx crypto 新增能力
- jwt-cpp（仅 RABC Token 适配层）
- nlohmann/json（复用或以独立包锁定版本）
- spdlog（复用 `szx::logger` 或服务私有 target）
- GoogleTest/GMock（仅测试构建）

### 现有业务客户端适配

- Qt 6 `QNetworkAccessManager`（若客户端已是 Qt/QML）或 libcurl（若需要无 Qt 的 C++ SDK）
- nlohmann/json / `szx::common::Serializer`
- 不需要把 libhv、ormpp、SQLite、OpenSSL、JWT 签发能力带入客户端；客户端只保存短期 access token，并调用 `/client/me/permissions`。

## 5. CMake 与供应链要求

1. RABC 建议单独仓库或顶层 `apps/rabc-server`，不要修改 `szx_core` 的默认构建以强制引入服务依赖。
2. 每个依赖使用 namespaced imported target，通过 `target_link_libraries` 精确挂接，禁止全局 include/link 路径。
3. 固定版本或 commit、记录许可证、生成 SBOM，并在 CI 做漏洞扫描和许可证检查。
4. 运行时依赖（OpenSSL、SQLite、PostgreSQL）必须有 Windows/Linux 的 DLL/so 清单和升级策略。
5. `user_logs`、refresh token 和密码哈希的数据库写入必须使用事务；所有第三方异常在 Service 边界转换为稳定错误码，不得穿透 REST 或 C++ 公共 API。
6. 若复用 `szx::common`/`szx::logger`，只依赖其公开 target，不直接 include `third_party` 私有路径。

## 6. 评审结论（分级）

- **P0 必需**：libhv、ormpp + SQLite/libpq、`szx::crypto`（OpenSSL 静态库）、`szx::crypto_service`、jwt-cpp、JSON、日志。
- **P0 测试必需**：GoogleTest/GMock、HTTP/API 测试工具（可用 Python/Node，不必进入 C++ 运行时）。
- **P1 推荐**：OpenAPI 文档/校验工具、SBOM 与依赖漏洞扫描、反向代理 TLS。
- **暂不引入**：Drogon、Boost 全家桶、第二个 ORM、Redis、消息队列、服务注册中心、动态权限引擎；首版单项目 RABC 没有这些需求。

静态 OpenSSL 的发布要求：固定 OpenSSL 版本并保留源码/构建参数；补丁升级时重新构建并回归测试；确认 `/MT`/`/MD`、Debug/Release、x64 ABI 与应用一致；审计静态库许可证和 NOTICE。OpenSSL 3.x 使用 provider 机制时，还要确认是否依赖外置 provider 模块；若要求真正单文件部署，应验证所选配置是否会在运行时加载 provider/DLL。OpenSSL 项目当前采用 Apache-2.0 许可证[^8]。
