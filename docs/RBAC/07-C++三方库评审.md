# RBAC C++ 三方库评审

## 1. 结论

RBAC 设计采用 Vue + REST API，后端当前使用 C++ 实现。第一阶段不拆分仓库，后端位于 `tools/szx_admin`，前端位于 `tools/szx_admin/web/admin`；两者不得把服务依赖传播到现有核心组件的 PUBLIC 依赖中，后续再评估独立拆分。

已确认的首选组合：

- HTTP/REST：libhv
- JSON：复用 `szx::common` 已封装的 nlohmann/json
- 数据库访问：ormpp + MySQL 8.0+；使用 MySQL Connector/C 或兼容的 MariaDB Connector/C 提供客户端库
- 密码哈希、随机数和令牌密钥材料：由 `szx::crypto` 提供；Argon2id 已通过 OpenSSL provider 封装
- JWT：由 RBAC 认证模块使用 jwt-cpp 处理协议层；密码学原语统一经 `szx::crypto`（OpenSSL 静态库）提供，业务调用通过 `szx::crypto_service`
- 日志：复用 `szx::logger`/spdlog，或服务端独立使用固定版本 spdlog
- 测试：复用仓库 GoogleTest/GMock 接入方式

不建议把 libhv、数据库驱动或 OpenSSL 直接加到 `szx_core` 其他组件的 PUBLIC 依赖中。OpenSSL 仅由 `szx_crypto` 私有封装；RBAC 服务和 C++ 客户端适配应通过稳定 HTTP 契约隔离。

## 3. 关键取舍

### 3.1 libhv 的边界

libhv 负责 HTTP/HTTPS、连接和事件循环，但 RBAC 所需的认证中间件、路由分组、JSON 错误模型、请求上下文、限流和审计关联需要在应用层实现。建议建立 `HttpServerAdapter`，将 libhv 类型隔离在 transport 层，Controller/Service 不直接依赖 libhv。

libhv 与 ormpp 的线程模型必须明确：HTTP 回调中不要执行可能阻塞的数据库操作或 Argon2id 哈希；使用任务线程池/工作队列，并在回调边界捕获异常后转换为稳定错误码。

### 3.2 MySQL 连接与事务

第一阶段统一使用 MySQL 8.0+ 和 InnoDB。应用必须显式配置 UTC、`utf8mb4`、连接池、事务隔离级别、连接超时和断线重连策略。用户状态、角色变更、密码重置、refresh token 消费和审计写入必须在明确的事务边界内完成；最后一个 active 超管保护和 refresh token 行锁需要使用 MySQL 事务锁语义进行集成测试。

### 3.3 ormpp 使用注意事项

- 以 ormpp 的参数绑定 API 为唯一 SQL 入口，禁止拼接用户输入。
- 为 `users`、`refresh_tokens`、`user_logs` 建立显式迁移脚本；不要把 C++ 结构体变化自动视为数据库迁移。
- 为用户创建、角色变更、禁用/启用、重置密码和审计写入设计事务边界。
- 用连接池隔离 HTTP 请求；MySQL 下配置事务隔离、锁等待超时和死连接回收。
- 在 Repository/Service 边界捕获 ormpp/MySQL Connector 异常，映射为稳定错误码。
- 不修改三方源码：所有 MySQL 调用经过业务私有 `OrmConnection`。当前驱动的错误状态和事务开关是静态共享的，因此 `DatabasePool` 以进程内统一执行锁覆盖整个连接回调、重连和回滚；等待执行锁超过 3 秒返回 `DatabaseUnavailable`。连接池容量不代表可并行执行事务，增加 `poolSize` 不会提高数据库吞吐量。每次调用在锁内保存本连接错误标志。
- `OrmRuntime` 在进程启动时安装 stdout 过滤器，仅屏蔽当前线程在 ORM 调用范围内的输出；其他线程和业务输出正常转发。不得在运行期替换 `std::cout` 缓冲区或调用 `sync_with_stdio(false)` 绕过过滤。服务仍通过现有稳定错误码和脱敏日志报告数据库失败。
- 审计 JSON 不使用驱动 BLOB 结果绑定，也不直接绑定无界 JSON 字符串。分页先读取字节长度，再通过参数绑定和显式有界 `CAST` 按 16 KiB 二进制片段读取，拼接后交给既有 JSON 解析和脱敏逻辑。代价是每条日志增加分块查询；日志按追加写入使用，不支持跨分块并发改写同一条记录。

### 3.4 `szx::crypto` 的 JWT 边界

`szx::crypto` 负责 OpenSSL 静态库的唯一封装边界，提供哈希、HMAC、RSA-PSS、随机数、Base64 和 Argon2id 等密码学能力。`CryptoService` 负责面向业务的密码哈希、参数校验、`kid` 计算和统一 `Result<T>` 错误契约；密钥版本、轮换窗口和失效策略由 RBAC 密钥仓储负责。jwt-cpp 只放在 RBAC 的 Token 适配层，不能让其类型穿透 `CryptoService` 公共 API。现有 PBKDF2-HMAC-SHA256 继续用于通用 KDF，不能替代 RBAC 要求的 Argon2id。

### 3.5 JWT 与 OpenSSL 边界

如果 RBAC 服务独立部署，使用 OpenSSL 是可接受的工程选择；可以采用静态 `libssl`/`libcrypto`，从而避免随 RBAC 服务分发对应 OpenSSL DLL。静态链接并不等于没有系统依赖：Windows 仍需链接 `WS2_32`、`ADVAPI32`、`CRYPT32`，OpenSSL 官方还列出 `GDI32`、`USER32` 等依赖，具体以构建配置和 `dumpbin /dependents` 结果为准[^7]。

采用 OpenSSL 静态库后，需同步修订 `szx_core` 现有“核心加密不依赖 OpenSSL”的约束，建议：

1. `szx_crypto` 私有链接 OpenSSL 静态库，并在公共头文件中隐藏 OpenSSL 类型；
2. `CryptoService` 继续作为业务唯一入口，调用 `szx::crypto` 的实现；
3. jwt-cpp 仅在 RBAC Token 适配层使用，固定 PS256 并做完整 claims 校验。

无论选哪种方案，都必须校验算法白名单、issuer、audience、过期时间、not-before、jti 和密钥版本，不能只“解析 JWT 后相信 payload”。

## 4. 建议的最小依赖集合

### 当前仓库内的 C++ 后端

- libhv（HTTP/HTTPS 与事件循环）
- ormpp + MySQL 8.0+ Connector/C
- `szx::crypto`（OpenSSL 静态库）+ `szx::crypto_service`（业务门面）；Argon2id 作为 szx crypto 新增能力
- jwt-cpp（仅 RBAC Token 适配层）
- nlohmann/json（复用或以独立包锁定版本）
- spdlog（复用 `szx::logger` 或服务私有 target）
- GoogleTest/GMock（仅测试构建）

### 现有业务客户端适配

- Qt 6 `QNetworkAccessManager`（若客户端已是 Qt/QML）或 libcurl（若需要无 Qt 的 C++ SDK）
- nlohmann/json / `szx::common::Serializer`
- 不需要把 libhv、ormpp、MySQL、OpenSSL、JWT 签发能力带入客户端；客户端只保存短期 access token，并调用 `/client/me/permissions`。

## 5. CMake 与供应链要求

1. 当前阶段使用 `tools/szx_admin` 和其中的 `tools/szx_admin/web/admin`，不要修改现有核心组件的 PUBLIC 依赖以强制引入服务依赖；后续再评估拆分仓库。
2. 每个依赖使用 namespaced imported target，通过 `target_link_libraries` 精确挂接，禁止全局 include/link 路径。
3. 固定版本或 commit、记录许可证、生成 SBOM，并在 CI 做漏洞扫描和许可证检查。
4. 运行时依赖（OpenSSL、MySQL Connector）必须有 Windows/Linux 的 DLL/so 清单和升级策略。
5. `user_logs`、refresh token 和密码哈希的数据库写入必须使用事务；所有第三方异常在 Service 边界转换为稳定错误码，不得穿透 REST 或 C++ 公共 API。
6. 若复用 `szx::common`/`szx::logger`，只依赖其公开 target，不直接 include `third_party` 私有路径。

## 6. 评审结论（分级）

- **P0 必需**：libhv、ormpp + MySQL Connector/C、`szx::crypto`（OpenSSL 静态库）、`szx::crypto_service`、jwt-cpp、JSON、日志。
- **P0 测试必需**：GoogleTest/GMock、HTTP/API 测试工具（可用 Python/Node，不必进入 C++ 运行时）。
- **P1 推荐**：OpenAPI 文档/校验工具、SBOM 与依赖漏洞扫描、反向代理 TLS。
- **暂不引入**：Drogon、Boost 全家桶、第二个 ORM、SQLite/PostgreSQL 后端、Redis、消息队列、服务注册中心、动态权限引擎；首版单项目 RBAC 没有这些需求。
