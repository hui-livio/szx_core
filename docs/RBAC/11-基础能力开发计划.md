# RBAC 基础能力开发计划

## 1. 实施边界

第一阶段代码统一放在当前仓库：

```text
RBAC/
  CMakeLists.txt
  szx_admin/       # C++ 后端与基础服务能力
  szx_admin_web/   # Vue 3 + TypeScript + Vite Admin
```

当前不拆分仓库。`szx_admin_service` 作为单进程同时提供 RESTful API 和 Admin Web 静态资源：`/api/v1/*` 始终优先匹配 API，其他路径从 `server.staticRoot` 提供前端构建产物，并对无扩展名路径回退到 `index.html`。这样部署时只需发布一个 admin 服务包；如需 TLS、域名或限流，可在前面增加 NGINX 反向代理。

开发负责人：项目负责人本人。

## 2. 固定依赖

| 依赖 | 版本 | 来源 | 用途 |
|---|---|---|---|
| libhv | v1.3.4 | GitHub release ZIP | HTTP/HTTPS、路由和事件循环 |
| jwt-cpp | v0.7.2 | GitHub release ZIP | JWT 协议解析和构建；签名通过 CryptoService |
| ormpp | 仓库固定版本 | `third_party/ormpp` | MySQL 数据访问 |
| MySQL | 8.0+ | 本地/部署环境 | 持久化数据库 |
| Vue | 3.x | 本地 Node 环境 | Admin 前端 |

依赖 ZIP 的 SHA-256、许可证和本地目录记录在[三方库评审](07-C++三方库评审.md)及仓库依赖清单中。升级依赖时必须重新记录版本、哈希并执行回归测试。

## 3. 阶段计划

当前执行顺序调整为：**数据库设计与 migration 优先完成，认证/API 和 Admin Web 顺延**。在数据库基线、内置 migration、幂等超管初始化和 Repository 事务测试通过前，不进入业务 API 开发。

### 阶段 0：依赖与环境验证

- 验证 libhv、jwt-cpp ZIP 源码可被当前 CMake/MSVC 构建。
- 验证 ormpp 自动发现本地 MySQL C API。
- 完成 MySQL 连接、事务、参数绑定和连接失败测试。
- 固定 Node、Vue、Vite、TypeScript 和包管理器版本。
- 记录 Debug/Release、x64、运行库和 OpenSSL 配置。

出口：后端空 target 和前端空项目均可构建；MySQL 最小连接测试通过。

### 阶段 1：基础能力

按以下顺序实现：

1. 配置加载和敏感配置来源。
2. 统一错误码、HTTP 错误映射和 request ID。
3. MySQL/ormpp 连接池、事务 RAII 和 migration 执行器。
4. `JwtService`：PS256、claims、`kid`、issuer/audience、时钟偏差和密钥提供接口。
5. 审计日志接口和脱敏策略。
6. HTTP transport、中间件和健康检查。
7. Vue API Client、Pinia 会话状态和路由守卫。

数据库优先交付内容：

- 建库、建表和 migration 执行器幂等；
- migration SQL 在构建阶段嵌入服务，运行时不读取或发布本地 SQL；
- `schema_migrations` 版本、checksum 和并发锁校验；
- users、refresh_tokens、user_logs 的 Repository、参数绑定和事务边界；
- 默认超管的幂等创建、唯一性约束、`force_password_change` 和首次改密数据状态。

数据库阶段出口：空数据库可重复启动并完成初始化；已有数据库重复启动无重复数据；并发启动只产生一条超管记录；已执行 migration 被修改时可靠阻断；建库、建表、Repository 和事务测试通过。

当前已完成的 JWT 基础能力：

- `JwtService` 支持 PS256、固定 claims、`kid`、issuer/audience、时钟偏差和稳定错误码；
- `JwtKeyStore` 支持内存密钥注册、当前签名密钥激活、按 `kid` 验证和旧密钥有效期；
- `JwtConfig` 仅保存配置数据，由后续主程序统一解析全局配置并注入。

当前已完成的基础设施能力：

- `ServerConfig` 支持 HTTP host、port、worker、请求体上限、连接上限、API prefix、访问日志，以及静态资源根目录、首页和 SPA 路由回退配置；
- `ErrorCode` 统一维护 API 错误码、HTTP 状态映射和安全默认消息；admin 将错误响应的 `code` 序列化为该枚举的 JSON 整数值（如资源不存在为 `2205`），名称仅用于诊断，完整数值表见 RESTful API 接口文档；
- `RequestContext` 规范化或生成 `X-Request-ID`，并保证响应回传 request ID；
- `HttpTransport` 通过 `szx::network` 提供 REST 路由注册、启动/停止、请求体限制和静态文件安全处理，不直接包含或链接 libhv；统一错误响应、request ID、访问日志、API 前缀排除和 SPA 回退由 admin 注入，并提供 `/api/v1/health` 健康检查；
- `ServerConfig` 和 `DatabaseConfig` 仅保存并校验配置数据，不自行读取文件或环境变量；后续由主程序统一解析全局配置后注入；`DatabasePool` 通过 ormpp 管理连接、会话参数和事务边界；`MigrationRunner` 校验版本 checksum 并执行内置 SQL migration；
- 业务 Repository 必须使用 ormpp 的反射实体、查询构造和参数绑定；原生 SQL 仅限审核后的 migration DDL、数据库会话初始化和 MySQL advisory lock，不得作为业务 CRUD 接口下沉。
- `DatabaseInitialization.cc` 统一固化 schema_migrations、users、refresh_tokens、user_logs、admin_bootstrap 的建表语句和初始账号定义。
- `szx_admin_service` 已提供主服务启动入口：通过 CLI11 解析唯一配置参数 `-c/--config`，未指定时按进程工作目录下 `config.yaml`、`config/config.yaml` 顺序查找；使用 Iguana YAML 加载配置，显式构造日志 `LogOptions` 后初始化 logger，启动数据库连接池、执行 migration、暴露 `/api/v1/health` 与 `/api/v1/ready`，并处理 SIGINT/SIGTERM 优雅停止。

尚未完成的数据库业务接入：users、refresh_tokens、user_logs 的完整 Repository，以及用户管理、令牌轮换/撤销和审计同事务写入。现有数据访问仅覆盖 migration journal 和 bootstrap，因此不能将“数据库初始化完成”视为“数据库接入全部完成”。尚未完成的认证业务能力：登录、refresh token family、登录密码校验、首次改密接口和持久化密钥存储。

REST 基础层已接入：`RestApi` 统一提供 JSON 对象/字段白名单校验、分页、If-Match 版本解析、Bearer 凭据提取、成功/错误 envelope 和空 204；`HttpRequest` 透传已解码路径/查询参数并提供忽略大小写的请求头查询。`registerApiRoute()` 自动应用配置前缀，允许显式注册 OPTIONS。`src/Routes.cc` 集中维护健康、就绪和后续业务路由注册，主程序只负责依赖构造及调用入口。`/ready` 使用统一响应格式和稳定数据库错误码。

该阶段只交付协议基础层，Bearer 提取不代表已完成认证，If-Match 解析不代表已完成乐观锁更新。认证、用户与审计 Repository、权限中间件和业务端点仍按后续阶段实现。验证覆盖纯协议边界、真实 TCP 路径/查询参数、大小写请求头、PATCH 校验、OPTIONS/204、自定义前缀、数据库不可用响应，以及独立 MySQL 实例上的就绪响应契约。

2026-09-17 数据库初始化 review：修复 bootstrap 在事务提交前释放初始化锁的并发窗口；初始化服务自行负责事务，账号与完成标记原子提交，失败/异常回滚后才解锁。migration journal 也使用事务 RAII，避免异常时带着未提交事务释放迁移锁。连接池首次连接与重连统一设置 UTC、READ COMMITTED 和锁等待超时。配置入口兼容 LF/CRLF 换行。

迁移执行前根据实际内置 SQL 重新计算 SHA-256 并与声明 checksum 比较，防止 SQL 已修改但 fingerprint 未同步；读取 journal 后拒绝重复版本、checksum 冲突以及当前程序不认识的更高版本，避免旧服务回滚后继续操作新版 schema。

代码组织：建库、所有建表语句、migration 版本/checksum 和初始账号定义及执行逻辑集中在 `RBAC/szx_admin/src/infra/DatabaseInitialization.cc`；不再保留独立 migration SQL 或 CMake 生成模板。`Database.cc` 负责配置校验、连接池和 ormpp 数据访问适配，并从私有 `DatabaseInitialization.h` 读取统一账号定义，不新增对外发布接口。

验证入口：`ctest --test-dir build -R test_rbac --output-on-failure`；真实 MySQL 回归使用 `python scripts/test_admin_database.py --service build/bin/szx_admin_service.exe`，要求 `mysql`、`mysqld` 在 PATH。脚本只运行独立临时实例，不访问已有业务数据库；验证无 SQL 文件的运行包、SQL URL 404、空库/重复/并发启动、账号状态保留、初始化标记、DDL 重放、checksum 冲突、写入故障回滚与重试、普通角色用户名冲突。用户与令牌/审计 Repository 的业务集成测试仍待实现。

HTTP 接入边界：`network.use()` 接收 request ID 和访问日志中间件；`onRequestError()` 接收早期解析错误、413 和异常兜底的 JSON 格式化回调；`onNotFound()` 接收静态资源及 SPA 策略。admin 复用 `HttpServer::CreateStaticHandler()`，根据 `staticHomePage` 提供目录首页，仅在非 API、无扩展名且文件不存在时执行 SPA 回退，路径安全失败不进入回退。缺失静态目录时仍允许 API 服务启动。

健康检查路径为 `${apiPrefix}/health`（默认 `/api/v1/health`），接受一个尾斜杠，不提供固定 `/health` 别名；仅当 `apiPrefix=/` 时健康路径为 `/health`。GET 返回 `200` 和 `{"data":{"status":"ok"},"request_id":"…"}`，HEAD 返回相同状态与响应头而不发送 body，其他方法返回 405。健康路由优先于静态文件和 SPA，不能被业务路由替换。路径兼容由 admin 层配置，网络库不内置健康接口。

admin 通过 `useBeforeRouting()` 注入路径归一化，将所有接口路径中的连续字面量 `/` 合并为一个，例如 `///api//v1///health` 转为 `/api/v1/health`。路由注册执行相同归一化，重复路径仍报冲突；查询参数、body 和 `%2F` 等百分号编码保持原样。路由匹配、API 前缀排除和静态文件处理使用同一路径。网络库提供通用路由前中间件接口，不内置此策略。

配置映射：`workerThreads=0` 使用 1 个 IO 线程，其他值映射到网络库总 IO 线程数；`maxConnections` 为全服务连接上限（包括空闲连接）；`maxRequestBodyBytes` 在报文体接收前生效。访问日志默认开启（`server.accessLog=true`），使用 `szx::logger` 的 `szx_admin.http` 模块，以 INFO 记录 request ID、方法、路径和最终状态，包含健康检查、业务路由、404 和异常响应。路径最多记录 512 字节并以 JSON 字符串转义，不记录查询参数、凭据或报文体；全局日志级别需允许 INFO。服务包需要携带 `szx_network.dll`。独立构建默认启用 `SZX_COMPONENTS_BUILD_RBAC`，子项目默认关闭；启用 admin 时必须同时启用 `SZX_COMPONENTS_BUILD_NETWORK`。

迁移验证：6 个真实 TCP 集成用例覆盖健康接口、request ID、业务异常与非法响应、早期 413、Expect、静态首页/SPA/API 隔离、路径逃逸拒绝、连接上限、端口冲突与重启。网络库 21 个用例和 RBAC 三组测试通过。未新增认证业务接口；`/ready` 仍沿用已有同步数据库探测，后续异步响应支持需另行设计。

出口：基础 target 可构建；JwtService 单测通过；错误、日志和数据库边界不泄漏异常。

### 阶段 5：Admin 与 Admin Web 联合发布

1. 固定前端产物目录结构：将 `szx_admin_web` 的 `dist/` 内容发布为 `<package>/web/`，入口文件为 `index.html`。
2. 生成 Release 包：包含 `szx_admin_service`、依赖 DLL、`config/` 和 `web/`；禁止包含 `migrations/` 或独立 SQL 文件。配置中的 `server.staticRoot` 使用相对进程工作目录的 `web`，不得指向源码或服务根目录。内嵌 SQL 是部署封装，不构成二进制加密保护。
3. 发布前验证：启动服务后检查 `/api/v1/health`、`/api/v1/ready`、`/`、深层前端路由和不存在的 API 路径；API 404 返回 JSON，前端深层路由返回 `index.html`。
4. 生产部署：服务直接监听内部端口；需要 HTTPS、域名、访问日志集中化或外部限流时，再由 NGINX 做 TLS 终止和反向代理。

### 数据库初始化约束

- 建库使用 `CREATE DATABASE IF NOT EXISTS`，建表和 `schema_migrations` 使用 `CREATE TABLE IF NOT EXISTS`。
- 已发布 migration 只读；结构变化必须新增版本，禁止修改旧 SQL 或通过覆盖 checksum 绕过冲突检查。
- migration 完成后执行 bootstrap 超管初始化。使用唯一索引、初始化 advisory lock 和服务自有事务保证幂等；持锁直到事务提交或回滚，账号与完成标记一同提交。已有完成标记不重建账号，已有超管不重置密码或业务状态。
- 默认超管初始化已在数据库启动流程实现，创建时设置 `force_password_change=true`；后续认证模块负责首次登录强制修改密码。
- migration SQL 不作为运行时文件读取，也不随发布包以明文目录发布。版本、SQL 内容、checksum 和初始账号定义直接内置于 `DatabaseInitialization.cc`；`ServiceConfig` 不暴露 migration 路径或初始账号参数。
- bootstrap 超管参数不进入当前服务配置文件；当前固定初始化策略仅对尚未初始化的数据库生效。
