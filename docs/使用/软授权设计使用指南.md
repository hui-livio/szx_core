# 软授权设计使用指南

本文面向产品集成、客户交付和内部签发人员，说明当前 SZX 软授权实现的工作方式、命令行用法、C++ 集成方式和安全边界。

> 本文描述的是仓库当前可执行实现（2026-09-09）。在线激活、许可证安装存储、时钟回拨保护、在线吊销和公钥轮换尚未实现，不应按已发布能力对外承诺。

## 1. 快速了解

软授权采用离线签名模式：

```text
客户程序 --发行方公钥--> 生成 .szxreq
                              │
                              ▼
                    内部发行环境解密并签发
                              │
                              ▼
客户程序 --发行方公钥--> 验证 .szxlic 并启用功能
```

- `.szxreq` 是使用发行方公钥加密的请求文件，只有发行方私钥可以解密。
- `.szxlic` 是使用发行方私钥签名的许可证文件，客户程序只需要发行方公钥即可验证。
- 私钥只允许出现在受控发行环境中，不得放入客户安装包、日志、测试资产或源代码仓库。
- 许可证默认绑定机器因子，机器变更后通常需要重新生成请求并重新签发。

当前工具通常位于 `build/bin/`；多配置构建时位于对应配置子目录：

- `szx_license_user_demo`：客户侧请求生成和许可证验证示例。
- `szx_license_issuer`：内部使用的密钥、签发和验证工具。

## 2. 标准交付流程

### 2.1 发行方首次准备密钥

在隔离的发行环境生成 RSA-3072 密钥对：

```powershell
szx_license_issuer keygen `
  --private-key issuer-private.pem `
  --public-key issuer-public.pem
```

使用 `key-info` 记录公钥 Key ID，并把公钥安全地交付给客户程序：

```powershell
szx_license_issuer key-info --public-key issuer-public.pem
```

发行私钥文件当前由工具按路径读取，格式为未加密 PKCS#8 PEM。应通过操作系统权限、专用发行机或密钥存储保护它；不要把私钥路径写入客户配置。

### 2.2 客户生成授权请求

客户程序使用发行方公钥生成请求：

```powershell
szx_license_user_demo request `
  --product szx.crypto-tool `
  --version 1.0.0 `
  --public-key issuer-public.pem `
  --output customer.szxreq
```

生成的请求包含产品标识、应用版本、请求 ID、UTC 创建时间、功能请求和机器因子摘要。原始硬件标识不会写入请求；请求文件本身也不包含私钥或密码。

客户只需把 `customer.szxreq` 交给发行方。请求文件不能自行产生有效许可证，也不能用客户侧 demo 代替内部签发工具。

### 2.3 内部签发许可证

发行方使用同一密钥对解密请求并签发许可证：

```powershell
szx_license_issuer issue `
  --request customer.szxreq `
  --private-key issuer-private.pem `
  --public-key issuer-public.pem `
  --output customer.szxlic `
  --license-id acme-2026-001 `
  --issuer szx-sales `
  --days 365
```

省略 `--days` 表示永久许可证；指定时必须是正整数。签发工具会校验请求格式、私钥解密、公私钥匹配、期限范围，并在输出前使用公钥自验签名。输出文件已存在时默认拒绝覆盖。

签发成功后，只把 `.szxlic` 交给客户。发行方应保留许可证 ID、客户和签发记录，但不要记录机器原始标识。

### 2.4 客户验证许可证

```powershell
szx_license_user_demo verify `
  --input customer.szxlic `
  --public-key issuer-public.pem `
  --product szx.crypto-tool
```

验证成功后，程序会输出许可证 ID、产品、版本、发行方、UTC 时间、功能列表和机器因子数量。验证失败返回非零退出码；产品参数省略时不会执行产品匹配，因此生产程序应始终传入编译期或配置确定的预期产品标识。

## 3. C++ 集成

客户程序只应依赖 `SzxLicense/License.h`，不应包含 `SzxLicense/Issuer.h`。后者属于内部签发 API，不得随客户 SDK 或安装包发布。

### 3.1 生成请求

```cpp
#include "SzxLicense/License.h"

SZX::LICENSE::RequestOptions options;
options.productId = "szx.crypto-tool";
options.appVersion = "1.0.0";
options.requestedFeatures = {"crypto.symmetric", "crypto.asymmetric"};
options.customFields["customer"] = "acme";

auto result = SZX::LICENSE::createRequestFile(options, "customer.szxreq", issuerPublicKey);
if (!result.ok) {
    // 记录 result.error；不要依赖 result.message 做业务判断。
}
```

`issuerPublicKey` 是 `std::span<const std::uint8_t>`，支持基础密码库定义的 DER 或 PEM 密钥字节。若业务只需要构造或测试请求 JSON，可使用 `createRequest`；真实交付流程应使用 `createRequestFile`，以获得请求文件的加密保护和原子写入。

### 3.2 验证并检查功能

```cpp
auto result = SZX::LICENSE::verifyFile(
    "customer.szxlic", issuerPublicKey, "szx.crypto-tool");
if (!result.ok) {
    // fail closed：不要启用受保护功能。
    return;
}

const auto &license = result.value;
if (SZX::LICENSE::hasFeature(license, "crypto.asymmetric")) {
    // 启用非对称密码功能
}
```

`verify` 用于验证内存中的许可证封装，`verifyFile` 用于按路径读取许可证。两者都会校验封装格式、版本、发行方 Key ID、RSA-PSS-SHA256 签名、产品、机器因子和有效期；签名或业务校验失败时必须保持功能关闭。

所有 API 返回 `SZX::COMMON::Result<T>`。调用方应判断 `ok` 并按稳定错误码处理，不要匹配错误消息文本。

## 4. 授权字段设计

| 字段 | 用途 | 使用建议 |
|---|---|---|
| `productId` | 区分产品和摘要域 | 使用稳定、全局唯一的产品标识，不随显示名称变化 |
| `appVersion` | 标识请求或许可证对应版本 | 采用统一版本格式；当前实现不提供版本范围策略 |
| `licenseId` | 追踪一份许可证 | 在发行系统中保持唯一，便于补发和审计 |
| `issuer` | 标识签发方 | 使用固定内部标识，不放入敏感信息 |
| `features` | 功能授权码 | 使用稳定字符串，如 `crypto.symmetric`；业务代码通过 `hasFeature` 查询 |
| `customFields` | 传递非敏感业务元数据 | 只放客户编号等必要信息，不放密码、密钥或原始硬件标识 |

授权类型由到期时间表达：`expiresAtUtc` 缺省表示永久许可证；设置为未来 UTC Unix 秒时间戳表示期限许可证。当前发行 CLI 通过 `--days` 设置期限。

## 5. 机器绑定规则

当前平台采集以下产品域隔离后的摘要：

- Windows：SMBIOS UUID、`MachineGuid`、系统卷序列号。
- Linux：`/etc/machine-id`。

验证时最多允许 8 个因子。许可证包含 1 个因子时要求匹配 1 个；包含 2 个及以上因子时默认要求至少匹配 2 个不同因子。产品标识参与摘要域隔离，因此不同产品不会直接复用同一机器摘要。

机器重装、更换系统盘、主板更换、虚拟机迁移或镜像克隆可能导致 `MachineMismatch`。当前没有自动迁移或人工恢复 API；正确处理方式是重新生成请求，由发行方审核后重新签发，不能在客户端静默放宽匹配规则。

## 6. 错误处理与排障

| 错误码 | 含义 | 建议处理 |
|---|---|---|
| `InvalidArgument` | 参数为空、超限或期限非法 | 检查产品、版本、路径和 `--days` |
| `Malformed` | 文件结构或 JSON 不完整 | 重新传输或重新生成文件 |
| `Unsupported` | 请求/许可证版本或算法不支持 | 使用与当前 SDK 匹配的工具版本 |
| `SignatureInvalid` | 签名、密钥或请求认证失败 | 核对公钥、私钥是否属于同一发行方，检查文件是否被改动 |
| `Expired` / `NotYetValid` | 当前 UTC 时间不在授权区间 | 核对系统时间，必要时重新签发 |
| `WrongProduct` | 许可证产品与程序不一致 | 使用正确产品的许可证，禁止忽略该错误 |
| `MachineMismatch` | 当前机器因子不满足绑定规则 | 重新生成请求并申请重新签发 |
| `IoError` | 文件读取、写入或提交失败 | 检查路径、权限和磁盘空间 |

不要通过修改许可证二进制内容、替换公钥、删除机器校验或捕获错误后继续启用功能来“修复”授权问题。

## 7. 安全与发布检查清单

- 客户包只包含客户认证库和发行方公钥，不包含 `szx_license_issuer`、`Issuer.h`、发行私钥或签发脚本。
- 发布前确认许可证验证失败时 fail closed，且产品匹配始终开启。
- 不在日志中输出私钥、原始机器标识、请求明文或完整许可证内容。
- `.szxreq` 和 `.szxlic` 传输失败时重新生成或重新签发，不手工编辑文件。
- 发行私钥与公钥必须配对；轮换前后不得混用未登记的 Key ID。
- 使用受控发行环境保存签发记录和许可证 ID，并限制私钥文件读权限。
- 在发布验收中覆盖篡改、截断、错误产品、错误密钥、过期和机器不匹配场景。

## 8. 验证当前实现

仓库提供单元测试和 CLI 端到端测试。完成构建后可运行：

```powershell
py -3 scripts/test_license_flow.py
```

该流程覆盖请求生成、许可证签发、许可证验证，以及错误产品、许可证篡改、请求损坏和非法期限等失败场景。协议提案与尚未实现的扩展见 [软授权开发方案](../设计/软授权开发方案.md)，当前实现细节见 [软授权工具实现说明](../RBAC/09-软授权工具实现说明.md)。
