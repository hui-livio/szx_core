# CMake 构建系统优化与双仓拆分实施计划

> 文档状态：待评审。
>
> 编制日期：2026-08-12。
>
> 代码基线：`cmake_build_optimization` 分支，提交 `5fa5fc5b`。
>
> 上位决策：[PCB 检测系统双仓拆分实施方案](../设计/PCB检测系统双仓拆分实施方案.md)。本文不重新决定产品边界，只定义 CMake 包化、构建优化和物理拆仓的执行顺序与门禁。

## 1. 目的

当前工程采用单仓 superbuild：顶层 CMake 同时配置通用组件、PCB DetectEngine、Qt/QML 应用、工具和全部测试。该方式适合早期联合开发，但尚未形成可安装、可版本化、可独立消费的组件边界。

本计划的目标是：

1. 先在当前仓库内消除源码路径耦合和重复编译。
2. 将通用组件建设为标准 CMake package。
3. 证明 PCB 应用可只通过安装树消费组件。
4. 在验证通过后，将代码迁移为 `pcb-detect-app` 与 `szx-components` 两个仓库。
5. 让拆仓带来可复现构建和增量构建收益，而不是把单仓源码构建包装成跨仓 `add_subdirectory()`。

## 2. 范围与非目标

### 2.1 本期范围

- 顶层 CMake、Presets、依赖发现、编译选项、输出和测试辅助函数。
- `modules/common`、`crypto`、`logger`、`camera`、`plc` 的首批包化。
- `feature_manager`、`UIToolkits` 的迁移门禁和可选组件设计。
- PCBDetect 应用源码目标化。
- DetectEngine 公共/私有头文件和链接传播边界。
- install-tree consumer、CI、制品清单和版本锁定。
- Git 历史提取、切换和回滚方案。

### 2.2 非目标

- 不修改检测业务流程、算法结果、数据库语义或硬件协议。
- 不升级 Qt、MSVC、OpenCV、CUDA、TensorRT、IKap 或 MySQL 版本。
- 不将组件改造成网络服务。
- 不承诺首版组件包跨编译器或跨 Qt 大版本 ABI 兼容。
- 不在缺少基线数据时宣称具体构建性能收益。

## 3. 当前基线与主要问题

### 3.1 量化基线

基于 2026-08-12 静态检查：

| 指标 | 当前值 | 目标 |
|---|---:|---:|
| CMake 中 `${CMAKE_SOURCE_DIR}` 引用 | 216 | 组件仓内 0；应用对组件源码 0 |
| 测试直接引用 `apps/PCBDetect/src` | 121 | 0，改为链接应用核心目标 |
| 应用/工具/测试引用 `detectengine/pcb/src` | 64 | 应用和工具为 0；白盒测试受控 |
| `install(EXPORT)` / package config | 0 | 每个发布组件均可导出 |
| 默认构建修改受版本控制文件 | 存在，`lupdate` 修改 `.ts` | 0 |
| Repo B install-tree consumer | 不存在 | 必须通过 |

上述计数用于确定改造方向。实施开始前应补充同一机器、同一配置下的时间基线：

- 全新 configure 时间。
- 全新 `PCBDetect` 与全量 UT 构建时间。
- no-op build 时间。
- 修改单个 Controller、`common` 头文件和 QML 文件后的增量构建时间。
- 构建目录大小和部署目录文件清单。

### 3.2 阻塞拆仓的问题

1. `szx::common` 等名称当前只是 build-tree alias，没有可供外部仓库使用的导出目标。
2. `cmake/output.cmake` 虽有安装辅助函数，但尚未实现 `install(EXPORT)`、Config 和 Version 文件。
3. 模块使用 `${CMAKE_SOURCE_DIR}` 查找仓库内 thirdparty、SQLite 和测试源码，无法作为独立子项目或安装包构建。
4. PCBDetect 与测试直接包含 DetectEngine 私有源码目录，绕过公共 API。
5. 测试重复列举生产 `.cc` 文件，扩大编译图并可能产生不同于正式目标的编译契约。
6. DetectEngine 将 camera、PLC、OpenCV、TensorRT 等实现依赖广泛声明为 `PUBLIC`，消费者被迫继承无关依赖。
7. 公共头文件采用 `Result.hpp`、`Logger.h` 等扁平名称，安装后存在名称冲突风险。
8. 外部依赖默认值绑定开发机绝对路径，缺少 toolchain/preset/CI 注入契约。
9. `PCBDetect` 默认依赖 `lupdate`，普通构建可能改写源码树。
10. 全局 `add_compile_options()` 和全局 PIC 设置会隐式影响第三方及所有子项目。

## 4. 目标仓库与迁移批次

### 4.1 最终双仓

| 仓库 | 所有权 |
|---|---|
| `pcb-detect-app` | PCBDetect、DetectEngine、PCB 算法、数据库、配置、模型清单、业务工具、业务测试和部署 |
| `szx-components` | 无 PCB 业务语义的公共基础设施、设备适配、公共 UI 组件、组件测试、安装和制品发布 |

依赖必须单向：

```text
pcb-detect-app -> versioned SZXComponents package
```

禁止 Repo B 包含 PCB 数据结构、产品配置、模型路径或反向依赖 Repo A。

### 4.2 分批迁移

首批包化：

- `common`
- `crypto`
- `logger`
- `camera`
- `plc`

延后进入正式制品：

- `feature_manager`：当前没有生产消费者。只有在明确保留并重新建立真实消费方后才发布，否则从默认构建移除。
- `UIToolkits`：长期归 Repo B，但当前与 PCB UI 变更节奏高度耦合。必须先通过独立 QML import、插件安装和冷启动测试，再纳入正式组件包。

延后不改变上位 ADR 的最终归属，只降低首轮迁移同时处理 C++ ABI、Qt QML 插件和无生产消费者模块的风险。

## 5. 目标 CMake 架构

### 5.1 Repo B 导出目标

首版必须提供：

```text
szx::common
szx::crypto
szx::logger
szx::camera
szx::plc
```

满足迁移门禁后增加：

```text
szx::feature_manager
szx::feature_manager_qt
SZX::UIToolkits
```

组件内部可使用实现目标，但不得要求 Repo A 知道实现目标名称。

### 5.2 公共头文件布局

```text
include/
└── szx/
    ├── common/
    ├── crypto/
    ├── logger/
    ├── camera/
    ├── plc/
    └── feature_manager/
```

消费方使用稳定路径：

```cpp
#include <szx/common/Result.hpp>
#include <szx/logger/Logger.h>
#include <szx/camera/CameraService.h>
```

过渡期可以保留旧头文件转发层并标记弃用；移除旧路径属于后续 major 版本变更。

### 5.3 安装与导出

Repo B 使用标准安装导出：

```cmake
include(GNUInstallDirs)
include(CMakePackageConfigHelpers)

install(TARGETS szx_common szx_crypto szx_logger szx_camera szx_plc
    EXPORT SZXComponentsTargets
    FILE_SET HEADERS DESTINATION ${CMAKE_INSTALL_INCLUDEDIR}
    RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}
    LIBRARY DESTINATION ${CMAKE_INSTALL_LIBDIR}
    ARCHIVE DESTINATION ${CMAKE_INSTALL_LIBDIR}
)

install(EXPORT SZXComponentsTargets
    FILE SZXComponentsTargets.cmake
    NAMESPACE szx::
    DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/SZXComponents
)
```

同时生成：

- `SZXComponentsConfig.cmake`
- `SZXComponentsConfigVersion.cmake`
- `SZXComponentsTargets.cmake`
- `manifest.json`
- 第三方许可证清单

### 5.4 消费契约

Repo A 只能通过 package targets 消费：

```cmake
find_package(SZXComponents 1.0 CONFIG REQUIRED
    COMPONENTS Common Crypto Logger Camera Plc)

target_link_libraries(szx_detectengine_pcb
    PRIVATE
        szx::crypto
        szx::logger
        szx::camera
        szx::plc
)
```

禁止：

- `add_subdirectory()` 指向 Repo B 工作区。
- 添加 Repo B 的源码或私有 include 路径。
- 从 Repo A 复制一份组件源码。
- 构建时自动跟随 Repo B 的未固定分支。

### 5.5 依赖传播

链接可见性按公开签名决定：

- 公共头文件出现某依赖类型时使用 `PUBLIC`。
- 静态库实现需要链接、但公共头不暴露的依赖使用 `PRIVATE`；CMake 会以 link-only 形式满足最终链接。
- OpenCV、CUDA、TensorRT、IKap、libmodbus 等尽量不进入 Repo A 的公共接口。
- 每个已安装公共头文件必须通过独立自包含编译测试。

### 5.6 编译策略目标

使用接口目标代替目录级全局选项：

```text
szx::project_options
szx::project_warnings
```

自研目标显式链接这些策略；thirdparty 和 imported targets 不继承项目警告配置。统一：

- CMake 最低版本。
- C++20 声明方式。
- MSVC runtime、字符集和告警策略。
- Debug/Release/RelWithDebInfo 配置映射。

## 6. 实施工作包

### WP0：冻结和测量基线

工作内容：

1. 锁定工具链及三方库版本。
2. 记录 configure、全量构建、no-op 和典型增量构建时间。
3. 保存测试结果、安装目录和运行时 DLL 清单。
4. 建立构建测量脚本，输出机器、提交、配置和耗时。

退出标准：基线可在同一机器重复两次，波动范围有记录。

### WP1：构建副作用和配置入口治理

工作内容：

1. 将 `lupdate` 从 `PCBDetect` 默认依赖中移除，提供显式 `PCBDetect_update_translations`。
2. 普通构建只消费已提交的 `.ts` 并生成 `.qm`。
3. 统一 CMake 最低版本和 preset 入口。
4. 将 OpenCV、TensorRT、CUDA、IKap 等路径移入 user preset、toolchain 或 CI 参数。
5. 用 target 级策略替换全局编译选项。

退出标准：连续执行 configure/build 后 `git status --short` 为空。

### WP2：应用和测试目标化

工作内容：

1. 将 PCBDetect 非入口源码抽成 `pcbdetect_ui_core`。
2. `PCBDetect` 可执行文件只保留 `main`、资源、QML 注册和部署逻辑。
3. Controller、Gateway、Mapper 等测试链接 `pcbdetect_ui_core` 或粒度更小的正式目标。
4. 删除测试 CMake 对生产 `.cc` 文件的大规模重复列举。
5. 工具只使用 DetectEngine 公共目标，不包含 `detectengine/pcb/src`。

退出标准：

- 测试对 `apps/PCBDetect/src/*.cc` 的直接引用为 0。
- 应用和工具对 `detectengine/pcb/src` 的 include 路径为 0。
- 关键测试与现有基线一致。

### WP3：组件公共 API 和包化

工作内容：

1. 建立 `include/szx/<component>` 布局和兼容转发头。
2. 为公共头配置 `FILE_SET HEADERS`。
3. 为组件补齐 `BUILD_INTERFACE`/`INSTALL_INTERFACE`。
4. 收紧 `PUBLIC`/`PRIVATE` 依赖。
5. 实现 Config、Version、Targets 和 component 检查。
6. 增加 installed-header self-contained tests。

退出标准：Repo B 候选组件可独立 build、test、install。

### WP4：单仓内 install-tree 消费演练

工作内容：

1. 将组件安装到全新临时前缀。
2. 使用新的构建目录配置 PCB 应用。
3. 禁止该构建访问 `modules/*` 源码路径。
4. 运行应用编译、核心 UT、检测集成测试和部署检查。

建议验证命令：

```powershell
cmake --preset windows-ninja -S . -B build/components -DSZX_BUILD_APP=OFF
cmake --build build/components --config RelWithDebInfo
cmake --install build/components --config RelWithDebInfo --prefix build/stage/szx-components

cmake --preset windows-ninja -S . -B build/consumer `
  -DSZX_COMPONENTS_MODE=PACKAGE `
  -DCMAKE_PREFIX_PATH="$PWD/build/stage/szx-components"
cmake --build build/consumer --config RelWithDebInfo --target PCBDetect
```

退出标准：移除或隐藏 `modules/` 源目录后，consumer 构建仍成功。

### WP5：组件制品与版本锁定

工作内容：

1. 发布 Windows x64 MSVC 的 Debug、Release/RelWithDebInfo 兼容制品。
2. `manifest.json` 记录 Git commit、编译器、Qt、OpenCV、SDK 版本和 SHA-256。
3. Repo A 保存组件锁定版本，不自动跟随 Repo B 主分支。
4. 开发期可提供固定 tag/commit 的源码 fallback，但 CI 和正式发布必须验证安装包模式。

退出标准：从空缓存下载固定组件版本后可离线配置和构建 Repo A。

### WP6：物理拆仓

工作内容：

1. 使用历史保留工具从临时克隆提取 Repo B 路径。
2. 在 `szx-components` 中恢复独立顶层 CMake、测试和 CI。
3. 发布 `1.0.0-rc.1`，由 Repo A 完成兼容验证。
4. 提取或整理 `pcb-detect-app`，删除组件源码副本。
5. 固定正式组件版本并完成部署包冷启动验证。

退出标准：两个仓库分别从空目录独立构建，Repo A 不访问 Repo B 源码树。

### WP7：切换、观察和清理

工作内容：

1. 冻结原单仓写入并同步最后增量。
2. 建立双仓分支、发布、兼容和回滚规范。
3. 原仓库保持只读至少一个正式发布周期。
4. 删除过渡期转发头、源码 fallback 和兼容脚本前再次评审。

退出标准：一个正式发布周期内没有依赖方向、ABI、部署或回滚阻断问题。

## 7. CI/CD 门禁

### 7.1 `szx-components`

- 独立 configure/build/test/install。
- 公共头文件自包含测试。
- install-tree consumer 测试。
- package component 缺失和版本不兼容负向测试。
- Debug 与 Release/RelWithDebInfo 制品检查。
- DLL、QML 插件及许可证清单检查。
- camera/PLC mock 每次提交执行，真实硬件进入专用 runner。

### 7.2 `pcb-detect-app`

- 使用最低兼容组件版本构建。
- 使用推荐组件版本构建。
- 禁止扫描到 Repo B 源码路径。
- PCBDetect、DetectEngine UT 和本地模型检测集成测试。
- QML lint/AOT、部署目录检查和冷启动测试。
- Repo B 候选版本触发兼容流水线，但不得自动更新版本锁。

## 8. 性能验收

拆仓不自动等于构建加速。若 Repo A 每次仍通过 FetchContent 编译 Repo B 全部源码，则只增加仓库协调成本。

以 WP0 基线为比较对象：

| 场景 | 必须门禁 | 优化目标 |
|---|---|---|
| no-op build | 不比基线慢 10% 以上 | 减少不必要的代码生成和部署命令 |
| 修改单个 Controller | 不重编 DetectEngine/组件 | 相对基线缩短 30% 以上 |
| 修改 `common` 公共头 | 影响范围可解释 | 通过头文件分层减少无关重编译 |
| Repo A CI | 可复用已发布 Repo B 制品 | 不重复编译未变化组件 |
| configure | 不重复执行等价依赖发现 | 依赖发现集中且结果可追溯 |

若指标未达到，应先检查：

- 测试是否仍重复编译生产源码。
- QML/翻译代码生成是否仍挂在默认依赖链。
- 运行时 DLL 复制是否对每个目标重复执行。
- 公共头文件是否包含过多实现和第三方头。
- Repo A 是否误用了源码消费模式。

## 9. 风险与回滚

| 风险 | 影响 | 缓解与回滚 |
|---|---|---|
| 公共头路径调整 | 大量调用方编译失败 | 保留一个 minor 周期的转发头；独立提交可回滚 |
| MSVC/Qt ABI 不一致 | 链接失败或运行崩溃 | 制品按工具链和配置区分；manifest 强校验 |
| 静态库依赖收紧错误 | 最终链接缺符号 | install-tree consumer 覆盖每个组件组合 |
| UIToolkits 插件缺失 | 编译通过但应用无法启动 | 延后迁移；增加 QML import 和冷启动门禁 |
| IKap/libmodbus 不可再分发 | 组件包不完整 | 包内只发布允许制品；其余由部署环境提供并校验 |
| 双仓接口演进不同步 | Repo A 构建中断 | 语义化版本、最低/推荐版本矩阵和锁文件 |
| 一次改动范围过大 | 回归难定位 | 按 WP 独立提交；每个 WP 达标后再进入下一阶段 |

阶段 0—4 均在原仓完成，可普通 Git revert。阶段 5—6 期间不删除原仓代码；新仓失败时继续使用已验证的单仓模式。组件升级必须使用独立提交，问题发生时回退组件锁定版本，不回滚无关业务提交。

## 10. 里程碑与交付物

| 里程碑 | 工作包 | 交付物 |
|---|---|---|
| M0 基线可重复 | WP0 | 构建时间、测试结果、工具链和部署清单 |
| M1 构建图收敛 | WP1—WP2 | 无源码树副作用、应用核心目标、测试不重复编译生产源码 |
| M2 组件可安装 | WP3 | SZXComponents package、公共头和 consumer tests |
| M3 安装树可消费 | WP4 | 完全不访问组件源码的 PCB 构建证据 |
| M4 制品可发布 | WP5 | 版本化制品、manifest、版本锁和兼容矩阵 |
| M5 双仓切换 | WP6—WP7 | 两个独立仓库、CI、正式部署包和回滚记录 |

## 11. 最终验收清单

- [ ] 两个仓库均可从空构建目录独立 configure、build、test、install。
- [ ] Repo A 只通过 `find_package(SZXComponents CONFIG REQUIRED)` 消费 Repo B。
- [ ] Repo A 的 CMake 和源码不引用 Repo B 私有或源码目录。
- [ ] Repo B 不包含 PCB 业务命名、配置、数据库 schema 或模型路径。
- [ ] 所有导出 target 具有正确的 build/install interface。
- [ ] 所有安装公共头均可单独编译。
- [ ] 普通 configure/build 后工作区保持干净。
- [ ] Debug 与 Release/RelWithDebInfo 不混用。
- [ ] 组件包工具链、依赖版本和文件哈希可追溯。
- [ ] PCBDetect 编译、核心 UT、检测单元测试和模型集成测试通过。
- [ ] 部署目录可在干净机器冷启动并加载 QML 插件。
- [ ] 构建性能满足第 8 节门禁，未达目标项有数据和后续责任人。
- [ ] 原仓回滚通道保留至少一个正式发布周期。

## 12. 待评审决策

1. Repo B 正式名称是否使用 `szx-components`。
2. 组件制品使用内部通用制品库、Conan/vcpkg registry，还是版本化压缩包。
3. 首版是否只发布静态库，或同时发布 DLL。
4. `feature_manager` 是删除、冻结，还是在找到生产消费者后发布。
5. `UIToolkits` 进入首版组件包还是延后到 M4。
6. IKap、TensorRT、CUDA、MySQL、libmodbus 的再分发权限和安装责任。
7. ABI 兼容维度以及支持的最低 Qt、MSVC、Windows 和 GPU 版本。
8. 构建性能门禁由谁维护、在哪类 CI runner 上形成稳定基线。

## 13. 首个推荐提交序列

为避免第一批改动同时触碰包化和业务目标，建议从以下小步开始：

1. `[build|cmake|i18n] 将翻译更新移出默认构建链`
2. `[build|cmake|policy] 使用接口目标承载编译选项`
3. `[refactor|pcbdetect|build] 抽取应用核心编译目标`
4. `[test|pcbdetect|build] 测试改为链接应用核心目标`
5. `[refactor|detectengine|api] 移除应用对检测引擎私有头依赖`
6. `[build|components|install] 增加基础组件安装导出`
7. `[test|components|package] 增加安装树消费测试`

前五项完成后应重新测量构建性能，再决定包化时优先处理哪一个组件。
