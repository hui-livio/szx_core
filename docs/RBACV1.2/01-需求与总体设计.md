# RBAC V1.2 需求与总体设计

## 1. 背景

当前 `szx_admin` 第一阶段已经实现四个固定角色：

- `operator`；
- `engineer`；
- `admin`；
- `super_admin`。

角色到能力的映射编译在 `Policy.cc` 中，用户表直接保存角色字符串。该方案适合首期交付，但无法满足不同部署现场自行增加岗位、调整权限和限定管理范围的需求。

V1.2 的业务目标是让授权模型可配置，同时不降低第一阶段已经具备的认证、并发控制、审计和超级管理员保护能力。

第一阶段的用户表还存在 `uid + display_name` 与 `username + display_name` 两套互斥设计。由于 uid 和 username 都是登录标识，且用户只能拥有其中一个，这两套字段表达的是同一业务概念。V1.2 同时将其统一为一个登录标识，消除数据库、API、Repository 和前端的重复分支。

## 2. 用户故事

### 2.1 角色管理

- 作为超级管理员，我可以新增“质检员”“班组长”等自定义角色。
- 我可以修改角色名称、描述和权限集合，但角色 code 创建后不可修改。
- 我可以停用角色，使该角色下用户立即不能继续访问业务。
- 我可以归档没有用户引用的自定义角色，并且历史 code 不得复用。
- 我可以配置某个管理角色允许查看和管理哪些目标角色。

### 2.2 权限管理

- 我可以查看所有系统权限及其用途、来源、状态和被哪些角色使用。
- 我可以新增供业务 Client 使用的权限码，例如 `report.export`。
- 我可以修改自定义权限的名称、说明和模块分类。
- 我可以停用权限，使其立即从所有角色的有效权限中消失。
- 我可以归档未被角色引用的自定义权限。
- 我不能通过管理页面创建一个声称保护服务端接口、但后端没有实现校验点的权限。

### 2.3 用户分配

- 创建用户和修改用户角色时，角色选择来自后端，不再由前端写死。
- 管理员只能看到 `role_manage_scopes` 允许其管理的角色。
- 角色变更、角色停用、角色权限变化后，旧授权会话必须失效。

### 2.4 登录标识

- 创建用户时只填写一个“登录账号”，不再在 UID 和用户名两个输入框中二选一。
- `identifier_type=username/uid` 仅表示账号来源和界面标签，不决定不同的登录算法。
- 登录账号与显示名称（昵称）是不同概念：登录账号唯一且创建后不可修改，显示名称可重复且允许修改。
- UID 与用户名共用同一个不区分大小写的唯一命名空间，例如 `U10086` 与 `u10086` 不能属于两个用户。

## 3. 范围

### 3.1 本期包含

- 角色 CRUD（删除采用归档）；
- 权限 CRUD（删除采用归档）；
- 角色权限全量替换；
- 角色可管理范围全量替换；
- 用户绑定动态角色；
- 数据库驱动的权限判定；
- 角色与权限管理 Admin 页面；
- OpenAPI、错误码、安全审计、迁移和测试；
- V1.1 无 canonical 碰撞的数据自动迁移，并保持账号归属、密码、角色和状态不变；碰撞数据显式阻断并要求人工处置。
- 用户登录标识从四个可空列迁移为 `login_identifier`、`login_identifier_canonical` 和 `identifier_type`。

### 3.2 本期不包含

- 一个用户拥有多个角色；
- 用户级直接授权；
- Deny 权限、权限继承、嵌套角色；
- 数据行级权限、组织树、部门、租户和项目隔离；
- 基于属性、时间、IP、设备或表达式的 ABAC；
- 在线脚本或动态路由注册；
- SSO、MFA、外部目录同步；
- Redis、消息队列或跨服务授权中心；
- 面向第三方的公共 C++ SDK ABI 版本切换。
- 一个用户拥有多个登录标识；若未来需要同时支持工号、用户名和外部目录账号，应新增一对多身份表，不在 `users` 中继续增加可空列。

## 4. 核心概念

| 概念 | 定义 |
|---|---|
| Role | 用户承担的岗位；用户在 V1.2 中恰好绑定一个角色 |
| Permission | 稳定的能力码，例如 `user.read`、`report.export` |
| System permission | 后端代码或受控业务模块已经实现校验点的权限 |
| Custom permission | 管理员创建、由 Client 或业务模块消费的权限 |
| Effective permission | 角色已关联、权限 active、角色 active 时实际生效的权限 |
| Manage scope | 某角色允许管理的目标角色集合 |
| Protected resource | 不允许归档或改变安全身份的内置角色/权限 |
| Security floor | `super_admin` 不能被移除的一组恢复和 RBAC 管理权限 |
| Login identifier | 用户输入的唯一登录账号；username 与 UID 在存储和匹配上是同一概念 |
| Identifier type | 登录账号的来源标签，只能为 username/uid，不参与唯一性和匹配策略 |
| Display name | 显示名称或昵称，不参与登录，可重复且可修改 |

## 5. 授权模型

有效权限计算：

~~~text
用户有效
  = users.status == active
  AND role.status == active
  AND token.user_authz_version == users.authz_version
  AND token.role_authz_version == roles.authz_version

hasPermission(user, code)
  = 用户有效
  AND role_permissions 存在 (user.role_id, permission.id)
  AND permission.code == code
  AND permission.status == active
~~~

用户管理还必须额外满足目标范围：

~~~text
canManage(actor, target, requiredPermission)
  = hasPermission(actor, requiredPermission)
  AND role_manage_scopes 存在 (actor.role_id, target.role_id)
  AND 操作未违反自操作限制
  AND 操作未违反最后一个 active super_admin 保护
~~~

权限与范围必须同时成立。拥有 `user.update` 不代表能够修改所有角色的用户。

## 6. 自定义权限的执行边界

管理 API 只能创建 `enforcement=client` 的自定义权限。该权限会：

- 出现在权限目录；
- 可以分配给角色；
- 出现在 `GET /client/me/permissions`；
- 由 Admin/业务 Client 用于菜单、按钮和业务流程；
- 可由其他业务服务以明确的权限码进行服务端二次校验。

自定义权限不得使用 SZX Admin 保留前缀：`auth.`、`user.`、`role.`、`permission.`、`audit.`、`behavior.`、`system.`。保留前缀清单由后端代码和 OpenAPI 共同维护，防止自定义资源占用当前或后续服务端权限命名空间。

该权限不会：

- 自动生成 C++ 枚举；
- 自动注册 HTTP 路由中间件；
- 自动保护任意 `szx_admin` 接口；
- 替代业务服务自身的授权校验。

新增 `enforcement=server` 权限必须完成代码校验点、migration 种子、OpenAPI、审计和测试后随版本发布。管理 API 不接受此类型的创建请求。

## 7. 内置角色与安全底线

迁移后保留四个内置角色，其 `system_key` 固定：

| system_key | 默认 code | 保护规则 |
|---|---|---|
| operator | operator | 不可归档、不可修改 code |
| engineer | engineer | 不可归档、不可修改 code |
| admin | admin | 不可归档、不可修改 code |
| super_admin | super_admin | 不可归档、不可停用、不可修改 code，必须保留安全底线权限 |

角色显示名称和描述可以本地化修改。除安全底线外，内置角色的业务权限允许调整。

`super_admin` 安全底线至少包括：

- `user.read`、`user.create`、`user.update`、`user.status`、`user.unlock`；
- `user.password.reset`、`user.role.assign`；
- `role.read`、`role.create`、`role.update`、`role.status`、`role.archive`；
- `role.permission.assign`、`role.scope.assign`；
- `permission.read`、`permission.create`、`permission.update`、`permission.status`、`permission.archive`；
- `audit.read`。

任何 API 都不得移除这些权限。权限目录使用 `required_for_super_admin=true` 表示安全底线成员。

## 8. 状态模型

### 8.1 角色

~~~text
active <-> disabled
active/disabled -> archived
archived 为终态
~~~

- disabled：角色定义保留，角色下用户全部失去有效授权；
- archived：仅自定义且无用户引用时允许；code 永久占用；
- super_admin 不允许 disabled 或 archived。

### 8.2 权限

~~~text
active <-> disabled
active/disabled -> archived
archived 为终态
~~~

- disabled：关联关系保留，但不计入有效权限；
- archived：仅自定义且无角色引用时允许；
- 系统权限和安全底线权限不能归档；
- code 创建后不可修改且不可复用。

## 9. 授权版本与会话失效

V1.2 保留 `users.authz_version`，并新增 `roles.authz_version`。

| 变化 | user_authz_version | role_authz_version | Refresh token |
|---|---:|---:|---|
| 用户改密、状态变化、用户换角色 | +1 | 不变 | 撤销该用户全部 family |
| 角色权限集合变化 | 不变 | +1 | 无需批量删除；刷新时读取新版本 |
| 角色 manage scope 变化 | 不变 | +1 | 无需批量删除 |
| 角色 active/disabled 变化 | 不变 | +1 | disabled 时刷新被拒绝 |
| 权限 active/disabled 变化 | 不变 | 所有关联角色 +1 | 刷新时读取新版本 |
| 名称、描述变化 | 不变 | 不变 | 不影响 |

V1.2 access JWT 新增 `role_id` 与 `role_authz_version`。每次请求仍读取当前用户和角色状态并比对版本；JWT 中的角色 code 和权限列表均不作为授权事实。

部署 V1.2 后，缺少 `role_authz_version` 的旧 access token 默认返回 `401 / 2200`，客户端可使用有效 refresh token 换取 V1.2 token。这样无需等待旧 access token 自然过期。

## 10. 关键业务流程

### 10.1 新建角色

1. 校验调用者具备 `role.create`；
2. 校验 code 规范和永久唯一性；
3. 插入角色，初始 `version=1`、`authz_version=1`；
4. 可在同一请求提供权限和 manage scope；服务端锁定关联资源并校验；
5. 自动把新角色加入内置 super_admin 的 manage scope，并递增 super_admin 角色的 `version/authz_version`；
6. 写入可信安全审计 `role.created`；
7. 事务提交后返回完整角色。创建操作会使所有 super_admin 的旧 access token 失效，客户端应通过 refresh 获取新 token。

### 10.2 更新角色权限

1. 锁定调用者角色、目标角色和目标角色当前权限；
2. 校验 `If-Match`；
3. 校验目标权限存在、active 且允许分配；
4. 对 super_admin 校验安全底线；
5. 计算集合差异，新增/删除映射；
6. 仅在集合实际变化时递增 `version` 和 `authz_version`；
7. 同事务写 `role.permissions.changed` 审计，记录 added/removed code；
8. 旧 access token 在下一次请求时失效。

### 10.3 修改用户角色

1. 校验 `user.role.assign`；
2. 校验调用者对用户当前角色和目标角色均有管理范围；
3. 禁止给自己换角色；
4. 目标角色必须 active 且未 archived；
5. 更新 `users.role_id` 和兼容字段 `users.role`；
6. 递增用户 `version/authz_version`，撤销全部 refresh family；
7. 校验最后一个 active super_admin；
8. 写 `user.role.changed` 审计。

## 11. 总体架构

~~~mermaid
flowchart LR
    UI[Vue Admin] --> API[REST API /api/v1]
    CLIENT[业务 Client] --> API
    API --> AUTH[认证与 Token 校验]
    AUTH --> POLICY[AuthorizationService]
    POLICY --> USER[(users)]
    POLICY --> ROLE[(roles)]
    POLICY --> RP[(role_permissions)]
    POLICY --> P[(permissions)]
    POLICY --> SCOPE[(role_manage_scopes)]
    API --> RBACSVC[RoleService / PermissionService]
    RBACSVC --> ROLE
    RBACSVC --> P
    RBACSVC --> AUDIT[(security_audit_logs)]
~~~

Controller 只处理 HTTP；Service 负责授权、规则和事务；Repository 负责参数化 SQL。前端菜单只改善体验，后端始终独立鉴权。

## 12. 兼容性策略

### 12.1 保持兼容

- Base URL 继续使用 `/api/v1`；
- 用户请求中的 `role` 继续表示角色 code；
- User 响应保留 `role: string`，新增 `role_id` 和 `role_name`；
- `GET /client/me/permissions` 保留 `capabilities` 字段及已有 12 个 code；
- 现有四个角色迁移后 code 不变；
- 第一阶段所有用户接口路径和成功状态码不变。
- 登录接口继续使用已有 `identifier` 请求字段。
- `/api/v1` 创建用户在兼容期接受旧 `uid` 或 `username` 请求字段，但数据库只写统一登录标识；响应中的旧字段由 `identifier_type` 动态生成，不再对应旧数据库列。
- `2207 USER_IDENTITY_ONE_OF_REQUIRED` 保留原数值，仅用于旧格式请求的互斥错误；新格式请求使用通用 `2206` 校验错误。

### 12.2 行为变化

- OpenAPI 不再把 role 限制为四值 enum，而改为符合格式的字符串并提示从角色接口获取；
- 管理员可管理的角色不再由 code 判断，而由 `role_manage_scopes` 决定；
- 权限响应改为数据库动态结果；
- V1.1 access token 在 V1.2 部署后需要 refresh；
- V1.2 schema 已删除 V1.1 依赖的 uid/username 列，不能只回滚二进制；标准回滚必须恢复上线前数据库备份。
- 新 User DTO 以 `login_identifier` 和 `identifier_type` 为正式字段；`uid/username` 是 `/api/v1` 兼容别名，未来只能在新的破坏性 API 版本中移除。
- UID 从区分大小写改为与 username 相同的不区分大小写匹配。升级前检测到大小写折叠冲突时 migration 必须失败，不自动合并或重命名用户。

## 13. 非功能要求

- 授权判定 P95 新增开销目标不超过 2 ms（不含网络和数据库连接等待）；
- 角色详情最大 500 个权限；单次替换请求体不超过 64 KiB；
- 角色和权限列表 page_size 最大 100；
- 所有写操作使用 `If-Match` 和事务；
- 所有 RBAC 变更写入 `security_audit_logs`；
- 不在 API 中返回数据库、异常、SQL 或第三方诊断文本；
- code 使用 ASCII 小写稳定标识，显示名称使用 UTF-8；
- 不记录 token、密码、Cookie 或完整授权请求体。
- 登录标识原始值最多 64 个 Unicode 字符、512 字节；规范化规则由单一后端组件实现，数据库只对 canonical 列做精确唯一约束。

## 14. 决策记录

| 决策 | 采用方案 | 未采用方案与原因 |
|---|---|---|
| 用户角色数量 | 单角色 | 多角色会引入权限合并、来源解释和目标范围冲突，延后 |
| 管理范围 | 显式关系表 | 数字等级难表达非树形组织，且修改等级可能意外提权 |
| 删除 | 归档 | 硬删除破坏审计可追溯和 code 永久唯一性 |
| 服务端动态权限 | 不允许纯配置创建 | 没有代码校验点的“服务端权限”是安全假象 |
| 会话失效 | 用户版本 + 角色版本 | 批量递增所有用户版本在大角色上锁行过多 |
| API 路径 | 扩展 v1 | 当前变更可通过新增资源和响应字段保持兼容 |
| 用户登录标识 | 单列 + 来源类型 | uid/username 都用于登录且互斥，继续保留两套列只会放大查询、约束和 API 分支 |
| 标识大小写 | 统一不区分大小写 | 继续按类型采用不同规则会让 identifier_type 重新变成登录算法分支，并保留跨类型冲突复杂度 |
