# RBAC V1.2 后端代码架构优化设计

> 文档版本：V1.2-draft
> 编制日期：2026-09-24
> 代码基线：`tools/szx_admin` 第一阶段实现；审查记录基线 `e40f2c8`
> 关联文档：[后端与授权实现设计](04-后端与授权实现设计.md)

## 1. 文档目的

本文档记录对 `szx_admin` 后端现有实现的架构审查结论，并定义进入 RBAC V1.2 前的代码结构调整方案。

目标是：

1. 让模块职责清晰，便于阅读和维护；
2. 让角色、权限和用户身份模型的 API 改动集中在有限范围；
3. 降低数据库锁、重复查询和日志列表查询对性能的影响；
4. 只引入具有明确业务行为的对象，不建立通用框架式抽象。

本文档是代码结构设计，不改变 [RESTful API 接口设计](03-RESTful-API接口设计.md) 中已经确定的 HTTP 兼容策略。

## 2. 当前实现审查

### 2.1 已有基础

- `Result<T> + ErrorCode` 已形成稳定的错误传播方式；
- HTTP 传输层能够统一处理异常和错误响应，敏感诊断不会直接返回客户端；
- 用户写操作已经使用事务、`If-Match` 版本和审计写入；
- `BehaviorEventWriter` 已具备有界队列、批量提交、重试和故障状态；
- 数据库仓储已经将密码读取与用户管理读取分开，降低了凭据暴露范围。

这些能力继续保留，架构调整围绕边界收敛和动态授权展开。

### 2.2 主要问题

#### A. 数据库执行被进程级锁限制

`DatabasePool::withConnectionImpl()` 在整个连接回调期间持有 `ormMutex`，而 `OrmConnection` 的每次 SQL 调用也会获取同一把锁：

- `tools/szx_admin/src/infra/Database.cc`
- `tools/szx_admin/src/infra/OrmConnection.h`
- `tools/szx_admin/src/infra/OrmRuntime.h`

在当前实现下，连接池大小不等于 SQL 并发度。一个请求等待连接时，还可能阻塞其他请求使用已有连接。必须先采集锁等待和 SQL 执行指标，再决定移除回调级锁、按连接隔离锁，或更换数据库执行器实现。

#### B. 固定角色策略散落在业务代码

`Policy.cc` 固化了四个角色、权限位掩码和管理范围。`UserService`、`UserLifecycle`、审计服务、行为服务和用户仓储都直接依赖角色字符串或固定角色数组。

新增一个角色会同时影响：

- 权限矩阵和目标角色规则；
- 用户创建、列表、角色分配和状态变更；
- SQL 中固定四个角色占位符；
- HTTP DTO 和前端枚举；
- 对应测试 Fake 和测试数据。

这与 V1.2 的数据库驱动 RBAC 目标冲突。

#### C. `DatabaseConnection` 是聚合式大接口

当前接口同时提供登录、用户、审计、行为、日志维护仓储，以及事务、migration、bootstrap 和连接生命周期操作。仓储通过可空裸指针返回，导致每个 Service 都重复进行空指针检查。

新增 `RoleRepository` 或 `PermissionRepository` 时，会扩大公共头文件和所有测试替身的变更范围。migration/bootstrap 也不应与业务仓储访问共用同一个业务接口。

#### D. HTTP Handler 承担过多职责

`UserHandler.cc` 约 600 行，同时负责路由注册、CORS、请求解析、字段白名单、DTO 构造、Service 调用和 JSON 序列化。`Routes.cc` 又重复构造用户响应对象。

目前每个响应函数都自行捕获异常和映射错误，路由注册还重复实现 origin 检查、CORS 和 OPTIONS 注册。新增角色或权限接口会继续复制这套代码。

#### E. 鉴权和当前用户读取重复

`UserService`、`AuditService`、`BehaviorEventService` 都重复执行 JWT 校验、用户查询、状态判断和 `authz_version` 判断。行为事件写入路径每次入队前都要查询一次当前用户。

重复逻辑会产生授权规则漂移，也会增加单请求数据库往返次数。

#### F. 用户身份模型仍有双分支

`UserRow`、`LoginUser`、`NewUser` 和数据库表继续同时保存 `uid` 与 `username`。登录、创建用户、跨字段冲突检测和列表搜索均保留两套分支。

其中用户创建的冲突检查还需要扫描 UID canonical 值，数据量增大后会放大延迟。V1.2 已确定的 `login_identifier + identifier_type` 统一模型应优先落实到内部代码结构。

#### G. 列表查询存在重复和 N+1 访问

用户、审计和行为列表通常先执行 `COUNT(*)`，再执行分页查询。审计和行为详情还会按记录、按分块读取 JSON。用户列表使用固定四角色参数和多个可选条件 OR 表达式。

需要通过执行计划确认索引效果，并在 V1.2 中取消固定角色参数和逐记录详情查询。

#### H. 构建目标边界过宽

`szx_rbac_infra` 包含几乎全部后端源文件，HTTP、业务、策略、仓储和数据库适配器都集中在一个静态库中。公共 `Database.h` 的改动容易触发多个模块重新编译，也不利于确定依赖方向。

#### I. 领域 Service 测试接缝不足

现有测试重点在 HTTP、JWT、基础设施和工具边界。当前测试目标没有直接覆盖 `UserService` 的授权矩阵、用户生命周期和后续角色/权限 Service。

需要通过窄接口和事务测试替身，增加不依赖真实 MySQL 的应用层测试。

## 3. 目标架构

```text
HttpTransport
    -> Route Modules
    -> Request DTO / Response Mapper
    -> Application Services
         -> AuthorizationService
         -> DatabaseUnitOfWork
              -> Narrow Repositories
              -> MySQL Adapter
```

依赖方向固定为：

```text
HTTP -> Application -> Repository Contract -> Infrastructure
```

业务层不依赖 MySQL 查询文本、HTTP Header 或 JSON 结构；Repository 不负责 HTTP 错误和权限判定；HTTP 层不直接读取数据库。

## 4. 模块和对象设计

### 4.1 HTTP 层

建议目录：

```text
src/http/
  AuthRoutes.h/.cc
  UserRoutes.h/.cc
  RoleRoutes.h/.cc
  PermissionRoutes.h/.cc
  AuditRoutes.h/.cc
  BehaviorRoutes.h/.cc
  RequestDecoder.h/.cc
  ResponseMapper.h/.cc
```

路由模块只做四件事：

1. 从 `HttpRequest` 提取请求 DTO；
2. 调用 Application Service；
3. 将 `Result<T>` 映射为响应；
4. 交给统一的 CORS、request-id 和异常边界处理。

不建立通用 Controller 基类。只增加一个小型路由绑定辅助函数，集中处理受保护路由、CORS 和 OPTIONS 注册。

### 4.2 `AuthorizationService`

该对象拥有授权行为：

- 验证 access token；
- 加载当前用户和角色；
- 校验用户状态、角色状态和用户/角色授权版本；
- 根据稳定权限 code 判断能力；
- 根据 `role_manage_scopes` 判断目标范围；
- 返回已授权的 actor 或 mutation 上下文。

建议内部类型：

```cpp
struct AuthorizedActor final
{
    UserRow user;
    RoleRow role;
};

struct AuthorizedMutation final
{
    UserRow actor;
    UserRow target;
    std::uint64_t activeSuperAdmins{};
};
```

用户变更统一通过一个行为接口完成：

```cpp
Result<AuthorizedMutation> authorizeUserMutation(
    const ActorContext& context,
    std::string_view targetUserId,
    std::string_view permissionCode,
    std::uint32_t targetVersion,
    std::optional<std::string_view> destinationRoleCode = std::nullopt);
```

`UserService` 不再调用 `POLICY::allows()`、`POLICY::mayTarget()`，也不再维护四角色数组。

### 4.3 `DatabaseUnitOfWork`

建议将事务和仓储生命周期封装为一次数据库工作单元：

```cpp
class DatabaseUnitOfWork
{
public:
    UserRepository& users();
    LoginRepository& sessions();
    RoleRepository& roles();
    PermissionRepository& permissions();
    AuditRepository& audit();
    BehaviorEventRepository& behaviorEvents();
    LogMaintenanceRepository& logMaintenance();

    Result<void> begin();
    Result<void> commit();
    Result<void> rollback();
};
```

具体实现留在 `infra`。业务 Service 拥有一次工作单元的事务边界，成功提交或失败回滚由 Service 明确决定；`DatabasePool` 只负责借出和归还连接。业务层只看到必要的仓储引用，不再处理可空仓储指针。

角色、权限和用户变更使用确定的锁顺序：资源 id 升序，再锁关联集合；角色授权版本、用户授权版本和审计写入在同一事务中完成。行为事件继续使用异步 `BehaviorEventWriter`，不把客户端遥测写入强行并入用户变更事务。日志清理使用独立维护工作单元。

migration 和 bootstrap 使用独立的 `MigrationConnection`、`BootstrapStore` 接口，不通过业务工作单元访问。

### 4.4 RBAC Service

只增加有明确业务行为的 Service：

```text
AuthorizationService  授权判定、用户/角色版本校验、管理范围判定
RoleService           角色 CRUD、权限集合、管理范围、归档和审计
PermissionService     权限 CRUD、状态、引用检查和授权版本递增
UserService           用户生命周期和用户 DTO
```

不创建 `BaseService`、`GenericManager` 或通用 CRUD 框架。角色和权限的差异由各自 Service 明确表达。

### 4.5 稳定权限标识

服务端调用点使用字符串权限码常量：

```cpp
namespace SZX::ADMIN::RBAC::PERMISSIONS
{
inline constexpr std::string_view UserRead{"user.read"};
inline constexpr std::string_view RoleRead{"role.read"};
inline constexpr std::string_view RolePermissionAssign{"role.permission.assign"};
}
```

代码只依赖权限 code，不依赖数据库权限 id，也不把动态角色矩阵编译进代码。服务端权限由代码注册并通过 migration 落库；自定义权限仍只用于 Client/业务模块消费，不会自动保护后端路由。

服务端权限注册表必须同时提供：

- code、模块和安全底线标记；
- migration seed 生成或一致性校验输入；
- readiness 校验所需的完整清单；
- 与生产校验点的测试映射。

代码注册表、migration 和数据库中的 server 权限不一致时，服务启动 readiness 失败。权限状态变化必须锁定关联角色，并在同一事务中递增受影响角色的 `version/authz_version`；实际集合未变化时保持幂等，不递增版本。

### 4.6 现有代码到目标模块的迁移映射

| 当前代码 | 目标位置 | 迁移原则 |
|---|---|---|
| `Routes.cc`、`UserHandler.cc` | `http/*Routes`、`RequestDecoder`、`ResponseMapper` | 先移动路由和序列化，再收敛通用边界 |
| `UserService.cc`、`UserLifecycle.cc` | `application/UserService` | 保留用户业务事务，授权统一进入 `AuthorizationService` |
| `Policy.cc` | `application/AuthorizationService` + `rbac/PermissionCodes.h` | 删除角色矩阵，保留稳定权限 code |
| `Database.h`、`Database.cc` | `persistence/DatabaseUnitOfWork` | 公共头文件只保留池配置和生命周期 |
| `infra/*Repository.cc` | `persistence` | Repository 只负责数据访问和稳定错误分类 |
| `AuditService`、`BehaviorEventService` | `application/audit`、`application/telemetry` | 保留事务审计与异步行为事件的不同语义 |

### 4.7 本轮代码落地状态

本轮已完成事务边界收敛和动态 RBAC 第一批落地，作为后续身份模型迁移的兼容接缝：

- 新增 `src/rbac/AuthorizationService`，集中处理 access token、用户状态、`authz_version`、能力码和管理范围判断；
- 新增 `src/rbac/PermissionCodes.h`，用户、审计和行为服务只依赖稳定权限码，不再直接依赖 `POLICY::Capability`；
- `UserService`、用户生命周期、`AuditService` 和 `BehaviorEventService` 统一复用授权对象；
- 可管理角色列表由授权边界投影，用户服务不再维护固定角色数组；
- 新增不可变 migration 6，创建 `roles`、`permissions`、`role_permissions`、`role_manage_scopes` 并种子系统角色、系统权限和默认范围；
- 新增不可变 migration 7，以增量方式增加并回填 `users.role_id`、`login_identifier`、`login_identifier_canonical`、`identifier_type`；旧列仍保留，用户创建已开始双写正式字段；
- 新增 `RoleRepository`、`PermissionRepository` 运行时读写契约和 MySQL 适配器，`DatabaseUnitOfWork` 暴露窄仓储访问；
- 用户、审计和行为服务在生产连接具备 RBAC 仓储时优先使用数据库权限与管理范围，旧测试替身仍可走 `Policy` 兼容路径；
- 新增 `RoleService`、`PermissionService` 与角色/权限管理路由，支持角色和 Client 权限的列表、创建、资料更新、启停/归档，以及角色权限和管理范围集合替换；
- 集合替换使用同一事务、`If-Match` 版本校验和授权版本递增；实际集合不变时不写版本；
- `OrmConnection` 已记录执行槽等待，并对超过 5ms 的 ORM 操作输出受控慢操作指标，为 M4 压测和锁策略评估提供观测点；
- `/ready` 已增加 RBAC catalog gate，校验内置角色、代码注册的 server 权限、super_admin 安全底线和管理范围覆盖；
- 登录边界已增加 `LoginIdentifier`/`IdentifierType` 统一投影和新旧字段互斥适配；用户创建接口也接受正式的 `login_identifier + identifier_type`，migration 7 已完成正式字段增量回填和创建双写，登录读路径切换、冲突校验和旧列下线仍留待 M3 后续步骤；
- 角色/权限归档 DELETE 路由已与状态更新共用同一 Service 行为和版本保护。
- 第一阶段 `Policy` 仍作为缺少动态仓储时的兼容适配器保留；
- `role_id`、`login_identifier` 身份迁移、readiness 对身份列的完整校验、审计事件细化和 ORM 锁策略切换仍属于后续 M3/M4，不在本阶段隐式完成；
- 暂不移除 `DatabaseConnection` 聚合接口，也不直接缩小 ORM 全局锁，避免未经驱动线程安全验证引入回归。

本节记录的是当前代码已落地的边界，不改变 M1–M4 的目标架构和验收条件。

## 5. 用户身份统一方案

### 5.1 内部模型

```cpp
struct LoginIdentifier final
{
    std::string displayValue;
    std::string canonicalValue;
    IdentifierType type;
};
```

登录、创建用户、migration 回填和冲突检测统一调用一个规范化组件。核心仓储只查询：

```text
login_identifier
login_identifier_canonical
identifier_type
```

不再执行 `uid OR username` 查询，也不再扫描全部 UID 做跨字段冲突检查。唯一性由 canonical 字段上的唯一索引保证，业务层负责将唯一键冲突映射为 `UserIdentityConflict`。

### 5.2 HTTP 兼容

`/api/v1` 保留旧字段的兼容适配：

- 新请求优先使用 `login_identifier + identifier_type`；过渡期仍允许 `uid` 或 `username` 二选一，且两种格式禁止混用；
- Handler 将两种格式都转换为 `LoginIdentifier`；用户创建的正式格式已经贯通至 Service，旧格式仅作为 HTTP 兼容输入；
- Service、Repository、JWT 和数据库只使用统一模型；
- 响应可以继续返回 `uid`、`username` 兼容别名，同时增加正式身份字段。

这样 HTTP 兼容不会把两套身份模型继续带入业务代码。

兼容矩阵以 [RESTful API 接口设计](03-RESTful-API接口设计.md) 为唯一规范：

| 客户端请求 | 内部转换 | 响应兼容字段 | 处理规则 |
|---|---|---|---|
| `login_identifier + identifier_type` | 直接构造 `LoginIdentifier` | 按 `identifier_type` 生成对应正式字段 | 新格式不能与旧字段混用 |
| 仅 `uid` | `identifier_type=uid` | 返回 `uid` 别名 | 兼容输入，后续返回弃用提示 |
| 仅 `username` | `identifier_type=username` | 返回 `username` 别名 | 兼容输入，后续返回弃用提示 |
| 同时出现 uid/username，或新旧字段混用 | 不构造业务 DTO | `2207` 或 `2206` | 直接拒绝 |

正式字段只返回 `login_identifier`、`identifier_type`、`role_id`、`role_name` 等新模型字段。V1.1 access token 缺少 V1.2 角色版本 claim 时按 04 号文档 fail closed；新 JWT 中的 `role` 只用于显示和诊断，不作为授权事实。

## 6. 数据库和性能设计

### 6.1 ORM 锁优化

第一阶段先增加以下指标：

- ORM 全局锁等待时间；
- 数据库连接池等待时间；
- SQL 执行时间和事务持有时间；
- 连接失效、重连和不可复用次数；
- 请求队列等待与数据库错误码。

确认驱动线程安全后，优先将锁缩小到单连接操作。若驱动只能进程级串行，则改为显式数据库执行器并据此设置容量，避免使用无法提供并发的连接池配置。

### 6.2 查询策略

- 角色列表使用 `role_id` 或关联表查询，不再固定四个角色占位符；
- 可选条件只在存在时拼接受控 SQL 片段，外部值始终参数化；
- 用户和日志列表保留 `page/page_size` 兼容参数，同时评估 `(created_at, id)` keyset 分页；
- `COUNT(*)` 与数据查询的代价通过执行计划和指标评估，必要时增加轻量 count 模式；
- 审计和行为详情设置单条响应上限，避免按记录、按分块 N+1 查询；
- 为 `users`、`roles`、`role_permissions`、`role_manage_scopes` 和日志筛选条件建立并验证组合索引。

### 6.3 授权缓存

第一版优先保证正确性。同一请求内复用 `AuthorizedActor`，避免每个 Service 重复加载用户。

达到性能阈值后再增加有界进程内缓存：

```text
key   = role_id + role_authz_version
value = active permission codes
TTL   <= 60s，容量显式配置
```

版本变化后自然失效，缓存失败回退数据库，禁止缓存失败时放行。

## 7. CMake 目标调整

建议将当前单一 `szx_rbac_infra` 拆为三个边界：

```text
szx_admin_application  Application Service、DTO、授权契约
szx_admin_persistence   DatabasePool、UnitOfWork、Repository 实现
szx_admin_http          HttpTransport、Routes、Handler、Mapper
```

`szx_admin_service` 只负责配置、依赖组装和进程生命周期。无需将每个类拆成独立库。

公共 include 只保留确有外部消费者的稳定类型。当前应用内部 C++ API 不新增 DLL ABI 承诺，HTTP 兼容通过 `/api/v1` 和 OpenAPI 管理。

迁移期间先允许新文件继续接入现有构建目标，以降低一次性改动风险；完成 M1 边界收敛后再建立上述三个 target。本文档的最终 target 依赖关系覆盖 04 号文档中“继续使用单一 target”的过渡性约定。

## 8. 实施阶段

### M0：基线和指标

- 记录 ORM 锁、连接池和 SQL 延迟；
- 固化现有 HTTP、认证、用户生命周期和审计测试；
- 增加 `UserService` 授权矩阵测试；
- 确认 ormpp/MySQL 的线程安全边界。

出口条件：获得至少一组并发基线，包括吞吐、P95 延迟、数据库锁等待和连接池等待。

### M1：边界收敛

- 建立 `DatabaseUnitOfWork`；
- 将 `DatabaseConnection` 下沉到 infra；
- 增加统一 Request DTO、Response Mapper 和路由绑定辅助；
- 拆分 Auth/User/Audit/Behavior 路由模块；
- 保持现有 HTTP 响应格式不变。

出口条件：新增一个普通用户字段只需修改 DTO、Service 投影和 Mapper，不需要修改全部 Handler。

### M2：授权内核

- 实现 `AuthorizationService`；
- 增加 `RoleRepository`、`PermissionRepository`；
- 使用稳定权限 code 替换 `Policy::allows` 和 `mayTarget`；
- 用户、角色、权限授权版本按事务更新；
- 旧用户接口通过兼容适配层继续工作。

出口条件：新增一个自定义角色只产生数据库数据变化，不需要修改固定角色矩阵。

### M3：身份模型迁移

- 引入 `LoginIdentifier`；
- 完成旧字段数据校验、冲突阻断和回填；
- 切换登录、用户创建、搜索、审计和行为 JOIN；
- 保留 `/api/v1` 的 `uid/username` 兼容字段。
- 迁移前执行唯一性碰撞报告并完成备份；双读校验通过后再删除旧列；失败时按 07 号文档恢复数据库备份，禁止只回滚二进制。

出口条件：登录、创建、唯一性和大小写规范化全部使用同一实现。

### M4：查询和并发优化

- 根据执行计划调整索引和查询构造；
- 消除日志详情 N+1；
- 完成 ORM 锁策略切换或执行器隔离；
- 进行连接池、并发请求、角色权限变更和日志写入压测。
- 固化压测环境、数据规模、并发度、统计窗口和基线提交，记录 P50/P95/P99、吞吐、ORM 锁等待、连接池等待、SQL 次数和缓存命中率。

出口条件：在相同环境和数据规模下，P95/P99、吞吐、ORM 锁等待和连接池等待不得比 M0 基线恶化 10% 以上；单页日志查询不得产生按记录增长的详情 SQL；旧接口无回归。若业务目标需要更严格阈值，在 M0 评审时冻结具体数值。

## 9. 验收标准

### 可维护性

- HTTP、Application、Repository、Infrastructure 依赖方向清晰；
- Handler 不直接包含 SQL、权限矩阵和数据库状态判断；
- 用户、角色、权限响应映射各有唯一实现；
- 不存在通用 CRUD 基类或跨领域 Manager。

### API 改动范围

- 新增角色或权限不修改固定角色枚举和位掩码；
- 新增用户展示字段只影响 DTO、Service 投影和 Mapper；
- `/api/v1` 旧字段和错误码保持兼容；
- 角色/权限管理接口使用 `If-Match` 和版本冲突保护。

### 性能

- ORM 锁等待可观测，连接池容量与实际并发能力一致；
- 授权同一请求只加载一次 actor；
- 角色权限查询有索引或有界缓存；
- 日志列表不产生按记录的详情查询；
- 角色数量增长不会引入固定四角色 SQL 参数限制。
- 发布前压测必须报告 P50/P95/P99、吞吐、SQL 次数、ORM 锁等待、连接池等待和授权缓存命中率；缺少基线或数据规模的结果不能作为通过依据。

### 安全和错误契约

- 角色和权限变更会递增关联授权版本；
- 最后一个 active `super_admin` 保护保持不变；
- Repository 不向 Service/HTTP 返回 MySQL 原始诊断；
- 数据库、授权和传输错误统一映射到模块错误码。
- server 权限注册表、migration seed、OpenAPI 和 readiness 清单必须通过一致性校验。
