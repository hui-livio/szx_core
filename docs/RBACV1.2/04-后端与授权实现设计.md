# RBAC V1.2 后端与授权实现设计

## 1. 当前改造点

第一阶段的主要耦合点：

- `Policy.h/.cc`：`Capability` 枚举、固定 code 数组、四角色位掩码和 `mayTarget()`；
- `UserService`：按角色字符串判断能力和目标范围；
- `UserRepository`：UserRow 只有 role 字符串；
- `UserRepository/LoginRepository/Identifier`：uid 与 username 分列、分支规范化和跨字段冲突查询；
- `LoginService/JwtService`：token 只有用户 authz_version；
- `UserHandler`：User DTO 未返回角色 id/name；
- migration：`users.role` 只有四值 CHECK；
- 前端：固定 Role 联合类型和角色中文映射。

V1.2 不在 `Policy.cc` 中维护动态角色。稳定的“所需权限 code”仍由调用点定义，动态的“角色是否拥有 code”由数据库驱动。

## 2. 模块划分

建议在 `tools/szx_admin/src` 新增：

~~~text
rbac/
  AuthorizationService.h/.cc
  RoleService.h/.cc
  PermissionService.h/.cc
  RoleHandler.h/.cc
  PermissionHandler.h/.cc
  RbacValidation.h
infra/
  RoleRepository.h/.cc
  PermissionRepository.h/.cc
~~~

公共 include 仅保留确有外部消费者的稳定类型。当前 RBAC REST 实现是应用内部模块，不为本次改造引入 C++ `inline namespace v2`，也不承诺新增 DLL ABI；HTTP 契约通过 `/api/v1` 和 OpenAPI 管理。若未来抽出公共 C++ SDK，再单独建立版本化 public API。

## 3. 稳定权限标识

服务端调用点使用稳定字符串常量，而不是数据库整数或自由输入：

~~~cpp
namespace SZX::ADMIN::RBAC::PERMISSIONS
{
inline constexpr std::string_view UserRead{"user.read"};
inline constexpr std::string_view RoleRead{"role.read"};
inline constexpr std::string_view RolePermissionAssign{"role.permission.assign"};
}
~~~

要求：

- 常量只定义 code，不定义角色矩阵；
- 每个 server 权限至少有一个生产校验点；
- migration 中的 system 权限 code 与常量有一致性测试；
- 未注册或缺失的 server 权限 fail closed，并令 readiness 失败；
- 不把权限 id 编译进代码。

## 4. AuthorizationService

### 4.1 职责

- 验证 access token；
- 加载当前用户和角色；
- 校验用户/角色状态；
- 比对 user/role authz_version；
- 校验所需 permission code；
- 对用户目标操作校验 role_manage_scopes；
- 返回经过授权的 Actor，不返回诊断文本。

建议返回内部类型：

~~~cpp
struct AuthorizedActor final
{
    UserRow user;
    RoleRow role;
};
~~~

接口示意：

~~~cpp
Result<AuthorizedActor> authorize(
    const ActorContext &context,
    std::string_view requiredPermission,
    AuthorizationMode mode = AuthorizationMode::Read);

Result<AuthorizedMutation> authorizeUserMutation(
    const ActorContext &context,
    std::string_view targetUserId,
    std::string_view requiredPermission,
    std::uint32_t targetVersion,
    std::optional<std::string_view> destinationRoleCode = std::nullopt);
~~~

### 4.2 请求鉴权链

~~~text
Bearer
 -> JwtService verify signature/iss/aud/exp
 -> load user by sub
 -> load role by users.role_id
 -> user.status == active
 -> role.status == active
 -> token.user_authz_version == users.authz_version
 -> token.role_authz_version == roles.authz_version
 -> role has active required permission
 -> optional manage-scope and target checks
 -> handler/service operation
~~~

任何一步失败均不信任 JWT 中的 role code。身份/版本失败返回 AuthRequired；已认证但无权限或 scope 返回 Forbidden；资源是否存在的返回顺序保持现有防枚举策略。

## 5. Repository 接口

### 5.1 RoleRepository

至少提供：

- `findById/findByCode`；
- `list/count`；
- `lockById`；
- `insert/updateProfile/updateStatus/archive`；
- `permissions/replacePermissions`；
- `manageableRoles/replaceManageScopes`；
- `hasManageScope`；
- `countUsers`；
- `incrementAuthzVersionsByPermission`；
- `loadRoleOptionsForActor`。

### 5.2 PermissionRepository

至少提供：

- `findById/findByCode`；
- `list/count`；
- `lockById`；
- `insert/updateProfile/updateStatus/archive`；
- `countRoles`；
- `listByRole`；
- `hasActivePermission(roleId, code)`；
- `loadActiveCodes(roleId)`。

### 5.3 SQL 规则

- 所有外部值参数化；
- 排序字段通过枚举白名单映射，不能拼接用户输入；
- code 冲突映射为模块错误码；
- 集合替换不逐项自动提交；
- 列表聚合避免 N+1；
- Repository 不返回 MySQL 错误文本到 Service 结果；
- 异常在数据库边界捕获，原始诊断只写受控运行日志。

## 6. Service 事务

### 6.1 RoleService

负责：

- code/name/description 校验；
- 内置角色保护；
- 超管安全底线；
- role version 与 authz_version 更新；
- 权限/范围集合差异；
- 用户引用检查；
- 安全审计。

归档角色会删除以该角色为 target 的 manage scope。RoleService 必须锁定所有受影响的 manager roles，并对它们递增 version/authz_version，使旧 token 立即失效。

集合替换算法：

1. 校验输入 UUID、数量、重复；
2. 按 id 排序；
3. 锁定角色及所有目标资源；
4. 校验 If-Match；
5. 读取 current 集合；
6. 计算 added/removed；
7. 无变化则直接返回，不写版本和审计 success 变更事件；
8. 应用差异；
9. `version++`、`authz_version++`；
10. 写审计并提交。

### 6.2 PermissionService

负责：

- 只允许创建 custom/client 权限；
- 拒绝自定义权限使用 SZX Admin 保留前缀；
- system/custom 保护规则；
- permission version；
- 权限 active/disabled 状态变化时锁定并递增关联角色授权版本；
- 引用检查和审计。

权限状态变化不能只更新 permissions.status，否则已签发 token 的角色版本没有变化。停用和重新启用都必须在同一事务更新关联角色。

### 6.3 UserService 改造

- 注入 `AuthorizationService`；
- 移除 `POLICY::allows`、`POLICY::mayTarget` 和四角色数组；
- UserRow 用 login_identifier/identifier_type 替换 uid/username，并增加 role_id、role_name、role_status、role_authz_version；
- list/get/create/update/status/unlock/assign/reset 都按权限 code 和 scope 鉴权；
- CreateUserInput 正式字段改为 loginIdentifier + identifierType；Handler 单独适配旧 uid/username 请求，Service 和 Repository 不保留两套输入模型；
- 登录标识规范化收敛到一个组件，登录、创建、migration 回填和测试必须复用同一实现；
- LoginRepository 只按 login_identifier_canonical 查询，不再执行 uid/username OR 查询或跨字段冲突探测；
- 用户搜索统一查询 login_identifier/display_name；
- AuditRepository/BehaviorEventRepository 的用户 JOIN 改为读取 login_identifier；Handler 同时生成正式账号字段和 V1 兼容别名；
- create/assignRole 按 role code 查找并写 role_id + role；
- password policy 不再由 role code 推断。V1.2 统一服务端账号密码最低规则，前端角色差异规则移除或后续改为角色配置项；本期建议所有角色统一为至少 8 字符且包含字母和数字；
- 最后一个 super_admin 使用 `roles.system_key` + active 用户状态判断。

## 7. JWT 和认证更新

access token claims：

| Claim | 来源 | 说明 |
|---|---|---|
| sub | users.id | 用户身份 |
| authz_version | users.authz_version | 保持原字段 |
| role_id | users.role_id | 新增 |
| role_authz_version | roles.authz_version | 新增 |
| role | roles.code | 可保留用于显示/诊断，不作为授权事实 |

登录和 refresh：

- 登录请求字段仍为 `identifier`，规范化为统一 login_identifier_canonical 后精确查询；
- 在事务或一致性读中加载用户与角色；
- 角色非 active 时使用 AuthInvalidCredentials（登录）或 AuthRequired（refresh），不泄露角色状态；
- refresh 签发前读取最新 role_authz_version；
- V1.1 access token 缺失新 claim 时 fail closed；
- refresh token 表无需增加角色版本快照。

`JwtService` 公共输入结构若属于内部应用接口，可兼容新增字段；若已被外部 C++ 消费，应新增结构版本而不是破坏已发布布局。实施前通过 include 和链接搜索确认消费者。

## 8. 缓存策略

第一版优先保证正确性：

- 每次授权通过数据库验证用户/角色版本和单个权限；
- 不引入跨请求全量权限缓存；
- 数据库连接池和索引满足当前规模；
- 同一 HTTP 请求内复用 AuthorizedActor，避免每层重复查询。

达到性能阈值后可增加进程内有界缓存：

~~~text
key = role_id + role_authz_version
value = sorted active permission codes
TTL <= 60s, capacity 显式配置
~~~

由于 key 含 role_authz_version，变更后旧缓存自然不可命中。缓存失败必须回退数据库，不得默认放行。多实例无需广播失效。

## 9. 错误契约

错误生产链：

~~~text
MySQL/ormpp
 -> Repository: Database* 或唯一键分类
 -> Role/Permission/User Service: 2227–2234 等业务码
 -> Handler: RestApi::error
 -> HTTP integer code + 安全默认消息
 -> Admin 前端集中翻译
~~~

规则：

- admin 模块拥有 2200–2299 错误域，本次直接追加，不重复加 offset；
- 不把 SQL、`what()`、约束名或任意 message 作为失败身份；
- 冲突、保护、引用中和不可分配必须区分；
- cancellation/timeout/resource exhaustion 如后续引入异步接口，使用独立稳定码，不折叠为 InternalFailure；
- 日志记录 request_id、资源 id/code 和稳定错误码，诊断只在转换边界记录一次。

## 10. 路由与 Handler

在 `Routes.cc` 中注册 RoleHandler 和 PermissionHandler。静态路径必须先于参数路径：

~~~text
/admin/user-role-options
/admin/roles
/admin/roles/{id}
/admin/roles/{id}/permissions
/admin/roles/{id}/manage-scopes
~~~

当前 transport 使用显式路由注册时，应沿用现有冲突检测、路径归一化、body 大小和 Origin 策略。角色/权限集合请求单独允许 64 KiB，其他请求保持 8 KiB。

## 11. Readiness

`/ready` 增加 RBAC 检查：

- roles/permissions/关联表存在；
- 四个 system_key 角色存在且 code 唯一；
- 代码注册的 server 权限全部存在、未 archived、source=system、enforcement=server；非安全底线权限允许按管理配置 disabled；
- 数据库中不存在未被代码注册的 server/system 权限，无论其当前状态如何；
- super_admin 拥有全部安全底线；
- super_admin manage scope 覆盖全部非 archived 角色；
- users.role_id 非空，且 users.role 与 roles.code 一致；
- users.login_identifier/canonical/type 非空，canonical 唯一且用当前规范化组件重算一致；
- 数据库中不存在旧 uid/username 物理列，避免运行时误用双模型；
- 不存在用户绑定 archived 角色；active 用户绑定 disabled 角色属于合法的角色级紧急撤权状态，不使 readiness 失败。

readiness 失败不能自动修复生产数据；只返回不可用并记录稳定、脱敏诊断。

## 12. 审计和可观测性

运行日志：

- RBAC schema/seed 检查结果；
- 授权拒绝按聚合指标记录，避免每次拒绝刷日志；
- 角色权限变更记录 resource id、版本和变更计数；
- 不重复记录事务内完整安全审计。

建议指标：

- `szx_admin_authz_check_total{result,permission}`；
- `szx_admin_authz_check_duration_ms`；
- `szx_admin_rbac_mutation_total{resource,operation,result}`；
- `szx_admin_role_users{role_code}` 仅在角色数量有界且 code 不含敏感信息时启用；
- readiness RBAC gate 状态。

## 13. CMake 与文件接入

- 新源文件加入现有 `szx_admin_service` target，不创建重复基础库；
- 继续复用 common 的 Result、Json、Uuid、TimeHelper 与数据库能力；
- 不新增 ORM、缓存或 JSON 依赖；
- 测试文件加入 `tests/rbac/CMakeLists.txt`；
- OpenAPI 和 Admin dist 仍由现有静态资源路径发布。

## 14. 代码清理顺序

1. 先建立新表、Repository 和 AuthorizationService；
2. 增加统一登录标识列并完成碰撞预检；Repository 切换后再删除旧列；
3. 双读验证：测试环境比较固定 Policy 与数据库权限结果；
4. 用户查询和 `/client/me/permissions` 切换到新模型；
5. 所有服务鉴权切换；
6. 增加角色/权限管理接口；
7. 前端移除固定角色和双登录输入假设；
8. 删除固定矩阵实现，仅保留必要 permission code 常量；
9. 搜索并清除 `role == "admin"`、`role == "super_admin"` 以及 uid/username 数据库查询分支；业务身份判断改为 system_key，仅允许在最后超管与 bootstrap 规则中使用。

## 15. 禁止事项

- QML/Vue/Client 不能作为最终授权方；
- 不在 JWT 中嵌入并信任完整权限数组；
- 不根据角色 code 前缀、名称或数字等级推断权限；
- 不允许 API 创建 server enforcement 权限；
- 不允许删除/重命名已用 code；
- 不用错误 message 文本做控制流；
- 不因缓存、数据库异常或未知权限而默认放行；
- 不为减少 JOIN 而把 role_permissions 序列化进 users 表。
