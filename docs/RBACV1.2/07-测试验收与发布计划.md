# RBAC V1.2 测试验收与发布计划

## 1. 验收范围

本计划覆盖：

- 数据迁移和数据一致性；
- Repository、Service、HTTP API；
- 认证、授权、范围控制与会话失效；
- Admin 前端及浏览器端到端流程；
- 并发、性能、安全、审计和故障恢复；
- 生产发布、观测和回滚。

只有“能创建角色”不足以验收。必须证明新权限真实影响后端授权、旧会话及时失效、越权路径被拒绝、迁移可重试且第一阶段能力无回归。

## 2. 测试环境矩阵

| 环境 | 用途 |
|---|---|
| MySQL 8.0 当前最低支持小版本 | 主功能、migration、约束 |
| 全新空库 | 从 migration 1 执行到最新 |
| V1.1 真实/匿名化库副本 | 升级兼容 |
| 部分 DDL 已执行但 journal 未写 | migration 可重试 |
| 单实例服务 | 基础功能 |
| 双实例共享数据库 | 版本失效、migration lock、并发 |
| Chromium 当前支持版 | Admin E2E |
| Release 构建 | 性能和发布验收 |

验收记录必须写明 commit、构建类型、MySQL 版本、配置摘要、浏览器版本、数据规模和命令。

## 3. 数据库与 Migration 测试

### 3.1 正向

- 空库最终 schema 与设计一致；
- V1.1 所有用户 role_id 正确回填；
- V1.1 uid/username 正确映射为 login_identifier/identifier_type；
- 统一 canonical 重算与运行时一致，旧 uid/username 四列最终删除；
- 四内置角色 code/system_key 正确；
- 12 个旧权限映射逐项等价；
- 12 个 V1.2 RBAC 权限正确创建；
- admin/super_admin 默认 manage scope 正确；
- users.role CHECK 已移除且字段可保存 64 字符 code；
- FK、唯一键、索引和 CHECK 生效；
- schema_migrations checksum 正确。

### 3.2 负向

- 未知旧 role 字符串导致 migration 失败而非默认映射；
- system_key/code 冲突失败；
- 找不到或找到多个旧 role CHECK 时失败；
- applied checksum 被篡改时 `2224`；
- 数据库含未来 migration version 时失败；
- DDL 部分成功后重启可安全重试；
- 双实例只有一个获得 migration lock。
- 旧行 uid/username 同时为空或同时非空时迁移失败；
- 仅大小写不同的旧 UID、UID 与 username 跨类型 canonical 碰撞时迁移失败且不自动合并；
- 碰撞修复后重跑可成功，不覆盖其他用户或密码数据。

### 3.3 一致性查询

验收时运行并要求结果为 0：

~~~sql
SELECT COUNT(*)
FROM users u
LEFT JOIN roles r ON r.id = u.role_id
WHERE r.id IS NULL OR u.role <> r.code;

SELECT COUNT(*)
FROM role_permissions rp
LEFT JOIN roles r ON r.id = rp.role_id
LEFT JOIN permissions p ON p.id = rp.permission_id
WHERE r.id IS NULL OR p.id IS NULL;

SELECT COUNT(*)
FROM users u
JOIN roles r ON r.id = u.role_id
WHERE r.status = 'archived';

SELECT COUNT(*)
FROM users
WHERE login_identifier IS NULL
   OR login_identifier_canonical IS NULL
   OR identifier_type NOT IN ('username', 'uid');

SELECT login_identifier_canonical, COUNT(*)
FROM users
GROUP BY login_identifier_canonical
HAVING COUNT(*) > 1;
~~~

active 用户绑定 disabled 角色是合法的紧急撤权状态，不应被一致性查询判为 migration/readiness 失败。

## 4. 单元测试

### 4.1 Validation

- login_identifier 空白、字节/字符边界、Unicode NFC/case fold、case fold 扩展到 128 字符边界和控制字符；
- identifier_type 白名单以及“类型不改变规范化结果”；
- display_name 可重复但不能为空；
- role code 边界、非法大小写、点、连字符、空白、超长；
- permission code 多段格式、连续点、Unicode、超长；
- 自定义权限的 SZX Admin 保留前缀；
- name/description/module Unicode 长度和控制字符；
- UUID 数组重复、超限、非法值；
- status/source/enforcement 白名单。

### 4.2 AuthorizationService

至少覆盖：

- active 用户 + active 角色 + active permission 允许；
- 缺 permission 拒绝；
- permission disabled 拒绝；
- user/role disabled 拒绝；
- user authz_version 不匹配；
- role authz_version 不匹配；
- token role_id 不匹配当前用户；
- manage scope 存在/缺失；
- actor/target/new role 三方范围；
- 未知 server permission fail closed；
- Repository 异常映射为稳定错误码。

### 4.3 RoleService

- 创建、code 冲突；
- profile no-op 不增 version；
- permission set no-op 不增版本；
- permission set 差异和排序；
- super_admin 安全底线不可移除；
- super_admin 必选 scope 不可移除；
- protected role 不可停用/归档；
- 有用户引用不能归档；
- If-Match 冲突；
- 审计失败事务整体回滚。

### 4.4 PermissionService

- API 只能创建 custom/client；
- system 属性不可修改；
- protected permission 不可停用/归档；
- 有引用不能归档；
- 停用和重新启用时关联角色 authz_version 全部递增；
- 关联角色超过上限拒绝；
- 唯一键冲突映射 2228；
- 审计失败回滚。

## 5. API 集成测试

每个新增 operation 至少覆盖：

- 正常成功；
- 无 token/过期 token；
- 缺所需权限；
- 非法 path/query/body；
- 未知字段；
- body 超限；
- 资源不存在；
- If-Match 缺失/非法/冲突；
- 保护规则；
- 数据库失败；
- 审计失败；
- 响应 DTO 和 request_id。

现有接口回归：

- 登录、refresh、logout、change-password；
- 用户列表/详情/创建/更新/启停/解锁/换角色/重置密码；
- audit/behavior 查询；
- client permissions/behavior event；
- health/ready/static/Swagger。

用户 API 兼容专项：

- 新格式创建 username/uid 类型账号；
- 旧 uid 或 username 格式仍可创建，返回 Deprecation Header；
- 新旧字段混用、旧 uid+username 同时出现分别返回稳定错误码；
- User 正式字段始终存在，旧别名只返回与 identifier_type 对应的一个；
- login_identifier 大小写变体登录到同一用户；
- canonical 冲突统一返回 `409 / 2208`，不泄露原账号类型；
- 用户列表搜索同时匹配 login_identifier/display_name；
- 审计和行为列表的账号展示使用统一 login_identifier。
- 审计/行为 DTO 同时返回正式账号字段与值相同的 V1 兼容别名。

## 6. 安全测试矩阵

| 场景 | 预期 |
|---|---|
| 有 user.update 但无目标 role scope | 403 |
| 可管理当前角色但不可管理新角色，尝试换角色 | 403 |
| 直接修改请求加入 system_key/source/server | 422 |
| 创建名为 user.delete 的 custom 权限 | 422 / 2206，服务端命名空间受保护 |
| 删除 super_admin 安全权限 | 409 / 2233 |
| 禁用 super_admin 角色 | 409 / 2231 |
| 禁用安全底线权限 | 409 / 2232 |
| 归档有用户角色 | 409 / 2229 |
| 归档被引用权限 | 409 / 2230 |
| 使用归档 code 再创建 | 409 / 2227 或 2228 |
| 枚举不可见角色用户 | 403/404，不能泄露数量 |
| JWT 篡改 role/role version | 401 |
| V1.1 access token 访问 V1.2 | 401，可 refresh |
| 权限变更后重放旧 access | 401 |
| SQL/异常文本 | 不进入响应和审计 details |
| 用 U10086 创建 uid 后再创建 u10086 | 409 / 2208 |
| 新请求同时提交 login_identifier 和 uid | 422 / 2206 |
| 旧请求同时提交 uid 和 username | 422 / 2207 |

额外执行参数化 SQL、XSS 显示、CSRF/Origin、IDOR、批量 UUID、超大数组和 Unicode 混淆测试。

## 7. 并发测试

- 两请求以相同 If-Match 修改角色，恰好一个成功；
- 同时替换 permission set，不出现混合集合；
- 同时停用权限和更新角色集合，结果满足串行化之一；
- 归档目标角色时，所有失去该 target scope 的 manager role 授权版本递增；
- 同时将用户移出最后一个 active super_admin 和禁用该用户，至少一个被保护拒绝；
- 创建同 role/permission code，恰好一个成功，另一个稳定冲突；
- 双实例修改角色后，另一个实例立即拒绝旧 token；
- 锁等待超时映射稳定错误，不泄露诊断；
- 死锁重试策略若未实现则明确失败，不能自动重放非幂等审计。

## 8. 会话失效验收

| 变化 | 旧 access | refresh | 预期新 permissions |
|---|---|---|---|
| 用户换角色 | 401 | 已撤销，需登录 | 新角色 |
| 用户 disabled | 401 | 拒绝 | 无 |
| 角色权限变化 | 401 | 可换新 token | 新集合 |
| 角色 disabled | 401 | 拒绝 | 无 |
| 权限 disabled | 受影响角色 401 | 可换新 token | 移除该权限 |
| 权限重新 active | 受影响角色 401 | 可换新 token | 恢复该权限 |
| 仅名称/描述变化 | 继续有效 | 正常 | 权限不变 |

从事务提交完成到旧 access 被拒绝的目标为下一次请求即生效，不允许等待缓存 TTL。

## 9. 前端与 E2E 验收

- 动态角色名贯穿登录、首页、用户列表、详情和编辑；
- 新建权限 → 新建角色 → 分配权限 → 新建用户 → 登录验证；
- 修改角色权限后当前用户会话恢复流程清晰；
- role.read 与 permission.read 分别控制页面；
- 按钮能力控制与后端 403 一致；
- protected/disabled/archived 状态可识别；
- 归档确认要求正确 code；
- 409 version conflict 提示刷新；
- request_id 可复制；
- 浏览器刷新和深层路由正确；
- 键盘可操作、label/焦点/错误状态可访问；
- 500 权限页面无明显卡顿。

## 10. 性能验收

数据集：

- 10,000 用户；
- 100 角色；
- 500 权限；
- 每角色平均 100 权限；
- 10 个并发 Admin，请求端并发按现有服务容量配置。

指标：

| 指标 | 目标 |
|---|---:|
| 单权限鉴权数据库新增 P95 | <= 2 ms |
| GET /client/me/permissions P95 | <= 50 ms |
| 角色/权限列表 P95 | <= 100 ms |
| 100 权限集合替换 P95 | <= 200 ms |
| 角色权限变化到旧 token 拒绝 | 下一请求 |
| migration 10,000 用户回填 | 维护窗口预算内，实测记录 |

所有性能比较使用等价 Release 构建、数据库配置和预热条件。未达目标必须给出 profile 证据和批准的例外，不以主观“足够快”验收。

## 11. 故障与恢复

- 数据库连接中断时授权 fail closed；
- 审计 insert 失败时 RBAC 写操作回滚；
- 服务在权限集合事务中被终止，重启后无部分关系；
- migration 中断后可重试；
- readiness 对缺 seed、权限注册不一致、role 镜像不一致失败；
- 备份恢复后服务能够启动并通过 readiness；
- 日志中没有凭据、token、Cookie、SQL 连接密码。

## 12. 发布步骤

### 12.1 发布前

1. 冻结 RBAC 管理变更窗口；
2. 记录 V1.1 用户/角色/日志表行数和关键一致性查询；
3. 生成统一登录标识碰撞报告，要求零未处理冲突；
4. 完成数据库全量备份并验证可恢复；
5. 在生产副本演练 migration，记录 Unicode 回填、索引建立耗时和锁影响；
6. 构建 Release 服务和 Admin 静态资源；
7. 校验 OpenAPI、配置、密钥路径和包内容；
8. 准备回滚二进制和数据库恢复命令；
9. 通知旧 access token 将在升级后通过 refresh 更新，并通知旧 uid/username API 已进入兼容期。

### 12.2 发布中

1. 停止或摘除写流量；
2. 确认没有另一实例执行 migration；
3. 部署 V1.2 服务并执行 migrations；
4. 验证 `/health` 与 `/ready`；
5. 运行角色和统一登录标识一致性 SQL；
6. 验证 bootstrap/super_admin 登录和 refresh；
7. 验证角色/权限只读接口；
8. 恢复一台实例流量进行冒烟；
9. 验证创建临时自定义权限/角色并清理或归档；
10. 逐步恢复全部实例和 Admin 入口。

### 12.3 发布后监控

至少观察一个 access token TTL + refresh 空闲窗口：

- 401/403/409 比例；
- 旧 uid/username 创建格式的聚合使用量；
- refresh 成功率；
- readiness；
- DB 锁等待和死锁；
- authz P95/P99；
- RBAC mutation 失败率；
- AuditWriteFailed；
- 用户反馈的菜单/权限不同步。

## 13. 回滚

### 13.1 标准回滚

统一登录标识 migration 会删除 V1.1 依赖的 uid/username 列，因此 V1.2 不允许只回滚二进制。

1. 停止 V1.2 写流量；
2. 保存故障现场和日志；
3. 恢复上线前数据库备份；
4. 部署 V1.1 二进制和对应 Admin dist；
5. 验证 schema_migrations、用户数量、登录和第一阶段接口；
6. 宣布 V1.2 窗口失败并记录数据丢失范围；
7. 不在生产执行未经演练的手工 DOWN SQL。
