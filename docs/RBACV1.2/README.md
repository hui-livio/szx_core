# SZX Admin RBAC V1.2 设计文档集

> 文档版本：V1.2-draft
> 编制日期：2026-09-24
> 基线版本：`docs/RBAC/` 描述的第一阶段实现
> 适用范围：`tools/szx_admin`、`tools/szx_admin/web/admin`、`tests/rbac`

## 1. 目标

V1.2 将第一阶段的“四个固定角色 + 编译期权限矩阵”升级为可管理的数据库驱动 RBAC：

- 超级管理员可以创建、编辑、停用和归档自定义角色；
- 可以创建和管理供业务客户端使用的自定义权限；
- 可以为角色配置权限集合和可管理的目标角色范围；
- 将第一阶段重复的 `uid/username` 双登录字段统一为单一登录标识模型；
- 用户仍只绑定一个角色，角色变更继续使现有授权会话失效；
- 内置角色、服务端权限、安全审计和最后一个超级管理员保护保持兼容；
- `/api/v1` 现有用户与权限接口保持向后兼容，以新增字段和新增资源接口扩展。

## 2. 已确定的设计边界

| 项目 | V1.2 决策 |
|---|---|
| 租户模型 | 仍为单项目，不引入 tenant/project 维度 |
| 用户角色 | 每个用户恰好一个角色，不支持多角色叠加 |
| 登录标识 | 数据库只保存一套 `login_identifier`；`identifier_type` 仅标记 username/uid 来源，不改变匹配规则 |
| 标识匹配 | trim + Unicode NFC + locale-independent case fold；username 与 UID 共用不区分大小写的唯一命名空间 |
| 权限效果 | 仅支持 Allow，不引入 Deny、条件表达式或优先级 |
| 用户管理范围 | 使用显式 `role_manage_scopes`，不根据角色名称或可编辑排序推断 |
| 服务端权限 | 由代码注册、migration 落库；不能通过管理 API 凭空创建 |
| 自定义权限 | 管理 API 创建的权限用于 Client/业务模块消费，创建后不会自动保护后端路由 |
| 内置资源 | 四个内置角色、服务端权限码和超级管理员安全底线受保护 |
| 删除语义 | 角色和权限采用归档，不复用历史 code；有关联时先解除关联 |
| 授权失效 | 用户变更使用 `users.authz_version`；角色授权变更使用 `roles.authz_version` |
| API 版本 | 兼容扩展 `/api/v1`；破坏性变更另开 `/api/v2`，本阶段不启用 |

## 4. 与第一阶段的关系

第一阶段中的登录、刷新、退出、改密、用户生命周期、安全审计、行为事件、`If-Match` 乐观锁和统一错误响应继续作为 V1.2 基础。V1.2 主要替换以下硬编码点：

- `Policy.cc` 的固定角色能力位掩码；
- `validRole()` 和 `mayTarget()` 的字符串白名单；
- Admin 前端的 `Role` 字面量联合类型和固定中文映射；
- `users.role` 上的四角色 CHECK 约束；
- OpenAPI 中枚举为四个角色的请求与响应定义。
- `users.uid/uid_canonical/username/username_canonical` 四列及前后端二选一分支。

## 5. 评审重点

评审时应优先确认：

1. 是否接受 V1.2 继续保持“单用户单角色”；
2. 是否接受自定义权限默认仅为 Client/业务权限，服务端权限必须随代码发布；
3. 角色管理范围是否采用显式关系表，而不是角色等级数字；
4. 是否接受角色授权版本进入 JWT，并在角色权限变更后立即拒绝旧 access token；
5. 生产是否允许应用启动自动执行 V1.2 migration，或要求独立审核执行。
6. 是否接受 UID 与用户名统一为不区分大小写的登录标识；旧库若存在仅大小写不同的 UID，必须在升级前人工消除冲突。

以上任一项改变，都需要同步调整数据库、API、前端和迁移计划。
