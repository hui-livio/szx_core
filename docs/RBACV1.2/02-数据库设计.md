# RBAC V1.2 数据库设计

## 1. 设计原则

- MySQL 8.0+、InnoDB、`utf8mb4`、UTC，与第一阶段保持一致；
- 继续使用嵌入 `DatabaseInitialization.cc` 的不可变 migration；
- 授权关系使用规范化关联表，不在 JSON 中保存权限列表；
- 用户只保存一套登录标识列；`identifier_type` 表示来源，不产生第二套唯一性或查询规则；
- 稳定机器标识使用不可修改的 `code`，显示文本与 code 分离；
- 角色和权限只归档、不物理删除，历史 code 永久保留；
- 数据库约束保证引用完整性，Service 事务保证安全底线和业务不变量；
- 所有时间字段使用 `datetime(6)`；
- ID 使用现有 36 字符 UUID 字符串，后续若统一二进制 UUID 再单独迁移。

## 3. 表设计

### 3.0 users 登录标识统一

V1.2 将第一阶段的 `uid`、`uid_canonical`、`username`、`username_canonical` 四列合并为：

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| login_identifier | varchar(64) | NOT NULL | 登录标识展示值，创建后不可修改 |
| login_identifier_canonical | varchar(128) | NOT NULL, UNIQUE, bin collation | 登录匹配和唯一约束值；为 Unicode case fold 扩展预留空间 |
| identifier_type | varchar(16) | username/uid | 来源标签，不参与匹配算法 |
| display_name | varchar(128) | NOT NULL | 显示名称/昵称，可重复且允许修改 |

统一规则：

- `login_identifier` 原始输入最多 512 UTF-8 字节，trim 后执行 Unicode NFC；
- `login_identifier_canonical` 在 NFC 后执行 locale-independent Unicode case fold；
- 完整 case fold 可能扩展字符（例如一个字符变成多个字符），因此 canonical 最大允许 128 个 Unicode 字符；超出时请求返回校验错误，migration 返回冲突/失败而不是截断；
- username 和 UID 共用一个 canonical 唯一索引，`U10086` 与 `u10086` 视为同一登录标识；
- `identifier_type` 只用于界面显示、导入来源和兼容响应，不能用于选择查询、唯一性或大小写规则；
- `display_name` 不参与登录或唯一性校验；
- 登录接口继续接收 `identifier`，使用同一 canonical 规则查询；
- 登录标识创建后不可修改；未来如需修改必须单独设计高风险账号迁移接口和审计流程。

~~~sql
UNIQUE KEY uk_users_login_identifier_canonical
  (login_identifier_canonical),
CONSTRAINT chk_users_identifier_type
  CHECK (identifier_type IN ('username', 'uid'))
~~~

不保留 `uid`、`username` 物理兼容列，也不使用 generated columns 模拟旧结构。`/api/v1` 的旧字段由 API 层根据 `identifier_type` 和 `login_identifier` 计算。

### 3.1 roles

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | char(36) | PK | 角色 UUID |
| code | varchar(64) | NOT NULL, UNIQUE, bin collation | 稳定 API 标识；创建后不可修改 |
| name | varchar(128) | NOT NULL | 显示名称 |
| description | varchar(512) | NOT NULL DEFAULT '' | 说明 |
| system_key | varchar(32) | NULL, UNIQUE, bin collation | 内置身份；仅四个内置角色非空 |
| status | varchar(16) | active/disabled/archived | 状态 |
| version | int unsigned | > 0 | 资源乐观锁版本 |
| authz_version | int unsigned | > 0 | 授权语义版本，进入 JWT |
| created_by | char(36) | FK users，可空 | bootstrap/migration 创建时为空 |
| updated_by | char(36) | FK users，可空 | 最近修改人 |
| archived_at | datetime(6) | NULL | 归档时间 |
| created_at | datetime(6) | NOT NULL | 创建时间 |
| updated_at | datetime(6) | NOT NULL | 更新时间 |

约束：

- `code` 格式：`^[a-z][a-z0-9_]{1,63}$`，2–64 字符；
- code 使用 `utf8mb4_0900_bin`，虽然输入只允许 ASCII，仍明确精确比较；
- `system_key` 只能由 migration 写入，管理 API 不接受；
- `system_key=super_admin` 时 Service 禁止 disabled/archived；
- archived 时 `archived_at` 必须非空，其他状态必须为空；
- code 永不修改、永不复用。

索引：

~~~sql
UNIQUE KEY uk_roles_code (code)
UNIQUE KEY uk_roles_system_key (system_key)
KEY idx_roles_status_name (status, name)
~~~

### 3.2 permissions

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | char(36) | PK | 权限 UUID |
| code | varchar(96) | NOT NULL, UNIQUE, bin collation | 稳定能力码 |
| name | varchar(128) | NOT NULL | 显示名称 |
| description | varchar(512) | NOT NULL DEFAULT '' | 权限用途 |
| module | varchar(64) | NOT NULL | 分类，例如 user、rbac、audit、business |
| enforcement | varchar(16) | server/client | 执行边界 |
| source | varchar(16) | system/custom | 来源 |
| status | varchar(16) | active/disabled/archived | 状态 |
| required_for_super_admin | boolean | NOT NULL DEFAULT false | 超管安全底线 |
| version | int unsigned | > 0 | 资源乐观锁版本 |
| created_by / updated_by | char(36) | FK users，可空 | 操作者 |
| archived_at | datetime(6) | NULL | 归档时间 |
| created_at / updated_at | datetime(6) | NOT NULL | 时间 |

约束：

- `code` 格式：`^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`，3–96 字符；
- API 创建权限时强制 `enforcement=client`、`source=custom`；
- 自定义权限不得使用 `auth.`、`user.`、`role.`、`permission.`、`audit.`、`behavior.`、`system.` 保留前缀；
- `source=system` 或 `required_for_super_admin=true` 的权限不可归档；
- system 权限的 code、enforcement、source 和安全底线标记不可由 API 修改；
- archived 权限不能再分配给角色。

索引：

~~~sql
UNIQUE KEY uk_permissions_code (code)
KEY idx_permissions_status_module (status, module, code)
KEY idx_permissions_source_enforcement (source, enforcement)
~~~

### 3.3 role_permissions

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| role_id | char(36) | PK, FK roles | 角色 |
| permission_id | char(36) | PK, FK permissions | 权限 |
| assigned_by | char(36) | FK users，可空 | migration 时为空 |
| assigned_at | datetime(6) | NOT NULL | 分配时间 |

主键 `(role_id, permission_id)` 防止重复。外键使用 `ON DELETE RESTRICT`；V1.2 不物理删除角色或权限。

反向查询索引：

~~~sql
KEY idx_role_permissions_permission (permission_id, role_id)
~~~

### 3.4 role_manage_scopes

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| manager_role_id | char(36) | PK, FK roles | 管理者角色 |
| target_role_id | char(36) | PK, FK roles | 可管理目标角色 |
| assigned_by | char(36) | FK users，可空 | 操作者 |
| assigned_at | datetime(6) | NOT NULL | 分配时间 |

该表只表达“目标角色范围”，不能替代 `user.*` 权限。允许管理本角色并不代表允许用户修改自己；自我角色变更和自我禁用仍由 Service 拒绝。

默认迁移关系：

| manager | target |
|---|---|
| admin | operator |
| admin | engineer |
| super_admin | operator |
| super_admin | engineer |
| super_admin | admin |
| super_admin | super_admin |

### 3.5 users 变更

新增：

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| role_id | char(36) | NOT NULL, FK roles | 授权真相 |
| login_identifier | varchar(64) | NOT NULL | 唯一登录标识展示值 |
| login_identifier_canonical | varchar(128) | NOT NULL, UNIQUE | 统一规范化登录标识 |
| identifier_type | varchar(16) | NOT NULL, CHECK | username/uid 来源标签 |

保留并调整：

| 字段 | 调整 |
|---|---|
| role | 从 varchar(16) 四值 CHECK 改为 varchar(64)，作为兼容 role code 镜像 |
| display_name | 保留；明确为可重复、可修改且不参与登录的昵称/展示名称 |

删除：

| 字段 | 原因 |
|---|---|
| uid / uid_canonical | 与 username 表达同一登录标识概念 |
| username / username_canonical | 合并到统一登录标识列 |

V1.2 服务的授权与关联查询只使用 `role_id`。`users.role` 在创建和角色变更事务中与 `roles.code` 同步，用于：

- 保持 V1 API User 和登录 DTO 的字段兼容；
- 降低第一轮改造中所有查询同时 JOIN 的范围；
- 为运维排查保留可读快照。

写入后必须校验 `users.role = roles.code`。新增数据库一致性集成测试，定期运维检查也应检测不一致。V1.3 可在所有消费者完成迁移后评估移除冗余列；V1.2 不移除。

索引：

~~~sql
KEY idx_users_role_id_status (role_id, status)
CONSTRAINT fk_users_role FOREIGN KEY (role_id) REFERENCES roles(id) ON DELETE RESTRICT
UNIQUE KEY uk_users_login_identifier_canonical (login_identifier_canonical)
CONSTRAINT chk_users_identifier_type CHECK (identifier_type IN ('username', 'uid'))
~~~

## 4. 建表 SQL 草案

以下 SQL 用于设计评审。实施时应拆为新的不可变 migration，并为最终文本计算 SHA-256 checksum。

~~~sql
CREATE TABLE IF NOT EXISTS roles (
  id char(36) NOT NULL PRIMARY KEY,
  code varchar(64) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin NOT NULL,
  name varchar(128) NOT NULL,
  description varchar(512) NOT NULL DEFAULT '',
  system_key varchar(32) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin,
  status varchar(16) NOT NULL DEFAULT 'active',
  version int unsigned NOT NULL DEFAULT 1,
  authz_version int unsigned NOT NULL DEFAULT 1,
  created_by char(36),
  updated_by char(36),
  archived_at datetime(6),
  created_at datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
    ON UPDATE CURRENT_TIMESTAMP(6),
  CONSTRAINT uk_roles_code UNIQUE (code),
  CONSTRAINT uk_roles_system_key UNIQUE (system_key),
  CONSTRAINT chk_roles_status
    CHECK (status IN ('active', 'disabled', 'archived')),
  CONSTRAINT chk_roles_versions CHECK (version > 0 AND authz_version > 0),
  CONSTRAINT chk_roles_archive CHECK (
    (status = 'archived' AND archived_at IS NOT NULL) OR
    (status <> 'archived' AND archived_at IS NULL)
  ),
  CONSTRAINT fk_roles_created_by FOREIGN KEY (created_by) REFERENCES users(id),
  CONSTRAINT fk_roles_updated_by FOREIGN KEY (updated_by) REFERENCES users(id),
  KEY idx_roles_status_name (status, name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE IF NOT EXISTS permissions (
  id char(36) NOT NULL PRIMARY KEY,
  code varchar(96) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin NOT NULL,
  name varchar(128) NOT NULL,
  description varchar(512) NOT NULL DEFAULT '',
  module varchar(64) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin NOT NULL,
  enforcement varchar(16) NOT NULL,
  source varchar(16) NOT NULL,
  status varchar(16) NOT NULL DEFAULT 'active',
  required_for_super_admin boolean NOT NULL DEFAULT false,
  version int unsigned NOT NULL DEFAULT 1,
  created_by char(36),
  updated_by char(36),
  archived_at datetime(6),
  created_at datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
    ON UPDATE CURRENT_TIMESTAMP(6),
  CONSTRAINT uk_permissions_code UNIQUE (code),
  CONSTRAINT chk_permissions_enforcement CHECK (enforcement IN ('server', 'client')),
  CONSTRAINT chk_permissions_source CHECK (source IN ('system', 'custom')),
  CONSTRAINT chk_permissions_status
    CHECK (status IN ('active', 'disabled', 'archived')),
  CONSTRAINT chk_permissions_version CHECK (version > 0),
  CONSTRAINT chk_permissions_archive CHECK (
    (status = 'archived' AND archived_at IS NOT NULL) OR
    (status <> 'archived' AND archived_at IS NULL)
  ),
  CONSTRAINT fk_permissions_created_by FOREIGN KEY (created_by) REFERENCES users(id),
  CONSTRAINT fk_permissions_updated_by FOREIGN KEY (updated_by) REFERENCES users(id),
  KEY idx_permissions_status_module (status, module, code),
  KEY idx_permissions_source_enforcement (source, enforcement)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE IF NOT EXISTS role_permissions (
  role_id char(36) NOT NULL,
  permission_id char(36) NOT NULL,
  assigned_by char(36),
  assigned_at datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (role_id, permission_id),
  CONSTRAINT fk_role_permissions_role
    FOREIGN KEY (role_id) REFERENCES roles(id) ON DELETE RESTRICT,
  CONSTRAINT fk_role_permissions_permission
    FOREIGN KEY (permission_id) REFERENCES permissions(id) ON DELETE RESTRICT,
  CONSTRAINT fk_role_permissions_assigned_by
    FOREIGN KEY (assigned_by) REFERENCES users(id) ON DELETE SET NULL,
  KEY idx_role_permissions_permission (permission_id, role_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE IF NOT EXISTS role_manage_scopes (
  manager_role_id char(36) NOT NULL,
  target_role_id char(36) NOT NULL,
  assigned_by char(36),
  assigned_at datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (manager_role_id, target_role_id),
  CONSTRAINT fk_role_scopes_manager
    FOREIGN KEY (manager_role_id) REFERENCES roles(id) ON DELETE RESTRICT,
  CONSTRAINT fk_role_scopes_target
    FOREIGN KEY (target_role_id) REFERENCES roles(id) ON DELETE RESTRICT,
  CONSTRAINT fk_role_scopes_assigned_by
    FOREIGN KEY (assigned_by) REFERENCES users(id) ON DELETE SET NULL,
  KEY idx_role_scopes_target (target_role_id, manager_role_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
~~~

## 6. 初始角色权限映射

迁移后的有效权限必须与第一阶段完全一致，再为 super_admin 增加 V1.2 RBAC 管理权限：

| 角色 | 初始化权限 |
|---|---|
| operator | business.read、business.operate |
| engineer | operator 权限 + engineering.configure |
| admin | engineer 权限 + user.read/create/update/status/unlock/password.reset + audit.read + behavior.read |
| super_admin | admin 权限 + user.role.assign + 全部 V1.2 RBAC 管理权限 |

不自动给 admin 增加角色/权限管理权限。后续如业务需要，可由 super_admin 配置非底线权限和 manage scope。

## 7. Migration 设计

当前已发布 migration 1–5 必须保持字节级不变。建议追加：

### Migration 6：RBAC 目录

- 创建 `roles`、`permissions`、`role_permissions`、`role_manage_scopes`；
- 插入四个确定性 UUID 的内置角色；
- 插入已有 12 个权限和新增 12 个 RBAC 权限；
- 写入第一阶段等价角色权限映射；
- 写入 admin/super_admin 默认 manage scope；
- 所有种子使用确定性 ID 和幂等插入，支持 DDL 已提交但 journal 未写入后的重试。

### Migration 7：用户角色外键

- `users` 增加可空 `role_id`；
- 按 `users.role = roles.code` 回填；
- 启动前验证所有用户均成功匹配；
- 增加索引和外键；
- 将 `role_id` 改为 NOT NULL。

### Migration 8：兼容 role 字段

- 从 `information_schema.CHECK_CONSTRAINTS` 找出引用 `users.role` 且包含四个旧值的 CHECK；
- 要求恰好找到一个；未找到或找到多个均返回 `MIGRATION_CONFLICT`；
- 使用审核过的动态 DDL 删除该约束；
- 将 `users.role` 扩大为 `varchar(64)`；
- 数据一致性查询要求 `users.role = roles.code`。

动态约束发现必须在 migration 实现层提供专用步骤，不能把数据库返回的任意名称拼接进通用 SQL。约束名只接受从 `information_schema` 返回且符合 MySQL 标识符规则的当前库对象。

### Migration 9：统一登录标识

1. 为 `users` 增加可空的 `login_identifier`、`login_identifier_canonical`、`identifier_type`；
2. 对每行要求旧 `uid/username` 恰好一个非空，并映射：
   - uid 非空：`login_identifier=uid`、`identifier_type=uid`；
   - username 非空：`login_identifier=username`、`identifier_type=username`；
3. 由与运行时相同的规范化组件计算新的 case-fold canonical，不能依赖 MySQL `LOWER()` 替代 Unicode 规则；结果超过 128 个 Unicode 字符时停止迁移并报告用户 id；
4. 在创建唯一索引前执行全表碰撞检测。若两个旧账号折叠为同一 canonical（包括仅大小写不同的 UID、UID 与 username 跨类型冲突），返回 `MIGRATION_CONFLICT / 2224`，受控迁移日志只记录冲突用户 id、类型和 canonical 摘要；
5. 对无冲突数据创建唯一索引和 type CHECK，将三个新字段改为 NOT NULL；
6. 切换 Repository 和登录查询到新字段后，删除旧 unique index、旧二选一 CHECK 和 `uid/uid_canonical/username/username_canonical` 四列。

该 migration 不能自动选择某个冲突账号、改变大小写或合并用户。升级前由管理员处理冲突，并保留处理审计。

### Migration 10：授权版本上线

- 不需要批量修改现有用户版本；
- 确认所有角色 `authz_version=1`；
- 服务 readiness 增加 RBAC schema/种子检查；
- 此 migration 与包含新 JWT 校验逻辑的二进制一起发布。

如现有 migration 框架不适合安全执行约束发现或应用级 Unicode 回填，实施阶段可以把 Migration 8/9 改成“已审核的部署前迁移工具 + 应用 schema gate”，但不能使用数据库 `LOWER()` 猜测 canonical，也不能忽略旧 CHECK 或碰撞检测。

## 8. Bootstrap 调整

现有 BootstrapAdminService 在 migration 后运行。V1.2 调整为：

1. 查找 `roles.system_key='super_admin'` 且 active；
2. 新建 bootstrap 用户时写 `login_identifier=admin`、`login_identifier_canonical=admin`、`identifier_type=username`，并同时写 `role_id` 和兼容 `role=roles.code`；
3. 已有完成标记时仍不重建默认用户；
4. 没有完成标记但已有 active super_admin 用户时补写标记；
5. 不再仅按用户 role 字符串判断超级管理员身份。

Bootstrap 的 advisory lock、事务和幂等语义保持不变。

## 9. 一致性与并发

以下写操作必须在单事务内：

- 更新角色权限集合 + 递增角色 version/authz_version + 审计；
- 更新角色 scope + 递增角色 version/authz_version + 审计；
- 权限 active/disabled 状态实际变化 + 递增所有关联角色 version/authz_version + 审计；
- 用户换角色 + 同步 role/role_id + 用户版本递增 + refresh 撤销 + 审计；
- 角色归档前检查无用户引用、清空关系、更新状态；对因删除 target scope 而受影响的 manager roles 递增 version/authz_version；最后写审计。

锁顺序统一为：

1. actor user；
2. actor role；
3. target role/permission，按 id 升序；
4. target users，按 id 升序；
5. role_permissions / role_manage_scopes；
6. refresh token；
7. audit insert。

所有集合写入先排序去重，避免不同请求以不同顺序加锁。

## 10. 查询设计

### 10.1 请求授权

单条查询或固定两条查询读取：

- 当前用户状态、user authz_version、role_id；
- 当前角色状态、role authz_version；
- 所需 permission code 是否为 active 且已关联。

不要求每次加载完整权限列表。`GET /client/me/permissions` 才加载并排序全部有效权限。

### 10.2 列表统计

- 角色列表用聚合子查询返回 `user_count`、`permission_count`；
- 权限列表用聚合子查询返回 `role_count`；
- 避免逐项查询造成 N+1；
- 列表总数与 items 在同一隔离语义下读取。

## 11. 数据保留与审计

角色和权限归档后保留记录。`security_audit_logs.details_json` 建议记录：

- 资源 id 和 code；
- 操作前后 version/authz_version；
- added/removed permission codes；
- added/removed target role codes；
- before/after 状态；
- 拒绝原因的稳定错误码。

不得记录 access token、refresh token、密码、Cookie、SQL 或异常文本。

## 12. 回滚约束

- migration 6–10 是前向迁移，不在生产自动执行 DOWN；
- 发布前数据库备份是回滚前提；
- 登录标识统一会删除 V1.1 依赖的 uid/username 列，因此 V1.1 二进制不能直接读取 V1.2 schema；
- 安全回滚路径为恢复上线前数据库备份并回滚二进制；
- V1.2 不提供只回滚二进制的路径，即使尚未创建自定义角色或权限也必须恢复数据库备份。
